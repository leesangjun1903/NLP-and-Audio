## 3. 연구 목적, 제안 방법, 시스템 구조

### 3.1 해결하려는 문제와 연구의 필요성

**[저자 보고]** 저자들이 지적하는 기존 평가의 문제는 크게 세 가지입니다. 첫째, 짧은 상호작용에서는 장기간 공동 계획을 유지하고 수정하는 능력을 평가하기 어렵습니다. 둘째, 복잡한 게임에서는 이동이나 물체 조작의 실패가 협업 점수를 압도할 수 있습니다. 셋째, 대규모 사회 시뮬레이션에서 흥미로운 집단행동이 나타나더라도, 공동 과제를 얼마나 정확히 완수했는지는 별개의 문제입니다〔p.2, Introduction〕. 2609.31590v1

**[제 해석]** 중요한 문제의식은 “여러 모델을 연결하면 답이 더 좋아지는가?”에서 한 단계 나아가, **“서로 다른 정보와 능력을 가진 팀원들이 실제로 의존 관계를 해결했는가?”**를 묻는 데 있습니다. 예를 들어 제작 과제는 한 모델이 정답을 말하는 것만으로 끝나지 않고, 재료 확보·가공·전달·최종 제작이 올바른 순서로 연결되어야 합니다〔p.3, Figure 3〕. 2609.31590v1

> **용어:** 의존 관계는 어떤 행동을 수행하려면 다른 행동의 결과가 먼저 필요하다는 관계로, “광석 채집 → 제련 → 무기 제작”이 대표적인 예

다만 **“기존 연구에는 비대칭 역할이나 과정 평가가 없었다”는 강한 형태의 주장은 피해야 합니다.** 뒤에서 비교하는 Collab-Overcooked는 이미 자원 분리·비대칭 과제 지식·과정 중심 평가를 사용합니다. AgentWorld의 차별성은 이런 요소의 최초 도입보다는 **더 큰 역할 집합, 풍부한 세계, 확장된 실행 예산, CCE를 결합한 구성**에서 찾는 편이 정확합니다〔AgentWorld p.4, Table 1; Collab-Overcooked p.4925, Figure 1·§4.1〕. 2609.31590v1 [ACL 앤솔로지](https://aclanthology.org/2025.emnlp-main.249.pdf)

### 3.2 모델 구조: 새 신경망이 아니라 에이전트 실행·평가 구조

**[저자 보고]** 시스템은 다음과 같은 흐름으로 작동합니다.

```text
공동 과제 + 에이전트별 역할·기술·초기 자원
                    ↓
현재의 지역 관찰 + 자신에게 제공된 채팅 기록 + 과제 문서
                    ↓
              해당 에이전트의 LLM
                    ↓
             정확히 하나의 도구 호출
                    ↓
           게임 상태 변경 또는 메시지 전송
                    ↓
           다음 에이전트가 새 상태를 관찰
                    ↓
          전체 에이전트가 행동하면 다음 라운드
```

기반 환경은 Kaetram이라는 2차원 MMORPG 엔진이며, 실시간 게임을 **순서가 고정된 턴제 실행 방식**으로 변환합니다. 각 에이전트는 자신의 상태와 주변 환경을 설명하는 구조화된 텍스트를 받고, 다른 에이전트의 내부 상태·관찰·행동 기록에는 직접 접근하지 못합니다〔pp.4–5, §3.1〕. 2609.31590v1

> **용어:** MMORPG는 다수의 참여자가 같은 세계에서 활동하는 온라인 역할수행게임, API는 프로그램이 정해진 기능을 호출하는 인터페이스, 턴제는 참여자가 정해진 순서대로 행동하는 방식

중요한 구분은 세 가지입니다.

**첫째, 게임 화면이 있다고 해서 시각 입력을 평가하는 논문은 아닙니다.** 본문에서 설명한 에이전트 입력은 구조화된 텍스트 관찰과 과제 문서입니다. **둘째, 역할의 비대칭성과 서로 다른 LLM을 섞은 팀은 같은 개념이 아닙니다.** 이 논문의 역할 차이는 주로 게임 내 기술·자원·위치의 차이입니다. **셋째, 새로운 신경망 계층, 학습 손실함수, 협업 학습 알고리즘은 제안하지 않습니다.** 실험은 공통 프롬프트와 도구 정의 아래에서 기반 모델을 비교하는 방식입니다〔p.5; p.7, §4.1; pp.17–18, Appendix E〕. 2609.31590v1 2609.31590v1 2609.31590v1

**[제 해석]** 채팅도 한 번의 행동으로 계산되므로, 이 환경에서는 **말하기와 실제 작업이 동일한 행동 예산을 놓고 경쟁**합니다. 따라서 “메시지를 줄이면 효율이 좋아진다”는 결과가 나타나더라도, 그 일부는 이 인터페이스의 비용 구조에 의존할 수 있습니다〔p.5의 실행 규칙; p.20의 행동 단위 정의〕. 2609.31590v1 2609.31590v1

### 3.3 과제 설계와 데이터 구성

**[저자 보고]** 과제는 공동 목표, 에이전트별 설정, 라운드 예산, 관련 게임 문서, Python 성공 검증기로 구성됩니다. 다섯 명의 주석자가 과제를 만들고, 두 LLM을 이용한 예비 실행에서 오류를 점검하며, 성공에 필요한 실행 길이를 참고해 예산을 조정했습니다〔p.5, §3.2–3.3〕. 2609.31590v1

과제 범주는 전투·제작·채집·거래·탐색·생존·건설·조정의 여덟 가지이며, 기본 과제 중 **45개가 3인 팀 과제**입니다. 따라서 전체 평균을 곧바로 대규모 팀의 성능으로 해석해서는 안 됩니다〔p.6, Figure 4〕. 2609.31590v1

증강 과제는 Claude Opus 4.5로 생성하며, 목표·시작 위치·초기 아이템 등을 변경합니다. 부록에서 상세히 보고한 사람의 검증은 증강 과제의 10% 표본을 대상으로 하며, 이 표본에서는 협업 필요성과 역할 비대칭성 등이 유지되었다고 보고합니다〔p.6 각주 3; pp.16–17, Appendix D〕. 2609.31590v1 2609.31590v1

**[제 해석]** 이 증강은 완전히 새로운 협업 구조를 만드는 실험보다는, **기존 협업 구조에 작업량과 실행 조건의 변화를 주는 스트레스 테스트**에 가깝습니다. 실제로 저자들은 실행 순서는 유지한다고 설명합니다〔p.17, Appendix D〕. 2609.31590v1

> **용어:** 스트레스 테스트는 자원 부족·거리 증가·작업량 증가 등 부담을 높였을 때 시스템이 얼마나 버티는지 확인하는 시험

### 3.4 평가 수식: SR, PSR, CCE, PAC

#### A. 성공률과 부분 성공률

**[저자 보고를 수식으로 재표현]** 원문은 SR과 PSR을 문장으로 정의합니다. 이를 정리하면 다음과 같습니다〔p.7, §3.5〕. 2609.31590v1

```math
\text{SR}
=
100\cdot\frac{1}{K}\sum_{k=1}^{K}z_k
```

```math
\text{PSR}
=
100\cdot\frac{1}{K}\sum_{k=1}^{K}q_k
```

**기호 설명:** $K$는 평가 과제 수, $z_k\in\{0,1\}$는 과제 $k$의 전체 성공 여부, $q_k\in[0,1]$는 검증기가 보고하는 과제별 체크포인트 달성 비율입니다. SR과 PSR의 표시 단위는 %입니다.

> **용어:** 체크포인트는 최종 성공에 앞서 확인하는 중간 조건으로, 필요한 재료 수량 확보나 목표 적 처치 등이 해당

PSR은 부분 진척을 보여주지만, **어떤 체크포인트를 얼마나 세분화하는지**에 따라 값이 달라질 수 있으므로 과제 간 비교에서는 검증기 설계도 함께 살펴봐야 합니다. 이는 원문의 정의에서 도출되는 측정상의 주의점입니다.

#### B. 인과 행동 그래프

**[저자 보고]** 전체 행동을 노드로 하고, 한 행동이 다음 행동을 가능하게 했다고 판단되면 방향 간선을 연결합니다〔p.19, Appendix F.1.2〕. 2609.31590v1

$$
G=(\mathcal{T},E)
$$

**기호 설명:** $G$는 행동 그래프, $\mathcal{T}$는 실제 실행된 모든 에이전트의 행동 집합, $E$는 행동 사이의 선행 기여 관계를 나타내는 방향 간선 집합입니다.

> **용어:** 방향 그래프는 관계의 방향을 표시한 연결 구조, DAG는 방향을 따라 이동해도 원점으로 돌아오는 순환이 없는 그래프

#### C. 기여 행동 집합 — 원문 식 (1)

$$
C=S\cup\text{Ancestors}_{G}(S)
$$

**기호 설명:** $S$는 성공 조건을 직접 달성한 행동 집합, $\text{Ancestors}_{G}(S)$는 그래프에서 $S$의 행동으로 이어지는 경로를 가진 모든 선행 행동, $C$는 이들을 합친 기여 행동 집합입니다〔p.19, Appendix F.1.3〕. 2609.31590v1

> **용어:** 조상 노드는 최종 결과에 직접 연결되지 않더라도 여러 중간 단계를 거쳐 영향을 주는 선행 노드

#### D. CCE — 원문 식 (2)

$$
\text{CCE}=\frac{|C|}{|\mathcal{T}|}
$$

**기호 설명:** $|C|$는 기여 행동 수, $|\mathcal{T}|$는 전체 행동 수이며, $|\cdot|$는 집합의 원소 수를 뜻합니다〔p.19, Appendix F.1.4〕. 2609.31590v1

본문과 Table 2의 집계 규칙에서는 **실패한 과제의 CCE를 0으로 처리**합니다〔pp.7–8〕. 2609.31590v1 2609.31590v1

#### E. 에이전트별 기여 효율 — 원문 식 (3)

```math
\text{PAC}_i
=
\frac{|C\cap\mathcal{T}_i|}{|\mathcal{T}_i|}
```

**기호 설명:** $\mathcal{T}_i$는 에이전트 $i$가 실행한 행동 집합, $C\cap\mathcal{T}_i$는 그중 기여 행동으로 판정된 집합입니다. PAC는 해당 에이전트의 행동 중 유용했다고 판정된 비율을 나타냅니다〔p.19〕. 2609.31590v1

**[제 해석]** PAC는 팀 전체 성과의 몇 %를 누가 만들었는지 나타내는 기여분 배분 지표가 아니라, **각자의 행동 효율**입니다. 행동 한 번이 유용한 에이전트와 열 번 모두 유용한 에이전트가 모두 PAC 1을 받을 수 있다는 점에서 구분이 필요합니다.

### 3.5 CCE 계산 절차와 구현상의 특징

**[저자 보고]** 먼저 성공을 직접 만든 행동을 찾고, 그 행동을 가능하게 한 이전 행동들을 뒤로 추적하면서 $C$를 확장합니다. 기본 판정 모델은 GPT-4.1, 온도는 0이며, 과제와 행동 기록을 보고 기여 여부를 판단합니다〔pp.20–21, Appendix F.2–F.3〕. 2609.31590v1 2609.31590v1

모든 행동 쌍을 확인하면 최악에는 $O(|\mathcal{T}|^2)$개의 쌍을 다루게 되므로, 자원·위치·통신 채널의 관련성을 이용한 후보 제거, 여러 판단의 묶음 처리, 시간창 제한 등을 제안합니다〔p.20〕. 2609.31590v1

> **용어:** $O(n^2)$는 입력 수가 두 배가 되면 처리량이 대략 네 배까지 늘어날 수 있다는 계산량 표기, 시간창은 최근 일정 범위 안의 행동만 비교하도록 제한하는 장치

**[제 해석]** CCE는 “LLM 판정이 없는 객관적 지표”가 아닙니다. **LLM이 그래프의 기여 관계를 판단하고, 이후 그래프 계산은 명시적인 규칙으로 수행하는 지표**입니다. 판단 과정을 더 좁고 확인 가능하게 만들었다는 장점과, 판정 모델의 오류가 남는다는 한계를 동시에 인정해야 합니다.

## 5. 통계적 취약점과 측정·비교상의 한계

### 5.1 가장 중요한 주의점: 평균 CCE의 의미

**[제 해석 — 원문 정의에서 도출한 수학적 관계]**

과제별 CCE를 동일한 가중치로 평균하고 실패 과제는 0점으로 처리하면, 다음 관계가 성립합니다.

```math
\overline{\text{CCE}}
=
s\cdot
\overline{\text{CCE}}_{\text{success}}
```

```math
\overline{\text{CCE}}_{\text{success}}
=
\frac{\overline{\text{CCE}}}{s},
\qquad s>0
```

**기호 설명:** $\overline{\text{CCE}}$는 전체 과제 평균 CCE, $s=\text{SR}/100$은 0–1 범위의 성공 비율, $\overline{\text{CCE}}_{\text{success}}$는 성공한 과제만 대상으로 계산한 평균 CCE입니다. 이 관계는 Table 2의 평균 방식과 실패 시 0점 규칙에 따른 것으로, 새로운 실험 결과가 아닙니다. 2609.31590v1

Table 2의 값으로 재계산하면 성공 과제에서의 평균은 대략 다음과 같습니다.

| 모델 | 전체 평균 CCE | 성공률을 이용한 성공 과제 조건부 평균 — 제 계산 |
|---|---:|---:|
| Gemini | 0.320 | $0.320/0.52 \approx 0.615$ |
| Claude | 0.294 | $0.294/0.45 \approx 0.653$ |
| GPT-5 Mini | 0.206 | $0.206/0.36 \approx 0.572$ |
| DeepSeek | 0.125 | $0.125/0.20 = 0.625$ |

이 계산은 **전체 평균 CCE 순위와 성공했을 때의 행동 효율 순위가 다를 수 있음**을 보여줍니다. 원문도 조건부 분석의 필요성을 인정하며 Claude의 성공 과제 효율을 0.653으로 보고합니다〔p.9〕. 2609.31590v1

여기에 두 가지 주의점이 있습니다.

**첫째, 과제별 비율의 평균은 전체 행동을 합친 비율과 다릅니다.** 행동이 적은 과제와 많은 과제에 같은 가중치를 주기 때문입니다. 따라서 평균 CCE 0.320을 전체 행동을 합친 기여율 32%로 해석할 수 없습니다.

> **용어:** 매크로 평균은 과제마다 같은 비중을 주는 평균, 마이크로 평균은 모든 행동이나 표본을 합쳐 계산하는 평균

**둘째, 실패 과제의 유용한 중간 행동도 CCE에서는 0점으로 사라집니다.** 재료를 정확히 모으고 전달했지만 마지막 제작에 실패한 경우와, 처음부터 아무 진척이 없는 경우가 모두 0점이 될 수 있습니다. 따라서 “실패 과제의 행동이 모두 무용했다”는 결론도 나오지 않습니다〔p.7의 실패 처리 규칙〕. 2609.31590v1

**문서 내부 수치 확인 사항:** 원문은 Gemini의 성공 과제 평균을 **0.609**라고 보고하지만, Table 2의 0.320과 SR 52.0%를 같은 집합·같은 가중치로 사용하면 약 **0.615**입니다. 같은 집계 조건이라면 단순한 세 자리 반올림만으로 설명되기 어려우므로, 원자료 없이 어느 값을 정정값이라고 단정해서는 안 됩니다〔p.8, Table 2; p.9 본문〕. 2609.31590v1 2609.31590v1

### 5.2 CCE의 “인과성”과 “협업성”은 어디까지인가?

**[저자 보고]** 판정은 실제 개입 실험이 아니라 행동 기록을 본 LLM의 판단이며, 조금이라도 도움이 되는 행동을 포함하는 느슨한 정책을 사용합니다〔p.19, Appendix F.1.2〕. 2609.31590v1

**[제 해석]** 따라서 CCE는 다음과 같이 제한해서 읽는 것이 안전합니다.

**인과 효과를 직접 측정한 값은 아닙니다.** 해당 행동을 실제로 제거하거나 대체했을 때 성공 확률이 얼마나 바뀌는지 실험하지 않았기 때문입니다.

> **용어:** 반사실적 검증은 “그 행동을 하지 않았더라면 결과가 달랐을까?”를 실제 재실행이나 모델링으로 확인하는 방법

**협업의 상호 의존 정도를 직접 계산하지도 않습니다.** CCE 수식은 기여 행동 수를 세지만, 그 기여가 반드시 다른 에이전트를 거쳐야 하는지, 서로 독립적인 작업을 단순히 병렬 수행한 것인지는 별도로 점수화하지 않습니다.

**행동의 비용도 동일하게 취급합니다.** 전투 전체를 처리하는 API 한 번과 짧은 채팅 한 번이 모두 한 행동이므로, CCE는 토큰·시간·금전 비용의 효율 지표가 아닙니다〔p.5; p.20〕. 2609.31590v1 2609.31590v1

**관대한 판정 정책이 수학적으로 보장된 상한을 만들지는 않습니다.** 저자는 CCE를 유용한 행동 비율의 상한으로 읽으라고 제안하지만, 누락이나 잘못된 연결이 존재할 가능성까지 사라지는 것은 아닙니다. 또한 그래프를 따라 선행 행동을 포함시키는 구조에서는 한 번의 잘못된 연결이 여러 행동의 기여 판정에 영향을 줄 수 있습니다〔p.9; p.19의 정의에 대한 해석〕. 2609.31590v1 2609.31590v1

### Figure 5에서 특히 중요한 추가 관찰

**[제 해석·산술 예시]** Figure 5는 7라운드에 성공 행동이 발생한 뒤에도 8–9라운드의 행동을 분모에 포함합니다. 그림의 기여 행동 12개가 그대로 유지된다고 놓고 7라운드 종료 직후 실행을 멈추면,

```math
\text{CCE}_{\text{그림}}
=
\frac{12}{27}
\approx 44.4\%
```

```math
\text{CCE}_{\text{성공 직후 종료}}
=
\frac{12}{3\times7}
=
\frac{12}{21}
\approx57.1\%
```

**기호 설명:** 12는 그림의 기여 행동 수, 27은 3명×9라운드의 전체 행동 수, $3\times7$은 성공한 7라운드까지의 행동 수입니다. 이는 **그림에 대한 계산 예시이지 저자가 추가로 수행한 실험이 아닙니다**〔Figure 5〕. 2609.31590v1

### 7.2 일반화 연구에 특히 중요한 수식적 연결

#### A. Other-Play: 특정 동료와만 통하는 관습을 줄이는 목적함수

Other-Play의 원문 식 (2)는 다음과 같습니다〔PDF p.4, §4〕. [Proceedings of Machine Learning Research](https://proceedings.mlr.press/v119/hu20a/hu20a.pdf)

```math
\pi^*
=
\underset{\pi}{\text{arg max}}\;
\mathbb{E}_{\phi\sim\text{Uniform}(\Phi)}
\left[
J\bigl(\pi^1,\phi(\pi^2)\bigr)
\right]
```

**기호 설명:** $\pi=(\pi^1,\pi^2)$는 두 에이전트의 정책, $J$는 함께 실행했을 때의 기대 보상, $\Phi$는 게임의 의미를 보존하는 변환들의 집합, $\phi$는 그중 하나의 변환, $\pi^*$는 이 평균 보상을 최대화하는 정책입니다.

> **용어:** 대칭 변환은 상태나 행동의 이름을 바꾸어도 문제의 본질·보상·진행 규칙이 유지되는 변환

**[제 해석]** AgentWorld에 연결하면, 특정 사용자 이름이나 고정된 역할 배치에만 맞춰진 협업을 피하고 **의미가 같은 여러 표현·배치에서도 작동하는 규칙**을 학습하는 방향이 됩니다. 다만 나무꾼과 마법사의 실제 능력을 아무렇게나 바꾸는 것은 의미 보존 변환이 아니므로, 역할 이름 변형과 과제 자체 변경을 구분해야 합니다.

#### B. Collab-Overcooked: 행동이 추가한 진척을 측정

Collab-Overcooked는 새 행동이 궤적 효율을 얼마나 바꾸는지 다음과 같이 정의합니다〔p.4925, 식 (3)〕. [ACL 앤솔로지](https://aclanthology.org/2025.emnlp-main.249.pdf)

```math
\text{ITES}(\bar a,\bar h_k)
=
\text{TES}(\bar h_k\cup\bar a)
-
\text{TES}(\bar h_k)
```

**기호 설명:** $\bar h_k$는 에이전트 $k$의 기존 행동 기록, $\bar a$는 새로 실행한 협업 요청 또는 응답 행동, TES는 참조 성공 궤적과의 진행·중복 정도를 반영하는 효율 점수, ITES는 새 행동을 추가했을 때의 점수 변화입니다.

**[제 해석]** CCE가 **성공 결과에서 거꾸로 기여 행동을 찾는 방식**이라면, ITES는 **행동이 현재 진척을 얼마나 바꾸었는지 보는 방식**입니다. AgentWorld의 실패 과제에도 유용한 부분 협력이 있을 수 있다는 점에서 후자가 참고가 됩니다. 반면 참조 궤적 기반 평가에는 참조에 없는 유효한 해결 경로를 어떻게 인정할지라는 별도의 문제가 있습니다.

### 7.3 관련 연구 비교에서 도출되는 판단

**[제 해석]** AgentWorld의 향후 영향력은 단순히 “더 긴 게임 벤치마크”라는 데서 결정되기보다, 다음 세 가지를 연결할 수 있는지에 달려 있습니다.

**사회적 일반화:** Other-Play·Melting Pot처럼 새로운 동료와도 협력하는가?

**구조적 일반화:** TeamCraft처럼 학습에서 제외한 목표 조합·장면·팀 규모를 명확하게 시험하는가?

**개선 가능한 협업 방법:** MALT·MASBench처럼 협업을 실제로 학습하거나, 기억·통신·조정 구조의 효과를 분리해 검증하는가?

이 연결은 관련 연구에서 가져온 **후속 연구 방향**이며, AgentWorld가 이미 달성한 결과는 아닙니다.

## 9. 결론과 후속 연구: 일반화 성능 향상을 중심으로

### 9.1 저자들이 제시한 시사점과 후속 계획

**[저자 보고]** 결론에서 저자들은 최고 성공률 52.0%, 기본 네 모델 중 어느 것도 풀지 못한 과제 27%, 부분 성공과 완전 성공의 간극, 통신량과 성공률의 불일치를 근거로, 협업을 기반 모델의 중요한 미해결 역량으로 다루어야 한다고 주장합니다〔p.11〕. 2609.31590v1

환경·과제 정의·검증기·평가 코드·주석 플랫폼을 공개해 후속 평가를 지원한다는 방향도 명시합니다〔p.3〕. 2609.31590v1

다만 **구체적인 협업 학습 알고리즘, 일반화 실험 일정, 새로운 모델 훈련 계획을 후속 연구 계획으로 제시하지는 않습니다.** 아래의 제안은 저자의 계획이 아니라, 이 논문의 결과와 관련 연구를 연결한 추가 방향입니다.

### 9.2 일반화 성능 향상을 기대할 수 있는가?

**[제 해석]** 가능성은 있지만, 무엇이 개선되는지를 구분해야 합니다.

**에이전트 시스템의 일반화 개선**은 기반 모델을 그대로 두고 기억·통신 규칙·도구 사용 구조를 바꾸어 얻을 수 있습니다. 반면 **모델 자체의 일반화 개선**은 학습을 통해 매개변수나 행동 정책이 바뀐 뒤, 새로운 조건에서도 성능이 유지되는지 확인해야 합니다. AgentWorld는 현재 이 둘을 실증적으로 비교하지 않습니다〔§4.1의 평가 설정〕. 2609.31590v1

이 구분을 검증하려면 동일한 총 도구·토큰 예산에서 `기본 모델`, `기본 모델+기억·프로토콜`, `협업 학습 모델`, `협업 학습 모델+동일한 지원 구조`를 비교하는 실험이 유용합니다. 이렇게 해야 지원 프로그램을 잘 만든 효과와 모델이 협업 원리를 학습한 효과를 구분할 수 있습니다.

### 9.3 우선순위가 높은 개선 방향

**[후속 연구 제안 1: 상태를 기억하되, 블랙박스 조건은 유지하기]**

각 에이전트가 마지막으로 확인한 팀원 상태, 자원 수량, 담당 작업, 확인 시점, 완료 여부를 구조적으로 기록하도록 합니다. 다만 상대의 숨겨진 상태를 읽게 해서는 안 되며, **자신이 관찰했거나 명시적으로 전달받은 정보만** 기억하도록 제한해야 합니다. 이는 Table 5의 오래된 정보·역할 오인 문제를 겨냥한 가설입니다〔p.14〕. 2609.31590v1

**[후속 연구 제안 2: 고정 계획보다 수정 가능한 작업 의존 관계 관리]**

공동 목표를 선행 조건이 있는 작업 그래프로 표현하고, 자원 전달에 확인 응답을 붙이며, 실패·지연·수량 변경이 발생하면 담당 배정을 수정하게 합니다. 검증해야 할 것은 계획이 존재하는지가 아니라, **계획의 가정이 깨졌을 때 수정되는가**입니다. 이 방향은 고정 계획·무통신 조건의 결과와 연결되지만, 그 효과는 별도 실험이 필요합니다〔pp.9–10〕. 2609.31590v1

**[후속 연구 제안 3: 통신량이 아니라 필요한 정보의 전달을 학습하기]**

모든 상태를 반복 보고하는 대신, 자원 인계·작업 완료·계획 변경·실패 같은 사건이 발생했을 때 필요한 상대에게 알리도록 합니다. 모델 간 비교에서는 메시지 개수뿐 아니라 **메시지 길이, 전달 대상, 최신성, 실제 행동 변화, 총 비용**을 측정해야 합니다. MASBench의 프로토콜·기억·라우팅 분리 평가가 참고가 됩니다. [arXiv](https://arxiv.org/abs/2610.04672)

**[후속 연구 제안 4: 성공·진척·비용을 함께 고려하는 협업 학습]**

예를 들어 다음 목적함수를 연구 출발점으로 사용할 수 있습니다. 이는 **AgentWorld 원문에 없는 제안식**입니다.

```math
\max_{\theta}
\;
\mathbb{E}_{
\xi\sim\mathcal{D}_{\text{train}},
\;
\tau\sim\pi_{\theta}(\cdot\mid\xi)
}
\left[
z(\tau)
+
\alpha v(\tau)
-
\beta c(\tau)
\right]
```

**기호 설명:** $\theta$는 학습할 정책의 매개변수, $\xi$는 과제·지도·역할·동료 구성을 묶은 조건, $\mathcal{D}\_{\text{train}}$은 훈련 조건의 분포, $\tau$는 실행 기록, $\pi_\theta$는 행동 정책, $z(\tau)$는 최종 성공 여부, $v(\tau)$는 환경 검증기로 확인한 중간 진척, $c(\tau)$는 정규화한 실행 비용, $\alpha,\beta\ge0$는 진척과 비용의 가중치입니다.

**CCE만을 학습 보상으로 최적화하는 것은 신중해야 합니다.** 실패 과제의 진척이 사라지고, 판정 모델의 선호에 맞추는 방향으로 점수가 높아질 수 있기 때문입니다. 우선 실제 환경의 성공·자원 이동·중간 조건을 학습 신호로 사용하고, CCE는 별도의 진단 지표로 남겨 비교하는 설계가 유용합니다.

> **용어:** 보상 편법은 의도한 능력 대신 점수 계산 방식의 빈틈을 이용해 높은 점수를 얻는 현상

### 9.4 일반화를 검증하기 위한 구체적 시험 설계

**[후속 연구 제안]** 증강 성공률 하나보다 다음 축을 분리한 평가가 중요합니다.

| 일반화 축 | 제안하는 시험 | 반드시 통제할 조건 |
|---|---|---|
| **새 목표 조합** | 익숙한 제작·전달 기능을 처음 보는 의존 순서로 조합 | 단순한 작업량 증가와 새로운 구조의 어려움을 분리 |
| **새 지도·자원 배치** | 새로운 지역 배치나 자원 위치에서 평가 | 이동 거리·자원 희소성 차이가 점수를 모두 설명하지 않도록 난도 대응 |
| **새 동료** | 학습 중 보지 않은 모델이나 다른 행동 성향의 팀원과 협업 | 역할별 실제 능력과 정보 접근 권한을 명시 |
| **새 팀 규모** | 작은 팀으로 학습하고 더 큰 팀에서 시험 | 총 작업량, 에이전트당 작업량, 총 도구 예산을 함께 보고 |
| **더 긴 필수 협업 경로** | 반드시 거쳐야 하는 자원 인계·의존 단계 수를 증가 | 최대 허용 라운드가 아니라 **성공에 필요한 최소 연결 깊이**를 측정 |
| **통신 조건 변화** | 지연·누락·순서 변경·일부 팀원의 응답 중단 | 기본 통신 조건에서의 성능과 장애 복구 성능을 분리 |
| **새 영역** | 제작 게임에서 배운 계획·인계 규칙을 업무·코드 작업으로 이전 | 같은 기능 이름이나 고정 문구를 외운 효과와 실제 원리 이전을 구분 |

> **용어:** 분포 밖 평가, 즉 OOD 평가는 훈련에서 보았던 조건의 범위를 의도적으로 벗어난 상황에서 성능을 확인하는 시험

보고 지표는 SR·PSR·전체 평균 CCE뿐 아니라 **성공 과제 조건부 CCE, 에이전트별 PAC, 실패 단계, 메시지 토큰, 총 도구 호출, 실행 시간·비용**을 함께 두는 것이 좋습니다. 원본 과제와 그 변형은 서로 연관되므로 과제 가족 단위로 불확실성을 추정하고, 모델 간 비교는 동일 과제를 대응시켜 수행해야 합니다.

### 최종 판단

**AgentWorld는 협업을 단순한 정답 품질이나 메시지 수가 아니라, 역할 분담·자원 전달·실행 순서·계획 유지의 문제로 평가하려는 의미 있는 벤치마크입니다.** 그러나 평균 CCE를 전체 행동의 낭비율로 해석하거나, 증강 성능 하락을 순수한 일반화 실패로 단정하거나, 유리한 통신 조건의 점수 상승을 모델 학습 성과로 읽어서는 안 됩니다.

**일반화 연구에 대한 가장 중요한 다음 단계는 “같은 게임에서 성공률을 높이는 것”을 넘어, 새로운 동료·새로운 역할 배치·처음 보는 작업 의존 구조에서도 협업 원리가 유지되는지를 검증하는 것입니다.** 이 논문은 그 연구를 수행할 출발점을 제공하지만, 일반화 성능 향상 자체를 입증한 논문은 아닙니다.
