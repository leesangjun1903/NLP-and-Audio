## 2. 연구 목적과 필요성, 핵심 주장과 근거

### 2.1 정확히 어떤 문제를 해결하는가?

**[저자 보고]** 연구 대상은 **사전 제출 외부 루프의 테스트 실패**입니다. 개발자가 IDE에서 가까운 단위 테스트를 실행하는 단계가 아니라, 변경을 준비한 뒤 중앙 시스템이 저장소 전반의 의존 테스트를 실행하면서 발견한 실패를 다룹니다. 컴파일되지 않는 **빌드 실패**, 이미 저장소에서 발생하던 실패, 알려진 비결정적 테스트 등은 핵심 대상에서 제외합니다〔pp.2–3, §§2.1–3.1〕. 2610.07289v1 2610.07289v1

> **용어:**  
> **사전 제출(pre-submit)**은 변경을 공용 저장소에 반영하기 전 단계입니다.  
> **내부 루프(inner-loop)**는 개발자가 편집기에서 코드를 고치고 가까운 테스트를 실행하는 과정이고, **외부 루프(outer-loop)**는 중앙 시스템에서 더 넓은 영향 범위를 검사하는 과정입니다.  
> **비결정적 테스트(flaky test)**는 코드가 같아도 실행할 때마다 성공과 실패가 달라질 수 있는 테스트입니다.

Google에서는 **Cider**가 IDE, **Critique**가 코드 리뷰 도구, **TAP**가 의존 테스트를 찾아 실행하는 지속적 통합 시스템 역할을 합니다. FlowAgent는 TAP의 실패 알림을 받아 자동 실행되고, 결과를 개발자가 이미 사용하는 Critique와 Cider에 표시합니다〔pp.2–4, Fig.3〕. 2610.07289v1 2610.07289v1

> **용어:** **지속적 통합(CI)**은 코드 변경에 대해 빌드·테스트 등을 자동 실행하여 문제를 조기에 발견하는 개발 방식입니다.

**[해석]** 이 설정의 핵심은 “언젠가 정답을 찾는가?”가 아니라 **“개발자가 아직 활용할 수 있는 시점에, 원래 변경 의도를 보존하는 수정안을 전달하는가?”**입니다. 따라서 정답률뿐 아니라 실행 대상의 범위, 처리시간, 수정안의 최신성, 표시 방식, 실제 활용 여부가 함께 중요해집니다.

## 3. 제안 방법과 모델 구조 — 수식 포함

### 3.1 논문에 있는 것과 없는 것

**중요한 구분:** FlowAgent 논문은 새로운 학습 손실함수나 신경망 계층 구조를 제안하지 않습니다. 공개된 핵심은 **내부 Gemini 모델을 이용하는 실행 절차, 도구, 프롬프트, 필터 및 운영 평가**입니다. 따라서 아래의 에이전트 실행 수식과 표시 조건식은 **논문의 절차를 설명하기 위한 재표현**이며, 저자가 제시한 공식이나 실제 학습 목적함수로 해석하면 안 됩니다〔p.3, §3.2; p.5, Listing 4〕. 2610.07289v1 2610.07289v1

> **용어:**  
> **미세조정(fine-tuning)**은 이미 학습된 모델을 특정 데이터로 추가 학습하는 과정입니다.

### 3.3 입력과 실행 전 필터

**[저자 보고]** 초기 입력은 변경 설명, 수정 파일 목록과 차이, 실패 테스트 로그입니다. 실행 전 필터는 빌드 실패, 기존 실패, 알려진 flaky 테스트, 자동화 도구가 작성한 변경, 이미 수정된 오래된 변경, 지원하지 않는 파일 형식, **100개 초과 파일**, **1,000행 초과 변경**을 제외합니다〔p.3, §§3.1–3.2〕. 2610.07289v1

> **용어:** **diff**는 수정 전후 코드의 추가·삭제 부분을 나타내는 형식입니다. **패치(patch)**는 코드에 적용할 수정 내용입니다.

**[해석]** 이 필터는 “어려운 모든 문제를 해결하는 모델”을 만드는 장치가 아니라, **현재 시스템이 유용한 결과를 낼 가능성이 있는 영역으로 운영 범위를 제한하는 장치**입니다. 특히 자동 작성 변경을 제외한 상태에서 얻은 결과를 AI 작성 코드에도 그대로 적용할 수는 없습니다.

### 3.4 수정안 생성–검증 반복

**[저자 보고]** 에이전트는 격리된 실행 환경에서 코드를 조사하고 수정한 뒤 빌드·테스트 결과를 받아 수정안을 보완합니다〔p.3, §3.2〕. 2610.07289v1

> **용어:** **샌드박스**는 작업을 다른 시스템과 분리하여 실행하는 환경입니다. **궤적(trajectory)**은 에이전트가 수행한 일련의 행동과 관찰 기록입니다.

**[설명용 재표현]**

$$
a_t \sim \pi_\theta(\cdot \mid h_t)
$$

$$
(s_{t+1},o_{t+1})=F(s_t,a_t),
\qquad
h_{t+1}=h_t\oplus(a_t,o_{t+1})
$$

$$
N_{\text{tool}}\leq 100,
\qquad
T_{\text{agent}}\leq 30\,\text{min}
$$

**기호 설명:**  
$t$는 반복 단계, $a_t$는 파일 검색·수정·테스트 실행 등의 행동, $\pi_\theta$는 모델 파라미터 $\theta$를 사용하는 행동 생성 과정입니다. $h_t$는 해당 시점까지 이용 가능한 입력과 실행 기록, $s_t$는 작업 환경의 상태, $F$는 도구 실행, $o_{t+1}$은 실행 결과입니다. $\oplus$는 기록에 새 정보를 추가한다는 설명용 표기입니다. $N_{\text{tool}}$은 도구 호출 수, $T_{\text{agent}}$는 에이전트 실행시간입니다.

이 수식은 상호작용을 추상화한 것이며, 실제 문맥 관리나 내부 상태 표현의 구현 세부사항까지 논문이 공개한 것은 아닙니다.

### 3.5 최종 검증, 요약, 실행 후 필터

**[저자 보고]** 수정안이 만들어지면 마지막 검증 단계에서 실제 테스트 실행 여부와 결과를 확인하거나 테스트를 다시 실행합니다. 성공한 경우 전체 실행 기록을 LLM에 전달하는 **한 번의 추가 호출**로 원인과 수정 내용을 요약합니다. 요약 프롬프트는 최대 5문장, 가능하면 1–2문장을 요구합니다〔p.3, §3.2; p.5, Listing 4b〕. 2610.07289v1 2610.07289v1

실행 후 필터는 **개발자가 이미 변경을 수정했는지**, **이미 제출했는지**를 검사합니다. 이 두 조건에 걸리면 수정안을 표시하지 않습니다〔p.3, §3.3〕. 2610.07289v1

**[설명용 재표현]** 수정안을 표시하는 조건은 다음처럼 나타낼 수 있습니다.

```math
G_{\text{show}}
=
F_{\text{pre}}(x)
\cdot
\mathbf{1}\{\Delta\neq\varnothing\}
\cdot
V(P_\Delta,\mathcal{T}_{\text{checked}})
\cdot
S_{\text{fresh}}
\cdot
S_{\text{unsubmitted}}
```

**기호 설명:**  
$x$는 입력 변경과 실패 정보, $F_{\text{pre}}(x)$는 실행 전 필터 통과 여부입니다. $\Delta$는 생성된 패치, $P_\Delta$는 이를 적용한 프로그램, $\mathcal{T}\_{\text{checked}}$는 실제 검증에 사용한 테스트 집합입니다. $V$는 테스트 검증 통과 여부, $S_{\text{fresh}}$는 변경이 여전히 같은 버전인지, $S_{\text{unsubmitted}}$는 아직 제출 전인지 나타냅니다. 모든 항은 0 또는 1이고, $\mathbf{1}\{\cdot\}$는 조건이 참일 때 1인 지시함수입니다.

**핵심 한계:** 이 식의 테스트 검증과 최신성 검사가 개발 의도까지 보장하지는 않습니다.

$$
V(P_\Delta,\mathcal{T}_{\text{checked}})=1
\quad\not\Rightarrow\quad
C_{\text{intent}}(P_\Delta)=1
$$

여기서 $C_{\text{intent}}$는 패치가 개발자의 의도와 필요한 동작을 보존했는지를 뜻합니다. 실제로 논문의 Fig.9에는 이 함의가 성립하지 않는 사례가 제시됩니다. **테스트 삭제·변경 되돌리기를 막는 추가 검증은 완성된 구성요소가 아니라 후속 개선 과제**입니다〔pp.7–8〕. 2610.07289v1 2610.07289v1

### 4.2 67.18%의 통계적 불확실성

**[저자 보고]** 수동 평가는 195건 중 131건을 정확한 수정으로 판정했습니다. 평가자는 각각 5년 이상의 경험을 가진 개발자였고, 불일치는 회의로 조정했습니다〔p.4, Table 1〕. 2610.07289v1

```math
\text{CI}_{95\%}
=
\frac{
\hat p+\frac{z^2}{2n}
\ \pm\
z\sqrt{\frac{\hat p(1-\hat p)}{n}+\frac{z^2}{4n^2}}
}{
1+\frac{z^2}{n}
}
\approx
[0.6031,\ 0.7338]
```

**기호 설명:**

**주의:** 이 구간은 **논문이 보고한 결과가 아니라 제 계산**입니다. 같은 팀·프로젝트의 사례가 서로 유사할 수 있다는 점과 평가자의 판정 오류를 반영하지 않으므로, 실제 불확실성을 모두 포괄하지 않습니다. 저자도 평가자들이 해당 코드를 소유한 개발자가 아니었다는 한계를 인정합니다〔p.8, §5〕. 2610.07289v1

## 5. 가장 중요한 그림의 선정과 해석

### 5.1 Fig.2와 Fig.8 — 연구의 필요성과 성과를 함께 읽어야 하는 그림

**Fig.2〔p.3〕**는 개발자의 다음 편집까지의 시간을 보여주며 세로축이 로그 척도입니다. p10은 2.37분, p25는 6.72분, p50은 27.48분입니다. **Fig.8〔p.6〕**은 FlowAgent 실행시간 분포로, p10 4.78분, p50 9.85분, p90 25.83분을 표시합니다. 2610.07289v1 2610.07289v1

> **용어:** **로그 척도**는 같은 간격이 같은 차이가 아니라 같은 배수 차이를 나타내는 축입니다. 두 그림의 곡선 모양을 눈으로 직접 비교하면 오해할 수 있습니다.

**[해석]** 이 조합은 중앙값 수준에서는 도움을 줄 여지가 있지만, 빠르게 다음 편집을 시작하는 개발자에게는 10분 안팎의 실행도 늦을 수 있음을 보여줍니다. 따라서 “30분 이내 실행”과 “개발자의 흐름을 놓치지 않음”은 같은 목표가 아닙니다.

$$
Q_{0.9}(T_A) < Q_{0.5}(T_H)
\quad\not\Rightarrow\quad
P(T_A < T_H)\geq0.9
$$

**기호 설명:**  
$T_A$는 에이전트 소요시간, $T_H$는 개발자의 다음 편집까지 시간, $Q_q$는 $q$ 분위수입니다.

### 6.2 이 비교에서 중요한 세 가지

**첫째, FlowAgent의 차별점은 “LLM이 테스트를 실행한다” 자체가 아닙니다.** 그런 방식은 이미 선행 연구에 존재합니다. 더 좁고 방어 가능한 차별점은 **사전 제출 외부 루프에서 개발자의 다음 편집 시점을 고려한 자동 개입과 대규모 운영 평가**입니다. 저자의 “최초” 주장도 이 범위와 “우리가 아는 한”이라는 단서 안에서 읽어야 합니다〔pp.1, 10〕. 2610.07289v1 2610.07289v1

**둘째, 검증을 추가하면 단순 해결률이 항상 증가하는 것은 아닙니다.** Meta 연구의 Table III에서는 테스트 피드백만 사용한 설정이 해결률 43.9%, 정적 분석까지 더한 설정이 42.3%였지만, 보고된 오류율은 1.0%에서 0.2%로 낮아졌습니다. 이는 **해결률·오류율·비용·지연의 균형**을 평가해야 한다는 직접적인 사례입니다. [arXiv](https://arxiv.org/html/2507.18755v1)

**셋째, “기계가 보고한 버그”와 “AI가 작성한 코드”는 다릅니다.** Passerine의 기계 보고 버그 성과는 자동 분석 도구가 발견한 문제에 대한 결과이지, AI 작성 변경을 잘 수정한다는 증거가 아닙니다. FlowAgent의 AI 작성 코드 확장은 별도의 일반화 실험이 필요합니다. [arXiv](https://arxiv.org/abs/2501.07531) 2610.07289v1

## 7. 모델의 일반화 성능 향상 가능성 — 핵심 분석

### 7.1 현재 논문으로 입증된 일반화의 범위

**[저자 보고]** 여러 팀과 다수의 변경에 적용되었지만, 저자는 Google 인프라, 내부 Gemini, 프롬프트 변화, 테스트 품질 때문에 결과가 다른 환경으로 일반화되지 않을 수 있다고 인정합니다〔pp.8–9〕. 2610.07289v1

**[해석]** 다음 세 가지를 분리해야 합니다.

| 구분 | FlowAgent에서 확인되는 수준 |
|---|---|
| **운영 규모 확장** | 많은 변경과 작성자를 처리했다는 강한 증거 |
| **Google 내부 다양한 사례에 대한 적용** | 증거는 있으나 언어·팀·오류 유형별 성능은 불명확 |
| **미지의 프로젝트·조직·모델에 대한 일반화** | 별도 분리 평가가 없어 입증되지 않음 |

내부 코드로 미세조정한 모델을 내부 코드에서 평가했다는 사실만으로 데이터 누출이 있었다고 주장할 수는 없습니다. 다만 학습·평가 분리 정보가 없으므로 **암기, 프로젝트 적응, 새로운 문제 해결 능력의 기여를 분리할 수 없습니다**〔p.3, §3.2; p.9, §5〕. 2610.07289v1 2610.07289v1

### 7.2 방향 A: 데이터 양보다 저장소·오류 유형의 다양성을 통제한다

**[관련 연구 보고]** SWE-smith는 학습 궤적 수를 **700개로 고정**한 상태에서 학습에 포함하는 저장소 수를 늘릴수록 성능이 개선되는 결과를 제시합니다. 반면 특정 저장소에 집중해 학습하면 그 저장소 성능은 좋아지지만 다른 저장소 성능은 소폭 낮아졌습니다〔p.8, Figs.5–6〕. [arXiv](https://arxiv.org/html/2504.21798v1)

**[제안]** FlowAgent에서는 같은 학습 예산 아래 저장소, 프로그래밍 언어, 테스트 프레임워크, 오류 유형의 다양성을 늘리는 실험이 우선입니다. 단순히 적용 버튼을 누른 사례를 정답으로 삼기보다, **코드 소유자의 검토와 후속 유지 여부를 확인한 수정**을 학습 자료로 구성하는 것이 바람직합니다.

특히 Fig.9 유형처럼 **테스트는 통과하지만 잘못된 수정**을 음성 예제로 포함하면, 단순 테스트 통과 패턴보다 수정 의도를 학습시키는 데 도움이 될 가능성이 있습니다. 이는 타당한 연구 가설이지 이 논문에서 확인된 효과는 아닙니다.

> **용어:** **음성 예제**는 모델이 정답으로 선택하지 않아야 할 사례입니다. 여기서는 테스트를 없애거나 검증을 약화한 수정안 등이 해당합니다.

### 7.3 방향 B: 재학습과 검색 기반 적응을 분리한다

**[관련 연구 보고]** Chronos는 과거 변경의 설명과 의도를 구조화하여 검색하며, 현재 과제 이후에 생긴 변경이 검색 결과에 들어오지 않도록 시간 제한을 적용합니다〔§2.2.1, Algorithm 1; Tables 4–6〕. [arXiv](https://arxiv.org/html/2610.11578v1)

**[제안]** FlowAgent가 새로운 저장소를 처리할 때마다 모델을 다시 학습하기보다, 해당 저장소의 API 계약, 테스트 관례, 관련 변경 이력, 의존 관계를 검색하도록 할 수 있습니다. 이 방식은 프로젝트 지식을 외부에서 공급하므로 내부 모델을 교체하거나 다른 조직으로 옮길 때 유용할 가능성이 있습니다.

다만 이것은 **모델 가중치 자체의 일반화 향상**과 **검색으로 필요한 정보를 제공받아 성능이 좋아지는 것**을 구별해서 평가해야 합니다. 검색 결과가 오래되었거나 정답 변경을 누출하면 오히려 잘못된 성과를 측정할 수 있습니다.

### 7.4 방향 C: 개발 의도와 독립적인 검증 수단을 강화한다

**[관련 연구 보고]** SpecRover와 Abstain and Validate는 명세 추론과 수정안 평가를 활용하지만, 이들 역시 잘못된 수정안을 완전히 제거하지는 못합니다〔SpecRover p.7; Abstain and Validate Fig.13〕. [abhikrc.com](https://abhikrc.com/pdf/ICSE25.pdf)

**[제안]** FlowAgent에는 다음 검증을 단계적으로 결합하는 것이 유망합니다.

| 검증 대상 | 추가 검증 방안 | 주의할 점 |
|---|---|---|
| 테스트 무력화 | 테스트 제외 표시, 검증문 제거·약화, 예외 무시 패턴 검사 | 모든 테스트 수정이 잘못은 아님 |
| 변경 의도 훼손 | 원래 변경 설명과 수정안의 기능 변화 비교 | 설명 자체가 불완전할 수 있음 |
| 국소 테스트 과적합 | 에이전트가 수정할 수 없는 독립 테스트 및 추가 회귀 검사 | 테스트 비용과 지연 증가 |
| 낯선 API·환경 | 계약·타입·의존 관계에 기반한 분석 | 언어별 도구 지원 필요 |
| LLM 판정 오류 | 실행 검증과 코드 소유자 평가를 병행 | 같은 계열 모델끼리 같은 실수를 공유할 수 있음 |

> **용어:** **회귀 검사**는 변경으로 기존에 정상 동작하던 기능이 깨지지 않았는지 확인하는 검사입니다. **독립 테스트**는 수정 에이전트가 자신에게 유리하도록 바꿀 수 없는 별도의 평가 테스트입니다.

중요한 설계 원칙은 **“테스트 수정 전면 금지”가 아닙니다.** 사전 제출 환경에서는 기능 변경에 맞추어 테스트 기대값을 바꾸는 것이 정답일 수 있기 때문입니다. 필요한 것은 정상적인 기대값 변경과 검증 회피를 구분하는 능력입니다〔p.2, §2.1〕. 2610.07289v1

### 7.5 방향 D: 선택률과 오류율을 함께 평가한다

필터를 강화하면 어려운 문제를 더 많이 제외하여 표시된 수정안의 정확도만 올릴 수 있습니다. 이를 일반화 향상으로 오인하지 않도록 다음을 함께 보고할 것을 제안합니다.

**[제안하는 평가식 — FlowAgent 원문에는 없음]**

```math
\text{Coverage}(\tau)
=
\frac{1}{N}
\sum_{i=1}^{N}g_\tau(x_i)
```

```math
\text{Risk}(\tau)
=
\frac{
\sum_{i=1}^{N}g_\tau(x_i)(1-y_i)
}{
\sum_{i=1}^{N}g_\tau(x_i)
}
```

**기호 설명:**  
$N$은 필터 적용 전 전체 평가 사례 수, $x_i$는 사례, $g_\tau(x_i)$는 기준값 $\tau$에서 수정안을 표시하면 1인 선택 함수, $y_i$는 독립 평가에서 수정이 올바르면 1인 정답 표지입니다. Risk는 표시 사례가 한 건 이상일 때 정의합니다.

> **용어:** 여기서 **coverage**는 시스템이 결과를 제공하는 대상 비율이고, **risk**는 제공한 결과 중 잘못된 비율입니다. 테스트 코드의 실행 범위를 뜻하는 “테스트 커버리지”와는 다른 개념입니다.

**[해석]** 더 나은 일반화의 증거는 단순히 정확도가 올랐다는 것이 아니라, **같은 대상 제공 비율에서 오류율이 낮아지거나, 같은 오류율에서 더 많은 새로운 유형의 문제를 처리하는 것**입니다.

### 7.6 방향 E: 일반화와 저지연을 동시에 검증한다

**[제안하는 평가식]**

```math
Q_d(B)
=
\frac{1}{N_d}
\sum_{i=1}^{N_d}
g_i\,y_i\,\mathbf{1}\{L_i\leq B\}
```

$$
Q_{\min}(B)=\min_d Q_d(B)
$$

**기호 설명:**  
$d$는 평가 영역으로 저장소·언어·오류 유형 등이 될 수 있습니다. $N_d$는 해당 영역의 필터 전 사례 수, $g_i$는 실제 표시 여부, $y_i$는 의미적 정확성, $L_i$는 실패 알림부터 사용자에게 표시되기까지의 시간, $B$는 시간 예산입니다. $Q_d(B)$는 **정해진 시간 안에 올바른 제안을 전달한 전체 사례 비율**, $Q_{\min}(B)$는 가장 취약한 영역의 성능입니다.

이 평가는 선택적 제외, 느린 정답, 빠른 오답을 모두 구별합니다. 영역별 표본 수와 신뢰구간도 함께 보고해야 작은 표본의 최저 성능을 과도하게 해석하지 않을 수 있습니다.

### 7.7 권장 실험 설계

**[제안]** 다음 네 가지 실험이 일반화 주장에 가장 직접적으로 기여합니다.

| 실험 | 구체적 설계 | 확인할 질문 |
|---|---|---|
| 저장소·시간 분리 | 특정 저장소 또는 팀을 학습에서 완전히 제외하고 미래 변경 평가 | 프로젝트 암기가 아닌 새로운 문제 해결인가? |
| 동일 자원 비교 | 같은 모델·도구·하드웨어에서 5·10·30분 예산으로 단순 파이프라인, ReAct, 검증 추가형 비교 | 무엇이 시간 내 정확한 결과를 늘리는가? |
| 작성 주체 분리 | 사람 작성 코드와 여러 생성 모델의 AI 작성 코드를 분리 평가 | 특정 생성기의 오류에만 적응한 것은 아닌가? |
| 실제 작업 효과 실험 | 개발자 또는 팀 단위로 도구 제공 조건을 무작위 배정 | 진단시간·검토시간·최종 제출시간이 실제로 줄어드는가? |

성공 실행만 아니라 **실패·시간 초과·사용자 변경으로 폐기된 실행도 모두 포함**해야 합니다. 또한 평균값뿐 아니라 느린 사례의 지연, 변경 충돌, 잘못된 제안의 검토 부담, 최종 제출 후 회귀까지 측정하는 것이 필요합니다.

## 9. 결론: 저자의 시사점과 추가 후속 연구 방향

### 9.1 연구자가 제시한 시사점과 계획

**[저자 보고]** 연구자는 자동 수정 에이전트를 기존 개발 도구에 통합하는 것이 산업 규모에서 실용적일 수 있으며, 개발자들이 특히 원인 파악과 반복적 테스트 수정에서 도움을 받았다고 결론짓습니다. 후속 계획은 **테스트 삭제·변경 되돌리기 억제**, **더 최신 모델을 이용한 속도와 성공률 개선**, **실행 중임을 알려주는 상태 표시**, **AI 작성 변경으로의 확장**입니다〔p.10, §§7–8〕. 2610.07289v1

그러나 이 중 최신 모델 사용이 실제로 어느 정도 성능을 높이는지, AI 작성 코드로 확장했을 때 일반화가 유지되는지는 **계획 또는 기대이지 완료된 실험 결과가 아닙니다**.

### 9.2 추가 후속 연구의 우선순위

**[제안]** 가장 먼저 할 일은 더 큰 모델로 교체하는 것만이 아니라, **“올바른 수정”의 판정을 강화하고 그 판정으로 일반화를 측정하는 것**입니다. 테스트를 통과시키는 편법이 남아 있으면 모델 규모나 학습 데이터를 늘려도 잘못된 목표에 더 능숙해질 수 있습니다. Fig.9와 최근 평가 신뢰성 연구를 함께 보면, 독립 검증·개발 의도 보존·평가 정보 누출 방지가 우선적인 과제입니다. 2610.07289v1 [arXiv](https://arxiv.org/abs/2609.08149)

그다음에는 **저장소·시간·작성 주체를 분리한 평가**, **동일 시간 예산의 기준선 비교**, **실제 개발시간을 측정하는 무작위 실험**이 필요합니다. 이를 통해 내부 환경 적응, 순수한 모델 개선, 필터에 의한 선택 효과, 사용자 인터페이스 효과를 분리할 수 있습니다.

**[해석]** 앞으로의 연구에 이 논문이 제시하는 가장 중요한 방향은 자동 프로그램 수리의 목표를 다음처럼 넓히는 것입니다.

> **“테스트를 통과하는 패치를 만들었는가?”에서  
> “낯선 코드에서도 개발 의도를 보존한 수정안을, 개발자가 활용할 수 있는 시간 안에 전달했는가?”로 평가 대상을 확장해야 합니다.**

FlowAgent는 이 목표가 실제 서비스 설계에서 중요하다는 강한 증거를 제공합니다. 다만 **그 목표를 전 범위에서 달성했거나 모델의 일반화 성능이 향상되었다는 증거까지 제공하는 논문은 아닙니다.**
