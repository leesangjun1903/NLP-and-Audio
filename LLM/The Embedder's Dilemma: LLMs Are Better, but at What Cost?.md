## 1. Executive Summary (10문장 이내)

1. 본 논문은 LLM이 텍스트 임베딩 파이프라인을 대체할 수 있는지를 **비용 인식(cost-aware) 방식**으로 실증 분석한다.
2. 10개 LLM과 26개 임베딩 모델을 5개 태스크 범주(분류, STS, 클러스터링, 쌍 분류, 검색)에 걸친 **37개 태스크(MTEB(LLM) 벤치마크)**에서 비교하였다.
3. 집계 성능에서는 두 패러다임이 사실상 동점이다: 최고 LLM(Gemini 3.1 Pro, 77.6)과 최고 임베딩 모델(Octen-8B, 77.2)의 차이는 0.4점에 불과하다.
4. 그러나 태스크별 강점은 다르다: **LLM은 추론 집약적 검색에서 우위**, 임베딩 모델은 **분류에서 5.6점 우위**, 클러스터링·STS·쌍 분류는 통계적 동점이다.
5. 비용 격차는 극심하다: Gemini 3.1 Pro는 동급 임베딩 모델보다 **최대 1,431배 비싸다**($154 vs. $0.11/벤치마크 pass).
6. 처리량(throughput)에서도 동일 H100 GPU 기준 임베딩 모델이 LLM보다 **2.5~736배 빠르다**.
7. LLM 추론 비용의 28~81%는 내부 "사고 토큰(thinking token)"이 차지하며, **추론 예산을 줄여도 대부분 모델의 검색 품질은 유지 또는 향상된다**.
8. 파레토 프론티어에는 주요 임베딩 모델들과 단 하나의 LLM(Gemini 3.1 Pro)만이 포함된다.
9. 결론적으로 **하이브리드 전략**이 권장된다: 유사도·분류·클러스터링에는 임베딩, 추론 집약적 검색에는 LLM(또는 재랭킹 단계에서 LLM 활용).
10. 벤치마크 코드·데이터셋·결과는 공개되어 있으며, MTEB 프레임워크와 호환된다.

### 1-1. 연구 목적과 필요성

**목적**: "임베딩 파이프라인을 LLM으로 교체해야 하는가?"라는 실무적 질문에 **통제된 비용-인식 비교**를 통해 답하는 것.

**필요성**:
- LLM 성능이 비약적으로 향상됨에 따라 전용 임베딩 훈련 없이도 최고 임베딩 모델과 동등한 성능이 가능해졌지만, **배포 비용·처리량 비교는 기존 연구에서 누락**되어 있었다.
- 기존 벤치마크(MTEB)는 임베딩 모델 중심으로 설계되어, LLM과의 **공정한 비교 프레임워크**가 부재했다.
- Schwartz et al. (2020)의 "Green AI" 논문이 지적했듯, 정확도만을 기준으로 한 리더보드는 **계산 비용·환경 영향을 은폐**한다.
- 실무자들은 "레이블 데이터가 부족할 때 LLM을 쓸지, 임베딩 파이프라인을 구축할지" 판단이 필요한데, 이를 위한 **정량적 근거**가 필요하다.

## 2-1. 상세 설명: 문제, 방법, 모델 구조, 성능, 한계

### 해결하고자 하는 문제

> LLM의 성능이 전용 임베딩 모델과 동등해진 시점에서, **실제 배포 비용과 처리량을 함께 고려할 때 어떤 패러다임을 선택해야 하는가?**

구체적으로:
1. LLM과 임베딩 모델의 **태스크별 성능 차이 정량화**
2. **비용(API/GPU)**의 정확한 측정 및 파레토 프론티어 도출
3. LLM의 추론 토큰이 **비용 대비 성능 향상에 실제로 기여하는지** 검증

> 💡 **임베딩 모델(Embedding Model)**: 텍스트를 고정 길이 실수 벡터로 변환하는 모델. 코사인 유사도 등으로 의미적 유사성을 측정. BERT 계열의 인코더 구조 사용.

> 💡 **LLM (Large Language Model)**: 텍스트를 자동회귀 방식으로 생성하는 대규모 언어 모델. GPT, Gemini 등이 해당. 이 논문에서는 임베딩 벡터가 아닌 텍스트 출력을 생성하는 방식으로 활용.

---

### 제안하는 방법 (수식 포함)

#### (1) LLM 비용 계산 수식 (Eq. 1, §3.3)

$$\text{Cost} = (\text{input} - \text{cached}) \cdot r_{\text{in}} + \text{cached} \cdot r_{\text{cache}} + (\text{total} - \text{input}) \cdot r_{\text{out}}$$

**기호 설명:**
| 기호 | 의미 |
|------|------|
| $\text{input}$ | 총 입력 토큰 수 (캐시된 것 포함) |
| $\text{cached}$ | 프롬프트 캐시로 처리된 입력 토큰 수 |
| $\text{total}$ | 입력 + 생성된 전체 토큰 수 |
| $r_{\text{in}}$ | 비캐시 입력 토큰당 요금 (단위: $/token) |
| $r_{\text{cache}}$ | 캐시 입력 토큰당 요금 $= r_{\text{in}}/10$ |
| $r_{\text{out}}$ | 출력 토큰당 요금 (추론/사고 토큰 포함, 단위: $/token) |
| $\text{total} - \text{input}$ | 생성된 토큰 수 (표준 출력 + 사고 토큰) |

> 💡 **프롬프트 캐싱(Prompt Caching)**: 동일한 프롬프트 접두사(예: 코퍼스 전체)를 여러 쿼리에 걸쳐 재사용하는 기법. 반복 처리 비용을 절감함. Gim et al. (2024) 참조.

> 💡 **사고 토큰(Thinking Token / Reasoning Token)**: LLM이 답변 전 내부적으로 수행하는 체인-오브-소트(Chain-of-Thought) 추론 과정에서 생성되는 토큰. 출력 요금으로 청구됨.

#### (2) 임베딩 모델 비용 계산

$$\text{Cost}_{\text{emb}} = \frac{r_{\text{GPU}}}{T}$$

**기호 설명:**
| 기호 | 의미 |
|------|------|
| $r_{\text{GPU}}$ | GPU 시간당 비용 (Lambda Labs H100 spot: \$2.49/hr) |
| $T$ | 시간당 처리 토큰 수 (tokens/hour), 시퀀스 길이 512에서의 최대 처리량으로 측정 |

#### (3) 통계적 유의성 검정

**쌍별 부트스트랩 검정** (Efron, 1979; Appendix A):
- 10,000회 리샘플링
- 리샘플링 단위: 태스크 레벨
- 점수 차이: $\Delta = \bar{s}\_{\text{Pro}} - \bar{s}_{\text{best emb}}$ (평균의 평균 차이)
- 유의수준: $\alpha = 0.05$ (Bonferroni 보정: $\alpha = 0.01$)

> 💡 **쌍별 부트스트랩 검정(Paired Bootstrap Test)**: 통계적 유의성 검증 방법. 데이터에서 반복 샘플링하여 검정 통계량의 분포를 추정. 정규분포 가정이 불필요.

### 모델 구조

#### 임베딩 파이프라인 구조

```
[텍스트 입력]
    ↓
[인코더 모델 (단일 순방향 패스)]
    ↓
[고정 길이 벡터 (e.g., 768~4096차원)]
    ↓
[코사인 유사도 / kNN / k-means]
    ↓
[태스크 출력]
```

#### LLM 파이프라인 구조

```
[텍스트 입력 + 제로샷 프롬프트]
    ↓
[자동회귀 디코딩 (토큰 단위 순차 생성)]
    ↓ (선택적)
[사고 토큰 생성 (CoT 추론)]
    ↓
[구조화된 텍스트 출력 (JSON)]
    ↓
[태스크 출력]
```

#### 검색 아키텍처 비교 (Figure 5, §5)

| 아키텍처 | 쿼리-문서 처리 방식 | 쿼리당 비용 | 품질 |
|----------|-------------------|------------|------|
| **Bi-encoder** (임베딩) | 독립적 처리 (교차 어텐션 없음) | $N$회 벡터 비교 | 낮음 |
| **Cross-encoder** | 쿼리+문서 1개씩 동시 처리 | $k$회 쌍별 패스 | 중간 |
| **LLM Listwise 재랭커** | 쿼리+상위 $k$개 문서 동시 처리 | $k$개 문서 1회 패스 | 높음 |
| **LLM Corpus-in-context** | 쿼리+전체 $N$개 문서 동시 처리 | $N$개 문서 1회 패스 | 최고 |

> 💡 **Bi-encoder**: 쿼리와 문서를 별도 인코더로 독립 처리 후 벡터 유사도 비교. 문서 임베딩을 사전 계산 가능하여 고속 검색 가능.

> 💡 **Cross-encoder**: 쿼리와 문서를 함께 입력하여 관련도 점수를 직접 출력. 더 정확하지만 느림.

> 💡 **Corpus-in-context**: 전체 코퍼스를 LLM 프롬프트에 삽입하여 전역적 추론 가능. 소규모 코퍼스에만 현실적으로 적용 가능.

### 필자의 해석 (저자 주장과 분리)

> ⚠️ 이하는 **필자의 해석**으로, 논문 원문의 직접 인용이 아님.

1. **1,431배 비용 격차의 실용적 의미**: 이 수치는 H100 spot 가격 기준이며, 클라우드 API 환경($0.10/MTok)에서도 338배로 유지된다(Table 19). 즉 하드웨어 환경과 무관하게 **수십~수천 배의 격차는 구조적**으로 발생한다.

2. **추론 토큰 "과잉사용" 패턴**: 분류 태스크에서 추론 토큰 수를 줄여도 점수 변화가 $|\Delta| < 1.0$이라는 것은, LLM이 간단한 태스크에서도 불필요하게 많은 사고 과정을 거친다는 "overthinking" 현상(Sui et al., 2025)과 일치한다.

3. **하이브리드 전략의 실용성 한계**: 논문이 권장하는 "임베딩 1차 검색 + LLM 재랭킹" 파이프라인은 BRIGHT에서 효과적이지만, 재랭킹 비용($10~30/벤치마크)도 소규모 애플리케이션에서는 상당한 부담일 수 있다.

4. **임베딩 모델의 잠재적 과소평가**: 임베딩 훈련 비용이 벤치마크 비용에 포함되지 않아, 임베딩의 "실제 총비용"은 논문이 제시한 것보다 높을 수 있다. 단, 저자도 이를 인식하고 §H.4에서 "training is a one-time cost"라고 언급한다.

5. **AILAStatutes에서 LLM 열위의 함의**: LLM이 법령 검색에서 더 나쁜 성능을 보이는 것은, **추론이 항상 정밀도를 향상시키지 않는다**는 중요한 반증 사례다. 연관성 있지만 관련 없는 법령까지 폭넓게 검색하는 LLM의 특성이 오히려 노이즈를 만든다.

## 6. 논문이 답하지 않는 질문

1. **GPT-5, Claude Opus 4.6의 성능·비용은?** → 저자도 미평가 인정 (Appendix G(i))

2. **대규모 코퍼스(수십만 문서) 환경에서의 LLM 성능은?** → 현재 실험은 82~415개 문서; 실제 scale에서의 검색 품질 변화 불명

3. **분류에서 LLM이 더 많은 few-shot 예시를 받는다면?** → 5-shot 실험만 수행; Banking77에서 5→더 많은 예시를 줄 경우의 성능 변화 미탐구

4. **훈련 비용을 포함한 총소유비용(TCO)은?** → 벤치마크 통과 비용만 측정; 임베딩 모델의 사전 훈련·파인튜닝 비용 제외

5. **분류 특화 훈련을 받은 LLM은?** → "classification-post-trained LLM would likely narrow the gap"이라 언급하지만 미평가 (§5)

6. **시간에 따른 API 가격 하락 시 파레토 프론티어 변화는?** → 현재 가격 기준 스냅샷만 제공

7. **코퍼스 크기 변화에 따른 LLM 검색 성능 변화는?** → corpus size를 변수로 다루지 않음 (Appendix G(iii))

8. **환경적 영향(탄소 발자국)은?** → 윤리 선언에서 언급하나 정량화 없음

9. **다중 언어 환경에서 패러다임 차이는?** → 일부 다국어 태스크 포함이나 체계적 분석 부재

10. **프롬프트 디자인 변화에 따른 성능 민감도는?** → 단일 프롬프트 템플릿만 사용; ablation 없음

### Figure 5: 아키텍처별 어텐션 마스크 비교
> (p.10, §5)

**내용**: Bi-encoder, Cross-encoder, LLM Listwise 재랭커, LLM Corpus-in-context의 파이프라인과 어텐션 마스크를 동일 스케일로 시각화.

**해석**:
- 빨간 영역 = 쿼리와 함께 단일 순방향 패스에서 읽는 문서 범위 = 쿼리 도착 전 사전 계산 불가 = **비용의 직접 동인**.
- **Bi-encoder**: 빨간 영역 없음 (쿼리와 문서 독립 처리) → 최저 비용.
- **Cross-encoder**: 쿼리 + 문서 1개씩 → 중간 비용.
- **LLM Listwise**: 쿼리 + 상위 k개 → 높은 비용.
- **LLM Corpus-in-context**: 쿼리 + 전체 N개 → 최고 비용.
- 품질과 비용이 동일한 순서로 증가함을 보여주는 **구조적 근거 그림**.

> 💡 **어텐션 마스크(Attention Mask)**: 트랜스포머 모델에서 어떤 토큰이 다른 어떤 토큰을 "볼 수 있는지"를 결정하는 이진 행렬. 1이면 참조 가능, 0이면 불가.

## 8. 결론: 시사점, 후속 연구, 추가 방향

### 저자가 제시한 시사점 (§5, §6)

1. **실무 권고**: 분류·유사도·클러스터링 → 임베딩 (기본값); 추론 집약적 검색 → LLM 또는 하이브리드.
2. **하이브리드 아키텍처**: 임베딩 1차 검색 → LLM 리스트 재랭킹이 비용·품질 균형 최적.
3. **추론 예산 축소**: 대부분 모델에서 추론 비활성화·축소로 검색 품질 유지 가능.
4. **파레토 프론티어 보고 권장**: 정확도 단독 리더보드는 비용 차이를 은폐 → 배포 비용·처리량 함께 보고해야.
5. **MTEB(LLM) 공개**: MTEB 프레임워크 호환 벤치마크로 신규 모델 지속 평가 가능.

### 저자가 제시한 후속 연구

- GPT-5, Claude Opus 4.6 등 미평가 모델 포함 (Appendix G(i))
- 더 큰 코퍼스에서의 검색 실험
- 분류 특화 훈련 LLM 평가

### 8-1. 모델 일반화 성능 향상 가능성

**현재 한계**:
- 검색 태스크의 코퍼스가 82~415개 문서로 제한 → **소규모 환경에 특화된 결론**
- 임베딩 모델은 분류에서 전체 훈련 레이블 사용 / LLM은 제로샷 → **일반화 비교의 불공정성**
- 37개 태스크의 균등 가중 → 특정 도메인·언어에서의 일반화 불명

**일반화 향상을 위한 연구 방향**:

1. **도메인 특화 평가**: 의료·법률·금융 등 전문 도메인에서 두 패러다임의 일반화 격차 측정. 현재 일부(BIOSSES, LegalBench) 포함이나 체계적 분석 부재.

2. **다국어 일반화**: STS17, STS22v2 등 일부 다국어 태스크가 포함되지만, 저자원(low-resource) 언어에서의 성능 비교는 미탐구. 임베딩 모델의 언어 일반화 vs. LLM의 다국어 능력 비교가 필요.

3. **분포 이동(Distribution Shift) 실험**: 훈련 도메인과 다른 테스트 도메인에서의 성능 유지 여부. 임베딩 모델은 특정 도메인 데이터로 대조적 훈련을 받아 분포 이동에 취약할 수 있음.

4. **코퍼스 크기 스케일링**: 논문이 명시적으로 미탐구한 영역 — 코퍼스 크기를 10², 10³, 10⁴, 10⁵로 증가시킬 때 LLM 검색 품질과 임베딩의 품질 격차 변화 측정.

5. **제로샷 일반화 vs. 파인튜닝 갭**: LLM의 제로샷 분류와 파인튜닝된 임베딩의 격차(-5.6점)가 **새로운 레이블 공간**에서는 어떻게 변하는지 — 즉, 임베딩이 훈련에서 보지 못한 레이블 클래스에 대한 일반화 능력 비교.

6. **하이브리드 파이프라인의 일반화**: "임베딩 1차 검색 + LLM 재랭킹"의 조합이 BEIR/BRIGHT 외 다른 도메인에서도 동일한 패턴을 보이는지 검증 필요.

| Lee et al. (LOFT) | 2024 | 코퍼스-인-컨텍스트 프로토콜 | 본 논문 검색 방법론 기반 |
| Bucher & Martini | 2024 | 파인튜닝 인코더 > 제로샷 LLM (분류) | 본 논문 분류 결과와 일치 |
| Lu et al. | 2025 | CoT 재랭킹 < 직접 출력 재랭킹 | 본 논문 추론 축소 결과와 일치 |
| Gonzalez | 2026 | BERT 인코더 vs. GPT-4o 비용 파레토 | 본 논문과 동일 방향성 |
| Sui et al. (Overthinking) | 2025 | LLM 과도 추론의 비효율성 | 본 논문 사고 토큰 세금 근거 |
| BehnamGhader et al. (LLM2Vec) | 2024 | LLM을 인코더로 변환 | 두 패러다임 경계 모호화 |
| Muennighoff et al. (GritLM) | 2024 | 생성+표현 통합 모델 | 하이브리드 아키텍처 예시 |

#### 본 논문이 앞으로의 연구에 미치는 영향

1. **MTEB(LLM) 벤치마크의 영향**: MTEB 프레임워크와 호환되는 공개 벤치마크로, 신규 모델 평가의 표준화에 기여할 것. 특히 LLM-임베딩 크로스 패러다임 비교를 가능하게 하는 **최초의 비용 인식 벤치마크**.

2. **파레토 프론티어 패러다임 전환**: 정확도 단독 리더보드에서 **비용-품질 파레토 프론티어** 중심 평가로의 방향 전환을 촉진. 특히 산업계 배포 의사결정에서 활용도 높음.

3. **사고 토큰 최적화 연구 자극**: "추론을 줄여도 성능이 유지·향상된다"는 발견은 **적응적 추론 예산 할당(Adaptive Test-Time Compute)** 연구(Snell et al., 2024)와 맞물려, 태스크별 최적 추론 깊이를 학습하는 연구를 촉진할 것.

4. **하이브리드 아키텍처 설계 기준 제공**: BRIGHT에서의 재랭킹 효과(+12.8 nDCG@10)는 임베딩+LLM 하이브리드 시스템 설계의 실증적 기준을 제공.

5. **LLM 기반 임베딩 모델 연구**: GritLM, LLM2Vec 등 LLM을 임베딩 모델로 활용하는 연구에 **벤치마크 기준점** 제공.

#### 앞으로 연구 시 고려할 점

1. **비용 동태성**: LLM API 가격은 매우 빠르게 변동 — 연구 결과의 **시간적 유효성** 명시 필요.

2. **공정한 감독 조건**: 두 패러다임에 동등한 레이블 정보를 제공하는 실험 설계 필요 (현재: kNN은 전체 훈련 세트, LLM은 5-shot).

3. **환경 영향 정량화**: 탄소 발자국, 에너지 소비를 성능과 함께 보고하는 **Green AI** 지표 통합.

4. **태스크 가중치 다양화**: 단순 균등 가중 외 도메인 중요도·데이터셋 크기·실무 빈도를 반영한 가중 방법 탐구.

5. **온디바이스 배포 고려**: 클라우드 API가 아닌 엣지 디바이스·온프레미스 환경에서의 비용-성능 비교.

6. **멀티모달 확장**: MIEB(이미지), MAEB(오디오), MVEB(비디오) 등 저자들이 언급한 생태계와 연계한 멀티모달 임베딩 vs. LLM 비교.

7. **지속적 학습(Continual Learning) 고려**: 새로운 도메인이나 레이블이 추가될 때 각 패러다임의 적응 비용 비교.
