# An Empirical Study of Harness Design for Coding Agents

**분석 대상:** Run-Ze Fan 외, *An Empirical Study of Harness Design for Coding Agents*, arXiv:2609.20804v1, 2026년 9월 17일 공개본입니다. 아래 페이지 번호는 첨부된 43쪽 PDF를 기준으로 하며, 외부 연구는 2026년 10월 6일 확인한 원문을 사용했습니다. [arXiv](https://arxiv.org/abs/2609.20804)

## 1. Executive summary

이 논문은 코딩 에이전트의 성능을 좌우하는 **하네스의 개별 구성요소가 언제 도움이 되고, 언제 불필요한 비용이나 실패를 유발하는지** 밝히는 것을 목적으로 합니다.  
기존 연구가 완성된 에이전트 시스템들을 비교하면서 여러 설계 차이를 한꺼번에 섞어 평가했다면, 이 연구는 실행 루프를 고정하고 계획 수립, 행동 인터페이스, 컨텍스트 관리만 변화시켰습니다.  
저자들은 네 모델과 두 벤치마크에서 총 176개 설정을 평가했지만, 모든 구성요소의 조합을 교차한 실험은 아닙니다. **[p.2, §1; p.6, §3.1]** 2609.20804v1 2609.20804v1

컨텍스트 관리는 특히 작은 입력 창에서 효과적이었으며, 주요 이득은 새로운 문제 해결 전략을 만들어서라기보다 입력 한도 초과로 실행이 조기에 종료되는 것을 막는 데서 나타났습니다.  
오래된 도구 출력을 먼저 생략하고 필요할 때만 언어모델 요약을 수행하는 T4는 관리 전략 중 전반적으로 가장 유리한 비용 특성을 보였지만, 모든 개별 조건에서 최선은 아니었습니다.  
생략한 내용을 외부에 저장하고 다시 불러오는 기능은 거의 사용되지 않았으며, 생략만 사용하는 방식보다 일관된 성공률 향상을 보이지 않았습니다. **[pp.7–9, §3.2; Figures 3–5]** 2609.20804v1 2609.20804v1

명시적 계획은 가장 약한 모델에서는 조기 포기를 줄여 성공률을 높였지만, 강한 모델에서는 성공률을 조금 낮추면서 반복 검증을 줄여 비용을 절약하는 방향으로 작용했습니다.  
사전 정의된 도구와 셸 중심 인터페이스의 우열은 모델의 셸 활용 능력뿐 아니라 과제 유형에 따라서도 뒤집혔습니다.  
따라서 제 평가는 이 논문이 **기반 모델 자체의 일반화 능력 향상을 입증한 연구라기보다, 동일한 모델의 능력이 여러 실행 조건에서 얼마나 안정적으로 발휘되는지를 분석한 시스템 연구**이며, 단일 실행과 제한된 모델·과제 범위 때문에 보편적인 설계 법칙으로 확대해서는 안 된다는 것입니다. **[pp.9–14; p.16, Limitations]** 2609.20804v1 2609.20804v1 2609.20804v1

> **용어 풀이**  
> **하네스(harness):** 모델 주위에서 도구 실행, 입력 구성, 기억 관리, 종료 판단 등을 담당하는 소프트웨어 계층.  
> **컨텍스트(context):** 모델이 현재 응답을 생성할 때 입력으로 볼 수 있는 작업 설명과 이전 상호작용.  
> **셸(shell):** 명령어로 파일 조회·편집·프로그램 실행 등을 수행하는 인터페이스.  
> **일반화:** 설계하거나 평가할 때 직접 맞춰 보지 않은 새로운 과제·환경에서도 성능이 유지되는 성질.

### 1.1. 연구의 목적과 필요성

**[저자 보고]** 기존 하네스 간 비교에서는 프롬프트, 도구, 계획, 메모리, 오류 처리 등이 동시에 달라지므로, 성능 차이가 무엇 때문에 생겼는지 분리하기 어렵습니다. 저자들의 질문은 “하네스 구성요소는 일반적으로 유용한가, 아니면 모델 능력·과제 종류·자원 예산에 따라 효과가 달라지는가?”입니다. **[p.2, §1]** 2609.20804v1

**[해석]** 이 질문은 모델을 교체하거나 서비스의 입력 한도를 변경할 때 특히 중요합니다. 한 모델에 도움이 된 계획 도구가 다른 모델에서는 불필요한 입력과 호출을 늘릴 수 있고, 복잡한 파일 편집 인터페이스가 셸 사용에 능숙한 모델의 작업을 잘게 분절할 수도 있기 때문입니다. 이 논문의 핵심 기여는 새로운 최고 성능 시스템 하나를 제시하는 데 있기보다, **“어떤 지원이 어떤 실패를 보완하는가”를 비교 가능한 실험 대상으로 만든 것**에 있습니다. 이러한 해석의 근거는 모델·과제에 따라 방향이 달라지는 계획 및 행동 인터페이스 결과입니다. **[pp.9–14, Figures 6–9]** 2609.20804v1 2609.20804v1

## 2. 해결하려는 문제, 제안 방법, 모델·시스템 구조

### 2.1. 무엇을 바꾸고 무엇을 고정했는가?

이 연구는 새로운 신경망 구조나 학습 손실을 제안하지 않습니다. **기존 언어모델을 둘러싼 실행 구조를 바꾸는 실험**이며, 기본 구조는 추론–행동–관찰을 반복하는 ReAct 루프입니다. **[p.3, §2; p.4, Figure 2]** 2609.20804v1 2609.20804v1

> **용어 풀이 — ReAct:** 다음 행동을 생각하고, 실제 도구를 실행한 뒤, 결과를 읽고 다시 행동하는 반복 방식입니다. 계획을 처음에 한 번 작성하고 그대로 따르는 방식과는 다릅니다.

실험에서 변화시키는 요소는 다음과 같습니다.

| 구성요소 | 실험한 대안 | 실제로 측정하는 효과 |
|---|---|---|
| 계획 수립 | 지속적으로 유지·갱신되는 계획 사용 / 제거 | 특정 계획 프롬프트, 알림, 계획 상태 주입, `update_plan` 도구를 합친 지원 장치의 효과 |
| 행동 인터페이스 | 사전 정의 도구 집합 / bash-only | 도구 종류뿐 아니라 인터페이스 지침, 파일 상태 추적, 자동 진단 지원을 포함한 묶음의 효과 |
| 컨텍스트 관리 | T0–T4 | 오래된 이력을 보존·생략·회수·요약하는 정책의 효과 |

계획을 끈 조건에서도 모델이 내부적으로 계획하거나 추론하는 것까지 금지한 것은 아닙니다. 또한 **bash-only에서도 계획 및 기억 관리에 필요한 보조 도구는 남아 있으므로, 문자 그대로 도구가 하나뿐인 조건은 아닙니다.** **[p.3, §§2.1–2.2; p.4, Table 1]** 2609.20804v1 2609.20804v1

### 2.2. 모델·시스템 구조

**[저자 보고]** 문제 해결용 모델은 Nemotron-3 30B·120B·550B와 Mistral-Medium-3.5-128B입니다. 동일 계열의 세 크기를 능력 변화의 축으로 사용하고, 다른 계열의 Mistral을 추가해 결과가 한 계열에만 국한되는지 살폈습니다. 다만 저자들도 모델 크기가 능력의 불완전한 대리변수라고 인정합니다. **[p.2; p.6; p.16]** 2609.20804v1 2609.20804v1 2609.20804v1

시스템은 매 단계에서 관리된 대화 이력, 현재 계획, 도구 명세를 조합해 모델에 제공하고, 모델이 생성한 도구 호출을 과제 컨테이너에서 실행합니다. 결과는 다시 이력에 추가됩니다. 계획은 대화 이력과 별도로 저장하고 매 호출 때 새로 넣으며, 요약은 **평가 중인 동일 모델을 별도로 호출하되 도구 사용 없이** 생성합니다. **[pp.3–5, Figure 2, Algorithm 1]** 2609.20804v1 2609.20804v1 2609.20804v1

**[해석]** 따라서 여기서 중요한 “모델 구조”는 Transformer의 층 수나 주의집중 구조가 아니라 **모델과 외부 상태·도구·실행 루프의 결합 구조**입니다. 논문에 없는 기반 모델의 내부 구조나 학습 과정을 하네스의 기여로 해석해서는 안 됩니다.

#### 실행 루프의 수식화

아래 식은 원문에 번호가 붙은 제안 수식이 아니라, **Figure 2와 Algorithm 1을 설명하기 위해 제가 재표기한 식**입니다.

$$
\begin{aligned}
I_t &= \text{Assemble}(H_t,P_t,\mathcal A),\\
(r_t,a_t) &= f_\theta(I_t),\\
o_t &= \text{Execute}(a_t,E_t),\\
H_{t+1} &= \mathcal C\!\left(H_t\oplus(r_t,a_t,o_t)\right).
\end{aligned}
$$

**기호 설명:** $t$는 실행 단계, $I_t$는 모델 입력, $H_t$는 현재까지 관리된 이력, $P_t$는 별도로 유지하는 계획, $\mathcal A$는 사용 가능한 도구 명세입니다. $f_\theta$는 가중치 $\theta$를 가진 기존 모델, $r_t$는 추론 텍스트, $a_t$는 행동 또는 도구 호출 집합, $E_t$는 실행 환경, $o_t$는 도구 결과입니다. $\mathcal C$는 컨텍스트 관리 정책이며, $\oplus$는 이력에 새 내용을 이어 붙이는 연산입니다. **[재표기 근거: p.4, Figure 2; p.5, Algorithm 1]** 2609.20804v1 2609.20804v1

### 2.3. 계획 수립: 추론 알고리즘보다 지속적인 작업 상태 관리

**[저자 보고]** 계획 기능은 모델에게 처음에 작업을 분해하도록 요구하고, `update_plan`으로 전체 목록을 갱신하게 합니다. 정확히 하나의 작업을 진행 중으로 유지하도록 지시하며, 최신 계획을 이후 호출마다 다시 제공합니다. 계획 제거 실험에서는 이 지침·초기 알림·반복 주입·도구를 함께 제거합니다. **[pp.19–22, Figures 15–17]** 2609.20804v1 2609.20804v1 2609.20804v1

**[해석]** 이 실험이 답하는 것은 “계획을 생각하면 좋은가?”가 아니라, **“외부에 저장한 작업 목록을 계속 보여주는 특정 구현이 도움이 되는가?”**입니다. 계획의 내용이 정확한지, 계획 분해 자체가 더 우수해졌는지는 별도로 측정하지 않았습니다.

### 2.4. 행동 인터페이스: 도구 개수만의 비교가 아니다

사전 정의 도구에는 파일 읽기·쓰기·편집, 파일 및 내용 검색, 웹 페이지 읽기, 셸 실행 등이 포함됩니다. 반면 bash-only는 일반 작업을 셸 명령으로 표현하게 합니다. 사전 정의된 파일 도구는 사전 읽기 검사와 파일 상태 추적을 수행하며 지원되는 편집 뒤에 자동 진단을 실행하지만, 셸로 수행한 동등한 수정은 같은 상태 추적·진단 경로를 거치지 않습니다. **[p.3, §2.2; p.23, Appendix B.1]** 2609.20804v1 2609.20804v1

**[해석]** 그러므로 성능 차이를 “도구가 많아서”, “도구가 적어서”, 또는 “한 번에 더 많은 코드를 써서” 생긴 효과로 단독 귀속할 수 없습니다. 이 부분은 저자들도 명시한 중요한 식별 한계입니다. **[p.16, Limitations]** 2609.20804v1

> **용어 풀이 — 식별 한계:** 관측된 효과가 어떤 원인에서 비롯되었는지, 실험 설계만으로 분리해 알아내기 어려운 상황입니다.

### 2.5. 컨텍스트 관리: T0–T4

| 정책 | 생략 M1 | 외부 저장·회수 M2 | 요약 M3 | 작동 방식 |
|---|---:|---:|---:|---|
| T0 | 없음 | 없음 | 없음 | 추가적인 턴 간 압축 없이 유지하다 입력 창을 초과하면 종료 |
| T1 | 사용 | 없음 | 없음 | 오래된 도구 출력 본문을 짧은 표시문으로 교체 |
| T2 | 사용 | 사용 | 없음 | T1에 원문 저장과 `recall_event`를 추가 |
| T3 | 없음 | 없음 | 사용 | 오래된 이력을 언어모델의 누적 요약으로 대체 |
| T4 | 사용 | 사용 | 사용 | 먼저 생략·저장하고, 그래도 길면 요약 |

**[저자 보고: p.5, Table 2 및 Algorithm 1]** T1–T3는 상위 임계값에서 작동하고, T4만 더 이른 임계값에서 생략을 시작합니다. 2609.20804v1

> **용어 풀이**  
> **생략(elision):** 오래된 출력의 상세 내용을 지우고 “이 출력이 생략되었다”는 짧은 흔적만 남기는 처리입니다.  
> **회수(recall):** 밖에 저장한 과거 내용을 필요할 때 다시 입력에 가져오는 기능입니다.  
> **누적 요약(running summary):** 기존 요약과 새로 오래된 이력을 함께 정리해 계속 갱신하는 요약입니다.  
> T2의 “복구 가능성”은 저장한 출력에 대한 것이며, 에이전트 전체가 정보를 완벽히 활용한다는 뜻은 아닙니다.

#### 임계값과 보존 영역

다음 역시 원문의 설정을 재표기한 식입니다.

$$
H=H_{\mathrm{pre}}\oplus M\oplus H_{\mathrm{recent}},
\qquad
B_1=0.60U,\quad B_2=0.85U,\quad R=0.30U.
$$

**기호 설명:** $H_{\mathrm{pre}}$는 시스템 지침과 초기 과제 설명, $M$은 압축 대상인 중간 이력, $H_{\mathrm{recent}}$는 원문 그대로 보존하는 최근 이력입니다. $U$는 사용 가능한 입력 창, $B_1$은 생략을 시작하는 하위 임계값, $B_2$는 요약을 고려하는 상위 임계값, $R$은 최근 이력에 배정한 토큰 예산입니다. 최근 이력은 예산 방식으로 정하되 **최소 두 턴을 보존**합니다. $U$를 논문의 명목상 32k·64k·96k·128k와 무조건 같은 값으로 놓아서는 안 됩니다. **[p.5, §2.3; p.6, Implementation Details]** 2609.20804v1 2609.20804v1

T4의 단계적 처리 규칙은 다음과 같이 표현할 수 있습니다.

$$
H^{(1)}=
\begin{cases}
\text{ElideStore}(H), & \text{tokens}(H)\ge B_1,\\
H, & \text{otherwise},
\end{cases}
$$

$$
H'=
\begin{cases}
\text{Summarize}_{\theta}(H^{(1)}),
& \text{tokens}(H^{(1)})\ge B_2,\\
H^{(1)}, & \text{otherwise}.
\end{cases}
$$

**기호 설명:** $\text{tokens}$는 이력의 토큰 수, $H^{(1)}$는 첫 단계 처리 결과, $H'$는 최종 관리 이력입니다. $\text{ElideStore}$는 중간 영역의 큰 도구 출력을 저장하고 생략하는 연산이며, $\text{Summarize}_{\theta}$는 동일 모델로 오래된 중간 이력과 기존 요약을 정리하는 연산입니다. 시스템 지침·과제 설명·보존 대상 최근 이력은 이 연산의 압축 대상이 아닙니다. **[p.5, Algorithm 1]** 2609.20804v1

### 2.6. 실험 설계와 평가 지표

**[저자 보고]** SWE-Bench Verified는 500개 과제, Terminal-Bench 2.1은 89개 과제로 설명되어 있습니다. 모델·벤치마크 쌍마다 컨텍스트 관리 5종과 창 크기 4종을 조합한 20개 조건을 평가하고, T4/128k에서 계획 제거와 bash-only 두 조건을 추가했습니다. 따라서 설정 수는 $4\times2\times(20+2)=176$입니다. 각 과제는 각 설정에서 한 번 실행했습니다. **[p.6, §3.1; p.16, Limitations]** 2609.20804v1 2609.20804v1

성공률과 비용 정의는 다음처럼 정리할 수 있습니다.

```math
\widehat{\mathrm{SR}}
=
\frac{100}{n}\sum_{i=1}^{n}y_i,
\qquad
\overline C
=
\frac{1}{n}\sum_{i=1}^{n}
\frac{
p_{\mathrm{in}}N_{\mathrm{in},i}
+
p_{\mathrm{out}}N_{\mathrm{out},i}
}{10^6}.
```

**기호 설명:** $n$은 평가 과제 수, $y_i$는 과제 $i$의 성공 여부인 0 또는 1, $\widehat{\mathrm{SR}}$은 백분율 성공률입니다. $N_{\mathrm{in},i}$와 $N_{\mathrm{out},i}$는 비용 집계에 사용한 누적 입력·출력 토큰 수, $p_{\mathrm{in}}$과 $p_{\mathrm{out}}$은 백만 토큰당 단가, $\overline C$는 과제당 평균 환산 비용입니다.

비용은 로컬 모델 실행에 사용한 실제 GPU 운영비가 아니라 **2026년 8월에 확인한 OpenRouter 토큰 단가를 적용한 값**입니다. 따라서 현재의 실제 배포 비용이나 서로 다른 하드웨어의 효율로 직접 해석할 수 없습니다. **[p.6, Models 및 각주 1]** 2609.20804v1

### 5.2. “차이가 유의하지 않음”은 “동등함”이 아니다

**[통계 주의]** T4가 다른 관리 방식과 “비슷한 정확도”라는 문구는 주로 관측 평균에 대한 설명입니다. 원문이 명시한 비교군은 관리 정책 대 T0, 계획 사용 대 제거, 전체 도구 대 bash-only입니다. T1–T4 사이의 정확도 동등성이나 허용 가능한 손실 한도를 별도로 검증한 실험은 제시되지 않습니다. **[p.6, §3.1]** 2609.20804v1

> **용어 풀이 — 동등성·비열등성 검정:** 단순히 차이를 발견하지 못했다는 것을 넘어, 미리 정한 허용 범위 안에서 성능이 충분히 같거나 나쁘지 않음을 검증하는 방법입니다.

실제로 SWE 32k의 550B에서는 T3가 **58.4% / 1.25달러**, T4가 **55.6% / 1.45달러**로, 관측값상 T3가 성공률과 비용 모두 유리합니다. 이 비교의 직접적인 유의성은 표에 표시되지 않았습니다. 따라서 T4의 결론은 **전체 평균의 유리함**으로 제한해야 합니다. **[p.7, Table 3]** 2609.20804v1

### 5.3. 구성요소 상호작용을 충분히 측정하지 않았다

**[저자 인정]** 계획과 행동 인터페이스는 T4/128k에서만 제거 실험을 수행했습니다. 그러므로 작은 창, 요약만 사용하는 정책, 계획이 없는 bash-only 조건 등에 같은 결론이 유지되는지는 알 수 없습니다. **[p.16]** 2609.20804v1

**[추가 해석]** T4는 구성요소뿐 아니라 생략 시점도 다릅니다. T1–T3는 $B_2$에서 작동하지만 T4는 $B_1$에서 생략을 시작하므로, T4의 이득을 “세 기능의 결합”과 “더 이른 압축”으로 분리하기 어렵습니다. 또한 **회수 없는 생략+요약**, 즉 M1+M3 조건이 없어 T4에서 M2를 제거해도 같은 성능인지 직접 답할 수 없습니다. **[p.5, Table 2]** 2609.20804v1

### 5.4. 행동 분석은 유용하지만 독립적인 인과 검증은 아니다

저자들은 200개 실행 궤적에서 총 15,610개 단위를 사람과 모델이 분류해 검증했고, 전체 일치율 약 94.2%, 가중 평균 Cohen의 $\kappa$ 0.929를 보고했습니다. 그러나 세 사람은 서로 겹치지 않는 자료를 나누어 분류했으므로, 이 결과는 사람끼리 동일 사례를 판단한 일치도와 같지 않습니다. 실패 단계 진단 검증도 50개 사례에 해당합니다. **[pp.28–29, Appendix C.2]** 2609.20804v1 2609.20804v1

> **용어 풀이 — Cohen의 $\kappa$:** 우연히 같은 답을 선택할 가능성을 보정한 분류 일치도입니다.

**[해석]** 높은 일치율은 행동 분석의 신뢰성을 뒷받침하지만, “검증이 줄었기 때문에 비용이 감소했다”는 관찰을 “줄어든 검증은 모두 불필요했다”는 인과 주장으로 바꾸지는 못합니다. 성공한 과제와 실패한 과제, 일찍 종료한 실행과 오래 살아남은 실행의 구성이 달라지는 영향도 고려해야 합니다.

| **Xia et al., 2026 — *RRSI: Regularized Recursive Self-Improvement of Agent Harnesses*** | 하네스 수정 제안과 선택을 규제해 특정 벤치마크에 대한 과적합을 줄임. 변경에 사용하지 않은 SWE Verified에서 82.0→83.8, JobBench에서 36.0→40.7을 보고. **v2 p.8, Figure 3·Table 1**. [arXiv](https://arxiv.org/pdf/2609.24972v2) | 본 논문이 주로 조건별 효과를 분석했다면, RRSI는 하네스를 개선한 뒤 **보지 않은 평가 환경으로 고정 이전**하는 일반화 검증을 더 직접 수행 |

> **용어 풀이**  
> **pass@1:** 한 번 생성·실행한 결과가 성공하는 비율.  
> **증류(distillation):** 큰 모델의 출력을 학습 자료로 사용해 작은 모델이 유사한 기능을 수행하도록 만드는 방법.  
> **시드(seed):** 무작위 실행을 반복·구분하기 위한 초기 설정값.  
> **F1:** 정답 요소를 얼마나 정확하고 빠짐없이 맞혔는지 결합한 점수로, 전체 과제 성공률과는 다릅니다.  
> **F2PF:** 수정 전 실패하던 테스트 중 수정 후 통과하게 된 비율로, 과제를 완전히 해결했다는 지표와 다릅니다.  
> **과적합:** 설계에 사용한 과제의 특수한 패턴에는 잘 맞지만 새로운 과제에서는 이득이 줄어드는 현상.

SoL-Pi와 RRSI는 본 논문과 동시기 또는 이후에 공개된 비교 자료입니다. 이들을 **본 논문의 영향을 받아 수행된 직접적인 후속 연구라고 주장하는 것은 아닙니다.**

### 7.2. 관련 연구를 함께 읽었을 때의 핵심 차이

**첫째, “보존할 수 있음”과 “필요한 정보를 제대로 되찾음”은 다릅니다.** MemGPT는 외부 기억을 적극적으로 관리하는 구조를 다루지만, 본 논문의 T2는 과거 출력에 식별자를 붙여 회수할 수 있게 하는 비교적 제한된 구현입니다. 따라서 회수가 거의 없었다는 결과는 저장 기능 자체보다 **회수 필요성·회수 정책·도구 학습의 적합성**을 다시 설계할 필요성을 제기합니다. 이는 본 논문의 T1–T2 결과와 MemGPT의 과제 차이를 연결한 제 해석입니다. **[본 논문 pp.8–9; MemGPT p.1]** 2609.20804v1 2609.20804v1 [arXiv](https://arxiv.org/pdf/2310.08560)

**둘째, 고정 규칙의 효율과 학습된 압축의 일반화는 서로 다른 문제입니다.** T4는 언제 압축할지를 정한 규칙이 중심이고, ACON은 실패 사례를 이용해 무엇을 남겨야 할지 개선합니다. 후속 연구에서는 둘을 같은 하네스·같은 예산 안에서 비교해야, 학습된 압축의 추가 복잡성이 실제 코딩 성능으로 돌아오는지 판단할 수 있습니다. **[본 논문 pp.5–6; ACON §§4.2–4.3]** 2609.20804v1 [arXiv](https://arxiv.org/html/2510.00615v2)

**셋째, 일반화를 주장하려면 “좋은 구성을 찾은 과제”와 “성능을 확인할 과제”를 분리해야 합니다.** RRSI는 이 문제를 명시적으로 다루며, 본 논문에서 다음 단계로 나아갈 때 유용한 비교 대상입니다. 다만 하네스를 바꾸어 얻은 전이 성능 역시 기반 모델의 가중치에 새로운 능력이 학습되었다는 뜻은 아닙니다. **[RRSI pp.2–3, 7–8]** [arXiv](https://arxiv.org/pdf/2609.24972v2)

#### 관련 최신 방법의 수식 예: RRSI의 수정 예산

아래는 **본 분석 대상 논문의 수식이 아니라**, RRSI 원문의 식 (4)입니다.

$$
b_t=
\left\lceil
b_{\min}
+
(b_{\max}-b_{\min})
\frac{1+\cos(\pi t/T)}{2}
\right\rceil.
$$

**기호 설명:** $t$는 하네스 개선 라운드, $T$는 전체 라운드 수, $b_t$는 한 후보에 허용하는 수정 개수, $b_{\max}$와 $b_{\min}$은 최대·최소 수정 예산, $\lceil\cdot\rceil$는 올림입니다. 초기에는 여러 변경을 허용하고 후기에는 적은 변경만 허용해 효과를 추적하기 쉽게 만듭니다. 원문도 이를 고정된 신경망 가중치에 대한 정규화 손실이 아니라 **수정 과정에 대한 제한**으로 설명합니다. **[RRSI v2 p.5, Eq.4]** [arXiv](https://arxiv.org/pdf/2609.24972v2)

**[해석]** 본 논문의 모듈별 제거 실험과 이런 제한을 결합하면, 자동 탐색 과정에서 여러 기능이 한꺼번에 바뀌어 원인을 알 수 없게 되는 문제를 줄이는 연구 설계를 만들 수 있습니다.

## 8. 일반화 성능 향상 가능성과 결론

### 8.1. 이 논문에서 확인된 일반화와 확인되지 않은 일반화

**확인된 것은 제한된 범위의 조건 변화에 대한 성능 안정성입니다.** 특히 컨텍스트 관리를 사용하면 입력 창이 작아져도 성공률이 T0만큼 급격히 무너지지 않습니다. 두 모델 계열과 두 과제 집합에서 비교했다는 점도 단일 모델 연구보다 넓은 근거입니다. **[pp.2, 7–9]** 2609.20804v1 2609.20804v1

그러나 다음은 구분해야 합니다.

| 일반화의 대상 | 이 논문이 제공하는 근거 | 판단 |
|---|---|---|
| 입력 창 크기 변화 | 32k–128k 비교 | **직접적인 제한 범위의 근거 있음** |
| 모델 크기·계열 변화 | Nemotron 세 크기와 Mistral 한 모델 | **부분적 근거 있음** |
| 과제 유형 변화 | 저장소 문제 해결과 터미널 과제 | **부분적 근거 있음; 일부 효과는 반전** |
| 새로운 언어·비공개 저장소·장기 업무 | 별도의 고정 이전 평가 없음 | **입증되지 않음** |
| 모델 가중치에 내재한 능력 향상 | 하네스 실험이며 모델 학습 개입 없음 | **이 연구의 검증 대상이 아님** |

저자들도 SWE-Bench Verified가 Python에 한정되며, 모델 크기 외에 훈련·도구 노출·셸 능력이 결과에 영향을 줄 수 있다고 명시합니다. **[p.16, Limitations]** 2609.20804v1

**[해석]** 일반화 향상 가능성은 충분히 있습니다. 다만 기대해야 할 것은 우선 **“새로운 환경에서도 기존 능력을 잃지 않도록 돕는 하네스”**입니다. 그러한 하네스가 학습 과정에 활용되어 모델 자체의 도구 적응 능력까지 개선하는지는 별도의 연구 질문입니다.

### 8.2. 저자가 제시한 시사점과 향후 검증 과제

**[저자 결론]** 하네스는 기본적으로 기능을 많이 넣는 방향이 아니라, 대상 모델·과제 유형·자원 예산에 맞춰 선택해야 합니다. 컨텍스트 관리는 입력 한도에 의한 종료를, 계획은 너무 이르거나 늦은 종료를, 구조화된 도구는 제한된 셸 활용 능력을 보완하는 기능으로 설명됩니다. **[pp.15–16, §6]** 2609.20804v1

**[저자가 명시한 추가 검증 필요성]** 다른 계획·압축 구현, 전요인 실험, 다른 모델 계열과 과제로의 이전 검증이 필요합니다. 다만 논문은 이러한 필요성을 제시할 뿐, 구체적인 수행 일정이나 확정된 후속 연구 계획을 제시하지는 않습니다. **[p.16, Limitations]** 2609.20804v1

> **용어 풀이 — 전요인 실험:** 관심 있는 요인들의 가능한 조합을 모두 비교해 개별 효과뿐 아니라 결합 효과도 조사하는 설계입니다.

### 8.3. 추가 후속 연구 제안: 일반화를 우선하는 실험 설계

#### A. 구성 선택 단계와 최종 평가를 분리해야 한다

**[제안]** 하네스를 고르는 개발 과제와 최종 평가 과제를 저장소·시간·프로그래밍 언어·모델 계열 기준으로 분리해야 합니다. 개발 단계에서 계획 사용 여부와 압축 임계값을 선택한 뒤, 평가에서는 다시 맞추지 않고 고정해 실행하는 방식입니다. RRSI와 SoL-Pi의 고정 이전 평가를 참고하되, 본 논문의 모듈별 분석을 유지하는 것이 적절합니다. [arXiv](https://arxiv.org/pdf/2609.24972v2)

특히 공개 GitHub 과제에서 웹 검색을 제외하는 조치는 실행 중 정답 노출 위험을 줄이려는 것이지만, 사전학습 노출 여부까지 검증하는 조치는 아닙니다. 비공개 또는 시간적으로 분리된 과제로 확인해야 두 문제를 구분할 수 있습니다. **[본 논문 p.3, §2.2]** 2609.20804v1

#### B. 모델 크기가 아니라 실제 실패 행동으로 하네스를 선택해야 한다

**[제안]** 파라미터 수 대신 잘못된 도구 호출 비율, 수정 전 종료 비율, 반복 검증 비율, 입력 한도 압박, 복합 셸 명령 성공률을 측정해 구성을 선택하는 정책을 연구할 가치가 있습니다. 가령 조기 종료가 많은 모델에는 계획 유지 장치를, 셸 호출을 안정적으로 조합하는 모델에는 더 넓은 행동 표현을 제공하는 방식입니다.

이는 본 논문의 행동 분석에서 도출한 가설이지 검증된 적응형 정책은 아닙니다. 잘못된 진단이 잘못된 하네스 선택으로 이어질 수 있으므로, 진단 비용과 선택 실패까지 최종 성능에 포함해야 합니다. **[근거: pp.12–14, Figures 8–9, Tables 6–7]** 2609.20804v1 2609.20804v1

#### C. 회수와 요약을 “사용 횟수”가 아니라 “정보 필요성”으로 평가해야 한다

**[제안]** 다시 실행하면 얻을 수 있는 파일 내용과, 다시 얻을 수 없는 과거 오류·중간 상태를 구분한 과제를 만들어야 합니다. 회수를 배우지 않은 모델, 회수 사용을 학습한 모델, 자동 회수 정책을 비교하면 “필요 없어서 안 썼는가”와 “쓸 줄 몰라서 안 썼는가”를 분리할 수 있습니다.

요약 역시 길이만 줄이는 것이 아니라 정확한 파일 경로, 이미 반증된 가설, 통과·실패한 테스트, 아직 해결되지 않은 제약을 얼마나 보존하는지 평가해야 합니다. 이는 본 논문의 낮은 회수 사용량과 ACON의 실패 기반 압축 최적화를 연결한 후속 방향입니다. **[본 논문 pp.8–9, Figure 18; ACON]** 2609.20804v1 2609.20804v1 [Microsoft](https://www.microsoft.com/en-us/research/publication/acon-optimizing-context-compression-for-long-horizon-llm-agents/?lang=ko-kr)

#### D. 평균 최고점보다 여러 환경에서의 안정성을 최적화해야 한다

**[제안 수식 — 본 논문의 원문 수식 아님]**

```math
h^\star
=
\arg\max_{h\in\mathcal H}
\min_{d\in\mathcal D_{\mathrm{dev}}}
\left[
\widehat s_d(h)
-\lambda\widetilde C_d(h)
-\mu\Omega(h)
\right].
```

**기호 설명:** $h$는 하네스 설정 또는 구성 선택 정책, $\mathcal H$는 후보 집합, $\mathcal D_{\mathrm{dev}}$는 개발 단계에서 사용하는 여러 환경입니다. $\widehat s_d(h)$는 환경 $d$에서의 성공률을 0–1 범위로 표현한 값, $\widetilde C_d(h)$는 정규화한 비용, $\Omega(h)$는 복잡도 측정값입니다. $\lambda,\mu\ge0$는 비용과 복잡도에 부여하는 가중치이며, $\min$은 성능이 가장 불리한 개발 환경을 고려한다는 뜻입니다.

> **용어 풀이 — 강건 최적화:** 평균적으로 좋은 해뿐 아니라 불리한 조건에서도 지나치게 무너지지 않는 해를 찾는 접근입니다.

이 목적은 특정 벤치마크의 점수를 조금 올리기 위해 여러 환경에서 실패 위험을 키우는 구성을 피하려는 것입니다. 하지만 개발 환경에서의 강건성이 전혀 새로운 환경을 보장하지는 않으므로, **별도의 미관측 평가 집합, 과제별 반복 실행, 저장소 단위 불확실성 분석, 동일 시간·비용 예산 비교**가 함께 필요합니다.

### 최종 결론

이 논문의 가장 강한 메시지는 **“좋은 코딩 하네스는 기능이 많은 하네스가 아니라, 해당 모델이 해당 조건에서 보이는 실패를 정확히 보완하는 하네스”**라는 것입니다. 작은 입력 창에서의 컨텍스트 관리 효과와, 모델에 따라 계획·도구의 역할이 달라지는 관찰은 이를 뒷받침합니다. **[pp.15–16, Conclusion]** 2609.20804v1

반면 T4의 보편적 우월성, 외부 기억의 무용성, 강한 모델에서의 bash-only 우월성, 기반 모델 자체의 일반화 향상은 이 논문만으로 확정할 수 없습니다. 다음 연구에서 중요한 것은 **설계에 사용하지 않은 모델·저장소·언어·도구 환경에 하네스를 고정해 이전했을 때도 성공률–비용의 이점이 남는지**입니다. 그 검증까지 이루어져야 조건별 설계 관찰이 일반화 가능한 연구 원칙으로 발전할 수 있습니다.
