## 1. Executive Summary (10문장 이내)

Terminal-Universe는 터미널 기반 코드 에이전트의 **궤적(trajectory)을 재사용 가능한 실행 환경(environment)으로 역변환**하는 프레임워크이다.  
기존 에이전트 사후 훈련(post-training)에는 검증 가능한 실행 환경이 필요하지만, 현실적인 환경은 희소하고 수동 제작 비용이 크다.  
본 연구는 에이전트 궤적 내 파일 연산 기록이 원본 실행 환경의 구조와 내용을 암묵적으로 노출한다는 관찰에서 출발한다.  
이를 활용해 (1) 결정론적 재실행(deterministic replay)으로 부분 워크스페이스를 복원하고, (2) 에이전트 기반 완성(agentic completion)으로 누락 파일을 보충하여 완전한 실행 환경을 구성한다.  
복원된 환경에서 원래 작업을 재구성하고 새로운 작업을 합성하며, 단일·다중 워크스페이스 및 다회차(multi-round) 쿼리로 확장한다.  
공개 궤적 데이터에 적용한 결과 37.3k개의 충분한 환경이 생성되었다.  
Qwen3.5-27B를 이 데이터로 SFT(Supervised Fine-Tuning)하면 Terminal-Bench 2.1에서 +11.9점, EvoCode-Bench v2 MT@4에서 +13.8점 향상된다.  
절제 연구(ablation study)를 통해 환경 재구성 후 재풀이(re-solving)가 원본 궤적 모방보다 유의미하게 우수함을 확인하였다.  
본 연구는 축적된 에이전트 궤적을 새로운 훈련 데이터 합성 자원으로 재정의하는 확장 가능한 패러다임을 제시한다.

> **📘 용어 설명**
> - **궤적(trajectory)**: 에이전트가 작업을 수행하며 생성한 행동·관찰의 순차적 기록
> - **사후 훈련(post-training)**: 사전 학습된 모델을 특정 태스크에 맞게 추가 미세조정하는 단계
> - **SFT(Supervised Fine-Tuning)**: 레이블된 예시 데이터로 모델을 지도 학습 방식으로 미세조정하는 기법

### 1-1. 연구의 목적과 필요성

**문제 배경**: 터미널 기반 코드 에이전트가 보편화되면서 에이전트 궤적은 대규모로 축적되고 있으나, 사후 훈련에 실질적으로 필요한 **현실적이고 검증 가능한 실행 환경**은 여전히 희소하다 (p.1, Introduction).

| 비교 항목 | 궤적(Trajectory) | 환경(Environment) |
|---|---|---|
| 재사용성 | 단일 고정 기록 | 동일 환경에서 다수 태스크 생성 가능 |
| 검증 가능성 | 결과 정확성 확인 불가 | 자체 테스트로 검증 가능 |
| 확장성 | 원 모델 품질에 한정 | 더 강력한 모델로 재풀이 가능 |
| 난이도 조정 | 불가 | 동일 워크스페이스에서 더 어려운 태스크 부여 가능 |

**필요성**: 수동 제작 벤치마크(예: Terminal-Bench)는 높은 신뢰성을 제공하지만, 제작 비용 때문에 규모를 키우기 어렵다. 효과적인 사후 훈련은 수동 큐레이션이 제공할 수 있는 것보다 훨씬 많은 환경을 필요로 한다 (p.1).

## 2-1. 상세 설명

### 해결하고자 하는 문제

터미널 코드 에이전트 사후 훈련을 위한 **현실적이고 검증 가능한 실행 환경의 규모 확보 문제**.

기존 3가지 접근법의 한계:
- **저장소 기반**: 태스크 유형이 버그 수정으로 제한됨
- **변형(perturbation) 기반**: 주입 가능한 버그 유형에 의존
- **태스크 조건부 합성**: 실제 프로젝트와 무관한 소규모·정제된 워크스페이스 생성

---

### 제안하는 방법

#### 단계 1: 결정론적 재실행 (Deterministic Replay)

궤적 $\tau$의 파일 연산(read, write, edit)을 시간순으로 재실행하여 부분 초기 워크스페이스를 복원한다:

```math
\hat{E}_0 = \text{Replay}(\tau) = \{f_p \mid p \in \text{paths\_touched}(\tau),\ f_p = \text{earliest\_observed\_content}(p, \tau)\}
```

- $\hat{E}_0$: 재실행으로 복원된 부분 초기 워크스페이스
- $\tau$: 에이전트 궤적
- $p$: 궤적 내 에이전트가 접근한 파일 경로
- $f_p$: 경로 $p$에서 에이전트가 처음 변경하기 전의 파일 내용
- 에이전트가 새로 생성한 파일은 제외 (솔루션 누출 방지)

> **📘 용어 설명**
> - **결정론적 재실행**: 동일 입력에 대해 항상 동일한 출력을 생성하는, 랜덤성 없는 재현 방식

#### 단계 2: 에이전트 기반 완성 (Agentic Completion)

부분 워크스페이스 $\hat{E}_0$와 복원된 태스크 $q$를 받아 완전한 워크스페이스 $\hat{E}$를 생성:

$$\hat{E} = \text{Complete}(\hat{E}_0, q) \quad \text{s.t.} \quad \text{solution}(q) \notin \hat{E}$$

- $\hat{E}$: 완성된 실행 가능 워크스페이스
- $q$: 복원된 태스크 명세
- 완성 에이전트는 누락 파일 생성, 의존성 복원을 수행하되 솔루션을 구현하지 않는 제약을 준수

#### 단계 3: 환경 충분성 필터링 (Environment Filtering)

에이전트 판사(agentic judge)가 $\hat{E}$를 읽기 전용 도구로 검사하여 이진 레이블 부여:

$$\hat{E} \in \mathcal{E}_{\text{sufficient}} \iff \text{Judge}(\hat{E}, q) = \text{"sufficient"}$$

#### Cross-WS 관계 탐색 (TF-IDF 기반)

워크스페이스 프로파일 간 의존성 방향 탐지:

$$\text{sim}(w_i, w_j) = \text{TF-IDF cosine}(\text{profile}(w_i), \text{profile}(w_j))$$

$$\text{dependency}(w_i \to w_j) \iff \text{LLM judge}(w_i, w_j) = \text{"dependency"} \land \text{donor} = w_i$$

- $w_i, w_j$: 두 워크스페이스 프로파일
- $\text{donor}$: 능력(capability)을 보유한 참조 워크스페이스

> **📘 용어 설명**
> - **TF-IDF**: 문서 내 단어의 빈도와 역문서 빈도를 이용한 텍스트 유사도 측정 방법
> - **코사인 유사도**: 두 벡터 간 각도의 코사인값으로 유사성을 측정하는 지표

#### Multi-Round 깊이 확장

라운드 $t$에서의 세션 상태:

$$\mathcal{S}_t = (\mathcal{W}_t,\ \mathcal{R}_t^{\text{active}},\ \mathcal{R}_t^{\text{satisfied}},\ h_t)$$

- $\mathcal{W}_t$: 라운드 $t$의 워크스페이스 상태
- $\mathcal{R}_t^{\text{active}}$: 활성 요구사항 집합
- $\mathcal{R}_t^{\text{satisfied}}$: 충족된 요구사항 집합
- $h_t$: 대화 히스토리

사용자 에이전트의 다음 메시지 생성:

$$m_{t+1} = \text{UserAgent}(\mathcal{S}_t,\ v_t) \quad \text{where} \quad v_t = \text{Verifier}(\mathcal{W}_t, \mathcal{R}_t)$$

- $v_t$: 라운드 $t$의 검증기 실행 결과 (비공개, 코딩 에이전트에게 숨김)

## 4. 저자 보고 결과 vs. 해석 분리

### 연구 주제
**저자 보고**: "에이전트 궤적을 재사용 가능한 터미널 환경으로 변환하는 Terminal-Universe 프레임워크를 제안한다." (p.1, Abstract)

**해석**: 이는 기존 "환경→궤적" 방향의 접근을 역전시킨 것으로, 훈련 데이터 합성 패러다임의 전환을 의미한다. 데이터 플라이휠(data flywheel) 관점에서 보면, 에이전트가 더 복잡한 궤적을 생성할수록 더 풍부한 환경을 복원할 수 있는 자기강화 구조를 가진다.

> **📘 용어 설명**
> - **데이터 플라이휠**: 더 많은 데이터가 더 좋은 모델을 만들고, 더 좋은 모델이 더 많은 데이터를 생성하는 자기강화 사이클

---

### 방법 (수식 포함)

**저자 보고**: 

재실행 단계에서 초기 워크스페이스를 다음과 같이 정의한다 (p.4, §3.1):

$$\hat{E}_0 \leftarrow \{f_p^{\text{earliest}} \mid p \in \text{touched}(\tau)\} \setminus \{f_p^{\text{agent-created}}\}$$

평균 파일 수가 2.9에서 22.4로 증가하였음을 보고한다 (p.7, Figure 4):

$$\frac{|\hat{E}|_{\text{files}}}{|\hat{E}_0|_{\text{files}}} \approx 7.7 \quad \text{(Terminal pool)}$$

**해석**: 파일 수 7.7배 증가는 단순 파일 추가를 넘어 의존성 그래프 복원과 프로젝트 맥락 재구성을 포함한다. 그러나 텍스트 라인 수의 64.0배(90→5,761) 증가는 에이전트가 생성한 파일의 규모가 상당히 크다는 것을 시사하며, 이 중 일부는 태스크와 직접 관련 없는 파일을 포함할 수 있다. 저자도 수동 검사에서 30개 샘플 중 8개에서 불필요한 파일 추가를 발견했음을 인정한다 (p.18, §B.1).

---

### 결과

**저자 보고**:
- Terminal-Bench 2.1: 기준 46.2% → 58.1% (+11.9pp) (p.9, Table 3)
- EvoCode-Bench v2 MT@4: 6.3% → 20.1% (+13.8pp) (p.9, Table 3)
- Intent Recovery vs Source SFT: 52.1 vs 36.7 (p.9, Table 4)

**해석**: 
- MT@4 기준값 6.3%는 매우 낮아, 단순히 첫 번째 라운드조차 통과하지 못하는 경우가 대부분임을 시사한다. 이는 베이스 모델이 다회차 인터랙티브 태스크에 구조적으로 취약함을 보여주며, +13.8pp 향상이 절대값으로는 아직 낮은 수준(20.1%)임에 유의해야 한다.
- Source SFT가 베이스 모델(47.0)보다도 낮은 36.7을 기록한 것은 **원본 궤적의 품질 불균일성**이 학습을 저해할 수 있음을 시사한다. 이는 단순히 더 많은 데이터가 더 좋은 것은 아님을 보여주는 중요한 발견이다.

## 7. 가장 중요한 그림 5개 해석

### Figure 1 (p.2): 프레임워크 개요
**해석**: 기존 연구가 "환경→궤적" 방향(롤아웃)을 취하는 반면, Terminal-Universe는 이를 역전하여 "궤적→환경" 방향(재구성)을 택한다. 그림 좌측의 **이중성(duality)** 개념이 논문의 핵심 통찰이다. 복원된 환경은 단일 워크스페이스, 교차 워크스페이스, 다회차 쿼리의 세 방식으로 재활용될 수 있어 하나의 환경에서 다수의 훈련 신호를 생성하는 승수 효과(multiplier effect)를 달성한다.

---

### Figure 2 (p.5): 프레임워크 상세 메커니즘
**해석**: 환경 복원(좌측)과 재쿼리(우측) 두 축의 구체적 실행 방식을 보여준다. 특히 에이전트 완성 단계에서 `/app` 하위에 새 파일들(`schemas/`, `scripts/`, `Makefile`, `pyproject.toml`)이 추가되는 과정이 시각화되어 있다. Cross-WS 섹션에서 워크스페이스 간 의존성 방향(A→D: dependency, B-E: similar)을 그래프로 표현한 부분은 관계 탐색의 복잡도를 직관적으로 전달한다. Multi-Round 섹션의 대화 흐름은 사용자 에이전트가 실패 피드백을 자연어로 변환하는 과정을 보여준다.

---

### Figure 4 (p.7): 에이전트 완성 전후 워크스페이스 크기
**해석**: 세 가지 지표(파일 수, 전체 텍스트 라인, 소스 코드 라인)에서 에이전트 완성의 효과를 정량적으로 보여준다. Terminal 풀에서 코드 라인이 43→503(×11.7배) 증가한 것은 단순 파일 복사가 아닌 **실질적인 프로젝트 맥락 구성**이 이루어졌음을 시사한다. 그러나 텍스트 라인의 90→5,761(×64배) 증가는 완성 에이전트가 생성하는 비코드 파일(설정, 문서 등)의 규모가 상당히 크다는 점에서 잠재적 노이즈 우려가 존재한다.

---

### Figure 6 (p.11): Cross-WS 카테고리별 성능 변화
**해석**: 전체 +2.0pp 향상의 이면에 카테고리별 비대칭성이 존재한다. 모델 훈련(+15.0), 디버깅(+10.0), 수학(+10.0)의 대폭 향상은 Cross-WS 태스크가 **다중 코드베이스 통합 능력**을 효과적으로 훈련시킨다는 증거이다. 반면 보안(-2.1), 머신러닝(-2.2), 과학 계산(-2.5)의 소폭 하락은 이 카테고리들이 Cross-WS 훈련에서 충분히 커버되지 않거나 도메인 특화 지식이 부족함을 시사한다. 단, 이들 카테고리는 n=3~9로 소표본이므로 통계적 유의성이 낮다.

---

### Figure 7 (p.17): 환경 복원 전체 파이프라인 흐름
**해석**: 359,593개 소스 궤적에서 최종 37,273개 충분한 환경까지의 데이터 감소율을 명확히 보여준다. **291,330개(81.1%)가 불충분한 재실행 복잡도로 탈락**하는 것은 현재의 공개 궤적 코퍼스의 상당 부분이 파일 내용을 충분히 노출하지 않는다는 현실적 제약을 드러낸다. 이는 향후 더 표현적인 궤적을 생성하는 에이전트가 등장할수록 이 파이프라인의 효율이 크게 향상될 여지가 있음을 의미한다.

## 8. 결론 및 후속 연구

### 8-1. 모델의 일반화 성능 향상 가능성

**저자가 제시한 시사점** (p.13, §7; p.13, §8):

1. **소스 궤적 품질과 복원 환경 복잡도의 양의 상관관계**: 더 풍부한 연산 이력(다중 파일 조작, 긴 도구 사용 체인)을 가진 궤적이 더 다양하고 어려운 합성 태스크를 지원한다.

2. **세션 병합을 통한 환경 복잡도 향상**: 동일 워크스페이스에서 여러 세션을 재실행하여 합치면 단일 궤적보다 풍부한 환경을 생성할 수 있다.

3. **에이전트 능력 향상과의 선순환**: 에이전트 능력이 발전할수록 더 복잡한 궤적이 용이하게 생성되어 파이프라인이 자연스럽게 확장된다.

**일반화 관련 핵심 발견**:

| 일반화 방향 | 결과 | 위치 |
|---|---|---|
| SWE→터미널 전이 | 47.0→50.0 (+3.0pp), 양방향 스캐폴드 모두 향상 | Table 11 |
| Single-turn→Multi-turn | MT@4: 18.4→21.0, Case: 71.9→76.9 | Table 9 |
| 단일→교차 워크스페이스 | 56.4→58.4 (+2.0pp) | Table 7 |
| 환경 확장 우위 | 환경 수 증가 > 쿼리/솔루션 수 증가 | Table 10 |

**일반화 성능 향상의 핵심 메커니즘 분석**:

Cross-WS 훈련이 일반화에 효과적인 이유는 **두 코드베이스의 맥락을 동시에 이해하고 통합하는 과정**이 단일 워크스페이스 태스크보다 더 강한 표현 학습을 유도하기 때문으로 해석된다. Cross-WS 태스크의 난이도 지표(교사 pass@1: 49.2% vs Single-WS 72.3%)가 이를 지지한다.

**향후 일반화 향상을 위한 제언**:

$$\text{Generalization}(\theta) \propto \mathbb{E}_{E \sim \mathcal{E}}[\text{TaskDiversity}(E)] \times \mathbb{E}_{q \sim \mathcal{Q}(E)}[\text{Verifiability}(q)]$$

- $\theta$: 모델 파라미터
- $\mathcal{E}$: 복원 환경 분포
- $\mathcal{Q}(E)$: 환경 $E$에서 생성 가능한 태스크 분포

즉, 환경의 다양성과 태스크의 검증 가능성을 동시에 최대화하는 방향이 일반화에 유리하다.

#### 향후 연구에 미치는 영향

1. **패러다임 전환 효과**: "환경이 먼저, 궤적이 나중"이라는 기존 순서를 역전하여 이미 축적된 궤적 데이터를 환경 생성 자원으로 재활용하는 새로운 데이터 파이프라인 설계 원칙을 제시한다.

2. **다회차 에이전트 훈련의 기반 마련**: EvoCode-Bench v2 성능 향상은 지속적 개발 세션(persistent coding session) 모델링의 중요성을 강조하며, 후속 연구에서 더 긴 다회차 태스크 합성이 활발해질 것으로 예상된다.

3. **교차 도메인 태스크 설계**: Cross-WS 방식은 단일 저장소를 넘어 **다중 코드베이스 통합 능력**을 훈련하는 새로운 방향을 제시하며, 실제 개발 환경에서의 "기존 참조 구현을 바탕으로 한 기능 이식" 시나리오를 반영한다.
