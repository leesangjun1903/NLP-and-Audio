## 1. Executive summary — 9문장

1. Harness²는 새로운 과제가 도착할 때 모델 가중치를 고정한 채 실행 하네스를 수정하고, 수정 경험을 축적하는 두 수준의 재귀적 개선 프레임워크입니다. [pp.3–7]
2. 해결하려는 문제는 실제 배포 과제에 정답 검증기가 없는 경우가 많고, 한 과제에 유용했던 수정이 다음 과제에서도 유효하리라는 보장이 없다는 점입니다. [p.2]
3. 과제 수준에서는 범용적인 작업 절차와 영역별 전문 요구를 각각 겨냥한 후보를 제안하고, 같은 과제에서 실행한 행동 차이를 관찰한 뒤, 근거가 있는 수정만 선택적으로 합성합니다. [p.5, Figure 3]
4. 과제 간에는 채택된 실행 하네스와 수정의 적용 조건·근거를 저장하지만, 새 과제의 실행은 항상 공통 초기 하네스에서 시작합니다. [pp.6–7]
5. 기본 실험의 두 실행 모델과 두 초기 하네스 조합 모두에서 한 단계 개선이 기본 설정보다 높은 평균 점수를 기록했으며, 최대 향상은 WorkBuddy-Bench 평균 11.5점, JobBench 4.5점, LAB 기준별 통과율 11.8%p입니다. [pp.8–9, Tables 1–2]
6. 병렬 탐색 예산을 $k=5$로 늘리면 한 단계 개선 대비 WorkBuddy-Bench에서 2.9–3.9점, JobBench에서 3.0–4.2점, LAB에서 2.6–6.7%p가 추가로 향상됩니다. [p.9]
7. JobBench에서 축적한 경험을 WorkBuddy-Bench로 이전하면 Code·Web·Office 점수가 각각 0.6·0.5·2.9점 추가 상승하여 벤치마크 간 경험 전이의 가능성을 보여 줍니다. [p.11, Figure 7]
8. 다른 실행 모델에 개선된 하네스를 그대로 적용하거나 실행자와 편집자를 같은 모델로 설정해도 개선이 관찰됩니다. [p.11, Figure 8; p.24, Figure 12]
9. 다만 추가 계산비용, 후보당 한 번의 시험 실행, 제한적인 불확실성 보고, 잘못된 후보 선택과 공유된 오판 때문에 결과의 정확성과 새로운 과제로의 전이는 보장되지 않습니다. [pp.25–26, 29, 33–34]

> **용어 풀이**
> - **하네스(harness):** 모델이 일하는 방식을 정하는 지침·메모리·도구·스킬·작업 분배·실행 제어의 묶음.
> - **모델 가중치:** 학습 과정에서 조정되는 모델 내부의 수치 매개변수.
> - **재귀적 개선:** 이전 개선의 결과와 경험을 다음 개선의 입력으로 사용하는 과정.
> - **%p:** 두 백분율의 차이로, 59.6%에서 71.4%로 상승하면 11.8%p 향상.

## 2. 연구 배경, 목표와 필요성

### 2.1 해결하려는 문제

**[저자 보고]** 논문은 개방형 환경에서 하네스를 자동 개선할 때 발생하는 두 문제를 제시합니다. [p.2]

| 문제 | 기존 접근의 어려움 | 이 논문의 대응 |
|---|---|---|
| **정답 감독의 부재** | 새 과제에 정답·검증기·신뢰할 수 있는 점수가 없으면 수정이 실제로 도움이 되었는지 판단하기 어렵습니다. | 수정 전후의 실행 궤적과 산출물을 비교해 행동 변화를 관찰합니다. |
| **과제별 개선 경험의 낮은 재사용성** | 특정 과제에 맞춘 실행 하네스를 그대로 물려주면 새로운 요구에 맞지 않는 규칙도 전달될 수 있습니다. | 실행 하네스 자체와 함께, 무엇을 왜 수정했고 어떤 조건에서 효과가 있었는지를 저장합니다. |

> **용어 풀이**
> - **개방형 환경(open world):** 설계 시점에 모든 과제와 요구를 미리 알 수 없고, 배포 후 새로운 과제를 계속 만나는 환경.
> - **정답 검증기(ground-truth verifier):** 결과가 맞는지를 알려 주는 정답, 숨겨진 테스트, 채점 기준 등에 기반한 판정 장치.
> - **실행 궤적(trajectory):** 에이전트의 행동, 도구 호출, 관찰, 중간 결과가 시간순으로 기록된 자료.

### 2.2 연구 목적

저자의 중심 질문은 **“현재 하네스뿐 아니라, 미래의 하네스를 개선하는 방식도 개선할 수 있는가?”**입니다. 이를 위해 다음 두 대상을 구분합니다. [pp.2–4]

- **실행 하네스:** 현재 과제를 수행하는 에이전트의 작업 방식을 규정합니다.
- **개선 하네스:** 실행 하네스를 수정하는 과정에 필요한 과거 구성요소와 개선 경험을 제공합니다.

**[해석]** 연구의 중요한 선택은 과거의 최종 설정 전체를 자동 상속하지 않고, **재사용할 부품과 적용 조건을 현재 과제의 증거에 맞춰 다시 선택하게 하는 것**입니다. 이는 과제 간 차이를 고려하는 설계이지만, 그 자체로 잘못된 전이를 완전히 막는다는 증거는 아닙니다. [pp.5–7, 29]

### 2.3 연구의 필요성

**[저자 보고]** 코딩, 문서 작성, 법률 업무 등은 필요한 도구·검증 절차·산출물 형식이 서로 다르므로, 모든 상황에 맞는 하네스를 사람이 반복적으로 설계하는 데 공학적 노력이 듭니다. 이 논문은 이러한 조정을 추론 시점에 자동화하려 합니다. [pp.1–2]

**[해석]** 따라서 연구의 실용적 질문은 “모델을 다시 학습하지 않고도, 현재 가진 능력을 더 적절한 절차와 도구로 활용할 수 있는가?”입니다. 실제 사례에서 개선 대상은 입력 파일 간 대조 누락, 도구 호출 형식 오류, 생성 파일을 다시 열어 확인하지 않는 문제 등이었습니다. [pp.11–12, Figure 9; p.27, Figures 15–16]

> **용어 풀이 — 추론 시점 적응(test-time adaptation):** 모델을 실제 과제에 사용하는 동안, 현재 과제의 정보와 실행 경험으로 시스템의 동작을 조정하는 방식입니다.

## 4. 제안 방법과 모델·시스템 구조

### 4.1 새로운 신경망 구조보다 하네스 개선 시스템에 초점

**[저자 보고]** 기반 모델 $\mathcal M$의 가중치는 고정됩니다. 실행 에이전트는 모델과 하네스의 조합으로 정의됩니다. [p.3, §2.1]

$$
\mathcal H=(c_1,\ldots,c_K),\qquad
\mathcal A(\cdot;\mathcal M,\mathcal H),\qquad K=8.
$$

- $\mathcal M$: 가중치가 고정된 기반 모델.
- $\mathcal H$: 실행 하네스.
- $c_i$: 편집 가능한 $i$번째 구성요소.
- $K$: 구성요소 수로, 이 논문에서는 8.
- $\mathcal A$: 모델과 하네스로 구성한 실행 에이전트.
- $\cdot$: 에이전트가 받을 과제 입력의 자리.

**대문자 $K$는 구성요소 수이고, 이후의 소문자 $k$는 탐색 예산입니다.**

#### 여덟 가지 편집 구성요소

| 구성요소 | 활성화 방식 | 역할 |
|---|---|---|
| **C1 System prompt** | 매 모델 호출 | 역할과 전체 작업 절차를 정합니다. |
| **C2 Guardrails** | 매 모델 호출 | 과제 수행 중 지켜야 할 상시 제약을 제공합니다. |
| **C3 Memory** | 매 모델 호출 | 해당 영역에서 재사용할 사실을 제공합니다. |
| **C4 Tool guidance** | 매 모델 호출 | 기존 도구를 언제, 어떻게 사용할지 안내합니다. |
| **C5 Subagents** | 하위 작업 호출 시 | 별도 문맥에서 작업하고 결과를 반환합니다. |
| **C6 Skills** | 필요한 스킬을 호출할 때 | 특정 상황에 적용할 전문 작업 절차를 제공합니다. |
| **C7 Scripts** | 셸을 통해 실행 | 추출·계산·변환·검사 같은 작업을 코드로 처리합니다. |
| **C8 Plugin** | 도구 실행 루프 내부 | 도구 호출과 결과, 턴 경계에 개입합니다. |

**근거:** Figure 2, p.3; Table 5, p.22.

> **용어 풀이**
> - **문맥(context):** 모델이 현재 판단할 때 읽을 수 있는 지시문과 자료.
> - **스킬(skill):** 특정 조건에서 불러오는 작업 절차.
> - **스크립트(script):** 정해진 연산을 실행하는 프로그램.
> - **미들웨어·플러그인:** 모델의 문장 지시와 별도로 실행 과정에 개입하는 코드.

여기서 **C3 실행 메모리와 개선 하네스의 경험 라이브러리는 서로 다릅니다.** C3는 실행자가 읽는 구성요소이고, 경험 라이브러리는 편집자가 과거 하네스와 교훈을 찾아보는 저장소입니다. 새 과제는 초기 실행 하네스에서 출발하므로 이전 C3 파일도 무조건 상속되는 것은 아닙니다. [pp.7, 21–22, 31]

### 4.3 식 (1): Propose–Probe–Compose 개선 연산

실행 기록은 다음과 같습니다. [p.4]

$$
e=(\tau,y).
$$

- $e$: 하나의 실행 기록.
- $\tau$: 실행 궤적.
- $y$: 최종 산출물.

논문의 첫 번째 수식은 다음과 같습니다.

```math
(\mathcal H',e',\xi)
=
\Phi(q_t,\mathcal H,\mathcal E;\mathcal R_t).
```

- $q_t$: 현재 $t$번째 과제.
- $\mathcal H$: 수정할 현재 실행 하네스.
- $\mathcal E$: 현재 과제에서 축적한 실행·개선 이력.
- $\mathcal R_t$: 현재 과제에 적용되는 개선 하네스.
- $\Phi$: 제안·시험 실행·합성을 묶은 개선 연산.
- $\mathcal H'$: 개선 후 실행 하네스.
- $e'$: 개선 후 하네스를 실행한 기록.
- $\xi$: 기준 실행, 후보, 시험 결과, 합성 결정, 후속 실행을 담은 단계 기록.

**근거:** Eq.(1), p.4.

#### ① Propose — 수정 후보 제안

먼저 현재 하네스를 실행합니다. [p.5]

$$
e_0\sim\mathcal A(q_t;\mathcal M,\mathcal H).
$$

- $e_0$: 기준 실행 기록.
- $\sim$: 확률적인 에이전트 실행에서 하나의 결과를 얻는다는 의미.
- $\mathcal A$, $q_t$, $\mathcal M$, $\mathcal H$: 각각 실행 에이전트, 현재 과제, 고정 모델, 현재 하네스.

이 기록을 바탕으로 두 종류의 후보를 만듭니다.

- **Invariant 후보:** 계획, 도구 사용, 문맥 관리, 위임처럼 여러 영역에서 반복될 수 있는 작업 수행상의 문제를 수정합니다.
- **Domain-specific 후보:** 현재 전문 영역의 지식, 절차, 자료 해석, 산출물 요구를 수정합니다.

과거 구성요소를 재사용할 수 있지만, 과거 과제의 수치·매핑·조건을 현재 과제의 사실처럼 사용해서는 안 되며 현재 자료로 재확인해야 합니다. [p.5; pp.30–33, Prompts 1–2]

> **용어 풀이 — Invariant:** 여기서는 “영역이 달라도 반복될 수 있는 수행 방식”을 뜻하며, 수학적 불변성이 증명되었다는 의미는 아닙니다.

#### ② Probe — 후보를 실행하고 행동을 비교

각 후보를 **같은 과제, 같은 모델 및 환경 구성**에서 실행합니다. 비교 대상은 “정답 점수가 올랐는가”가 아니라, “목표한 실패 행동이 줄었는가, 그대로인가, 새로운 문제가 생겼는가”입니다. [p.5]

예를 들어 수정 전에는 출력 파일을 다시 열지 않았지만 수정 후에는 실제로 재개방·검사했다면, 절차 변화에 대한 관찰 근거가 됩니다. 그 검사가 정답을 완전히 보장하는 것은 별개의 문제입니다. [pp.11–12, Figure 9]

**후보당 시험 실행은 한 번입니다.** 부록 프롬프트도 단일 실행의 좋은 결과나 나쁜 결과는 약한 근거라고 명시합니다. [pp.33–34]

> **용어 풀이 — Rollout:** 에이전트가 한 과제를 시작해서 종료할 때까지 수행하는 한 차례의 실행입니다.

#### ③ Compose — 근거가 있는 수정의 선택적 합성

Composer는 후보 파일, 원래 하네스와의 변경점, 실행 기록을 읽고 다음 중 하나를 수행합니다. [p.5; pp.33–34]

- 서로 도움이 되는 수정들을 병합합니다.
- 충돌하는 수정들을 고칩니다.
- 후보 하나를 채택합니다.
- 근거가 부족하면 현재 하네스를 유지합니다.

합성된 하네스도 다시 실행하므로, 식 (1)은 실행하지 않은 제안만 반환하는 것이 아닙니다.

**[해석]** 이 과정은 행동 변화에 근거한 진단 절차입니다. 그러나 여러 구성요소가 동시에 바뀌고 후보 실행이 한 번뿐이므로, 특정 수정이 성능 향상의 원인이라는 엄밀한 인과 추정과는 구별해야 합니다. [pp.34, 36–37]

> **용어 풀이 — 인과 귀속:** 관찰된 결과 변화가 어떤 수정 때문에 발생했는지 판단하는 것입니다.

### 4.4 식 (2): 병렬 재귀

병렬 방식은 여러 후보를 탐색한 뒤 전체 증거를 공유하여 여러 후속 하네스를 합성합니다. [pp.5–6]

```math
\mathcal H'_j
=
\text{Compose}_j
(q_t,\mathcal H,\mathcal B,\mathcal P;\mathcal R_t),
\qquad j=1,\ldots,k.
```

- $k$: 병렬 탐색의 폭을 정하는 예산.
- $\mathcal B$: 기준 실행 $k$개의 집합.
- $\mathcal P$: 후보 하네스와 해당 실행 기록의 전체 묶음.
- $\text{Compose}_j$: $j$번째 독립 합성 세션.
- $\mathcal H'_j$: 해당 세션이 만든 후속 하네스.
- $q_t,\mathcal H,\mathcal R_t$: 현재 과제, 현재 실행 하네스, 현재 개선 하네스.

실행 순서는 **기준 실행 $k$개 → 범용 후보 $k$개와 영역 후보 $k$개 실행 → 전체 증거로 $k$개 하네스 합성 → 각각 실행**입니다. [p.6, Figure 4(a)]

**실제 구현은 한 번의 후보 집합 갱신입니다.** 따라서 병렬 $k=5$는 다섯 세대의 개선 깊이가 아니라 탐색 폭을 뜻합니다. [p.6]

---

### 4.5 식 (3): 순차 재귀

순차 방식은 앞 단계의 하네스와 이력을 다음 단계에 전달합니다.

```math
(\mathcal H^{(r)},e^{(r)},\xi^{(r)})
=
\Phi
(q_t,\mathcal H^{(r-1)},\mathcal E^{(r-1)};\mathcal R_t),
\qquad r=1,\ldots,k.
```

초기 실행 하네스는 다음과 같습니다.

$$
\mathcal H^{(0)}=\mathcal H_0.
$$

- $r$: 현재 개선 단계.
- $\mathcal H_0$: 모든 과제에서 출발점으로 사용하는 초기 하네스.
- $\mathcal H^{(r-1)}$: 직전 단계의 실행 하네스.
- $\mathcal E^{(r-1)}$: 직전 단계까지 누적된 실행·개선 이력.
- $\mathcal H^{(r)},e^{(r)},\xi^{(r)}$: 현재 단계의 하네스, 실행 기록, 개선 기록.
- $\Phi,q_t,\mathcal R_t,k$: 앞에서 정의한 개선 연산, 현재 과제, 개선 하네스, 단계 예산.

초기 이력에는 $k$개의 기본 실행이 포함되고, 이후 각 단계의 기록이 추가됩니다. 뒤 단계는 앞선 수정을 유지·수정·복원할 수 있습니다. $\mathcal R_t$는 현재 과제의 모든 단계에서 고정됩니다. [p.6, Eq.(3); p.34, Prompt 4]

#### 최종 선택

$k>1$에서는 선택자가 출처를 가린 기존 산출물을 요청과 원자료에 비추어 비교합니다. 새 내용을 생성하지 않고 하나를 선택하며, 기본 하네스의 산출물을 선택하는 것도 허용됩니다. $k=1$에서는 이 선택 단계를 생략합니다. [p.6; pp.35–36]

선택된 산출물의 하네스는 $\mathcal H_t^\star$로 표기하며, **별표는 ‘채택됨’을 뜻할 뿐 검증된 최적성을 뜻하지 않습니다.** [p.6]

### 4.6 식 (4): 개선 하네스 갱신

과제가 끝나면 전체 개선 기록을 검토하여 다음 과제에 사용할 경험을 축적합니다.

```math
\mathcal R_{t+1}
=
\text{Update}
(\mathcal R_t,\mathcal H_t^\star,\mathcal D_t).
```

- $\mathcal R_t$: 현재 개선 하네스.
- $\mathcal H_t^\star$: 현재 과제에서 채택된 실행 하네스.
- $\mathcal D_t$: 기준 실행, 후보 시험, 합성 결정, 최종 선택을 포함한 전체 개선 기록.
- $\text{Update}$: 기록을 검토하고 라이브러리를 갱신하는 연산.
- $\mathcal R_{t+1}$: 다음 과제의 개선에 사용할 하네스.

**근거:** Eq.(4), p.7.

라이브러리는 실행 가능한 하네스와 `EXPERIENCE.md`, 검색을 위한 인덱스를 보관합니다. 경험에는 적용 상황, 수행할 수정, 그 판단의 근거가 들어갑니다. [pp.7, 21]

Reflector는 수정 효과를 `helped`, `hurt`, `no observed effect`, `confounded`로 구분하고, 근거가 부족하면 새 경험을 남기지 않는 `NO_ENTRY`를 허용합니다. 과제별 영속 경험은 최대 하나입니다. [pp.36–37]

> **용어 풀이 — Confounded:** 여러 변화가 함께 일어나거나 실행 변동이 커서, 어떤 수정의 효과인지 분리하기 어려운 상태입니다.

**수식 해석의 한계:** 네 수식은 알고리즘의 입출력과 상태 갱신을 설명합니다. 논문은 별도의 학습 손실함수, 경사 업데이트, 수렴 정리, 일반화 오차 상한을 제시하지 않습니다. [pp.3–7]

### 5.3 어떤 요소가 기여했는가?

#### 개선 과정의 구성요소

Gemini/OpenCode, $k=1$의 결과입니다. [p.10, Table 3]

| 조건 | WorkBuddy | JobBench |
|---|---:|---:|
| 전체 Harness² | **77.5** | **36.0** |
| 경험 라이브러리 제거 | 74.4 | 34.2 |

**[해석]** 경험 축적만으로 모든 효과가 설명되지는 않습니다. 역할 분리와 합성도 각각 평균 점수에 기여합니다. 다만 표에 불확실성 정보가 없어 기여 크기의 정밀한 순위를 확정하기는 어렵습니다.

#### 실행 하네스의 구성요소

이미 개선된 $k=5$ 하네스에서 부품을 제거하면 평균 점수는 다음과 같이 낮아집니다. [p.23, Table 6]

- 스킬 제거: **80.8→75.5, −5.3점**.
- 스크립트 제거: **80.8→77.1, −3.7점**.
- 프롬프트 관련 그룹 제거: **80.8→79.3, −1.5점**.
- Office에서는 스크립트 제거의 손실이 **7.4점**으로 큽니다.

**이 결과는 “스킬만 추가하면 5.3점 오른다”는 뜻이 아닙니다.** 이미 함께 최적화된 구성요소를 제거한 실험이며, 제거 후 개선 과정을 다시 수행하지 않았습니다. 저자도 가산적 효과는 입증하지 않는다고 명시합니다. [p.23]

### 5.4 도구 사용과 효율성

**[저자 보고]** JobBench의 도구 오류율은 **14.4%→9.1%**로 감소하지만, 도구 호출 수는 **27.4→32.8회**로 증가합니다. LAB에서도 오류율은 낮아지지만 호출 수는 증가합니다. [p.25, Table 7]

**[해석]** 성능 향상은 단순히 일을 적게 하거나 실행을 짧게 만든 결과만은 아닙니다. 필요한 확인 작업을 더 수행하면서 오류를 줄이는 경우도 있습니다.

## 6. 일반화 성능 향상 가능성: 무엇이 입증되었는가?

### 6.1 일반화의 대상을 먼저 구분해야 한다

이 논문에는 서로 다른 두 종류의 재사용이 있습니다. [pp.7, 11, 24]

1. **실행 하네스 전이:** 이미 만든 작업 절차·도구·스킬을 다른 실행 모델에 적용합니다.
2. **개선 경험 전이:** 과거 수정의 조건과 근거를 다른 과제의 하네스 편집에 사용합니다.

**[해석]** 모델 가중치가 고정되어 있으므로, 관측된 향상은 **모델·하네스·경험 상태가 결합된 시스템의 적응 및 전이 성능**입니다. 모델 자체의 학습된 표현이 더 일반화되었다고 볼 근거는 없습니다.

### 7.3 Figure 6의 비용 주장은 어디까지 유효한가?

**[저자 보고]** Figure 6은 최종 제출 전 사용한 전체 토큰으로 실행과 개선 비용을 비교합니다. Gemini/OpenCode의 Harness² $k=1$과 $k=5$는 관측된 비교 설정에서 파레토 경계에 놓입니다. [p.10]

> **용어 풀이 — 파레토 경계:** 비교한 선택지 중에서 비용과 성능을 함께 고려할 때 다른 선택지에 의해 명백히 압도되지 않는 조합들의 집합입니다.

**[해석]** 이는 해당 토큰 집계와 실험 설정에서의 결과입니다. 다음 사항은 충분히 명시되지 않아 실제 배포에서 항상 가장 저렴하다고 결론낼 수 없습니다.

- Meta-Harness의 오프라인 탐색 비용을 몇 개의 배포 과제에 나누어 계산했는지.
- 모델별 입력·출력·캐시 토큰을 실제 금액이나 지연시간으로 어떻게 환산할지.
- 산출물 제출 후 수행하는 경험 정리 비용이 어떻게 집계되었는지. [pp.6–7, 10, 20]

### 7.4 저자가 직접 명시한 한계

Appendix F는 다음을 명시합니다. [p.29]

1. 추가 실행과 편집 세션 때문에 추론 비용이 증가합니다.
2. 병렬화는 자원이 충분할 때 지연을 줄일 수 있지만 총계산량을 없애지는 않습니다.
3. 제한된 예산 범위만 평가했으며 보편적인 최적 자원 배분은 제시하지 않습니다.
4. 행동 대조와 모델 판단은 실행 변동과 공유된 모델 편향에 민감합니다.
5. 채택된 수정의 정확성이나 다른 과제로의 전이는 보장되지 않습니다.

## 12. 결론, 시사점과 후속 연구

### 12.1 저자가 제시한 결론과 시사점

**[저자 보고]** 현재 과제의 하네스 개선에서 얻은 결과를 다음 개선에 재사용하면, 개별 과제에만 머물던 조정을 지속적인 추론 시점 적응의 기반으로 만들 수 있다는 것이 논문의 결론입니다. 세 벤치마크, 두 실행 모델, 두 초기 하네스의 결과와 절제·전이 실험이 이를 뒷받침한다고 주장합니다. [p.13, §6]

**[해석: 학계]** 이 연구는 일반화의 평가 대상을 모델 가중치에 한정하지 않고, **실행 가능한 절차와 개선 경험이 새로운 적응을 돕는가**로 확장합니다. 앞으로는 실행 하네스의 전이와 개선 경험의 전이를 별도 실험으로 평가하는 것이 중요합니다. [pp.7, 11, 24]

**[해석: 실용 분야]** 입력 자료 대조, 출력 파일 재검사, 도구 사용 방식처럼 관찰 가능한 절차적 실패를 수정하는 접근이 구체적인 활용 지점을 제공합니다. 다만 추가 탐색 비용과 성능 하락 사례가 있으므로, 실제 가치는 평균 점수와 함께 비용·회귀율·산출물 사용성을 평가해야 합니다. [Figures 9, 14; Tables 6–7]

### 12.2 저자의 후속 연구 계획

Appendix G의 계획은 두 가지입니다. [p.29]

- **경험 저장소 관리:** 중복 구성요소 통합, 오래된 경험 수정, 현재 과제와 증거에 맞춘 검색 개선.

### 12.3 추가 후속 연구 방향

다음은 **분석자의 제안**이며, 성과가 이미 확인되었다는 뜻은 아닙니다.

**첫째, 일반화의 평가를 더 엄격하게 분리할 필요가 있습니다.** 경험을 만든 과제와 대상 과제를 분리하고, 여러 전이 방향·새로운 전문 영역·시간에 따라 요구가 달라지는 스트림에서 평가해야 합니다. 현재의 JobBench→WorkBuddy 전이와 모델 교체 실험이 제공하는 근거를 확장하는 방법입니다. [Figures 7, 12]

**둘째, 개선 경험의 신뢰도를 측정해야 합니다.** 후보 반복 실행, 구성요소별 통제, 독립 평가자를 통해 “도움이 되었다”고 저장한 경험이 실제로 얼마나 정확한지 확인할 수 있습니다. 이는 Figure 14의 잘못된 가정 전파와 부록의 `confounded` 문제를 직접 다룹니다. [pp.26, 36–37]

**셋째, 경험 저장의 장기 이득과 비용을 함께 평가해야 합니다.** 라이브러리 크기 증가에 따른 검색비용, 오래된 정보의 영향, 다른 과제에 해를 주는 전이, 현재 탐색이 미래 성능에 주는 이득을 함께 측정해야 합니다. [p.29]

> **용어 풀이 — 음의 전이(negative transfer):** 이전 경험을 활용했기 때문에 새로운 과제의 성능이 오히려 나빠지는 현상입니다.

**최종 평가:** Harness²는 **과제별 실행 개선을 재사용 가능한 개선 경험으로 바꾸는 시스템 설계**에 대해 유의미한 실험 근거를 제공합니다. 일반화에 대한 가장 직접적인 긍정적 증거는 벤치마크 간 경험 전이와 모델 간 하네스 전이입니다. 다만 현재 근거가 지지하는 결론은 **평가된 조건에서의 적응·전이 개선**까지이며, 기반 모델의 내재적 일반화 향상, 장기적인 안정적 자기개선, 임의의 새로운 환경에서의 성능 보장은 남아 있는 연구 과제입니다. [pp.11, 24, 29]
