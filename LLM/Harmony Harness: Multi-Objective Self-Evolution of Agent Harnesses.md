# Harmony Harness: Multi-Objective Self-Evolution of Agent Harnesses

**핵심 판단:** 이 논문은 **기능성과 보안을 함께 평가하면서 에이전트의 실행 구조를 개선하면, 다른 보안 코딩 과제로의 전이 성능도 높아질 수 있다**는 경험적 근거를 제시합니다.  
가장 중요한 기여는 다목적 탐색, 일반·환경 특화 구성요소의 분리, 과제별 동적 실행을 결합한 데 있습니다.  
다만 실험이 입증하는 범위는 **하네스를 포함한 시스템의 일반화**이며, 기반 언어모델의 가중치나 내부 표현이 개선되었다는 결과는 아닙니다. *(pp. 4–11, Tables 9–12)*

> **용어 — 하네스(harness):** 언어모델을 둘러싼 시스템 프롬프트, 도구, 실행 반복문, 검증 절차, 오류 복구, 작업 순서를 묶은 소프트웨어.

## 1. Executive summary — 9문장

1. Harmony Harness는 보안 코드 생성 에이전트의 하네스를 실행 피드백에 따라 자동 수정하여 **기능성과 보안을 동시에 개선**하는 프레임워크입니다. *(pp. 1–4)*
2. 서로 다른 목표 선호도를 가진 하위 문제들을 함께 탐색하는 MOEA/D 방식으로, 기능성과 보안을 하나의 전역 점수로 합쳤을 때 생기는 문제를 다룹니다. *(pp. 5–6)*
3. 하네스를 도구·스킬·제어 논리로 나누고 각 변경을 일반 범위와 환경 특화 범위에 배치하며, 실행 시에는 현재 과제에 맞는 작업 흐름을 구성합니다. *(pp. 7–8, Figure 1)*
4. SecRepoBench에서 기능·보안 공동 성공률은 미사용 동일 분포 평가에서 기준 하네스의 **50.0%에서 86.7%**, 분포 외 평가에서 **36.7%에서 66.7%**로 높아졌습니다. *(p. 29, Table 9)*
5. BaxBench에서도 공동 성공률이 동일 분포 평가에서 **42.9%에서 62.4%**, 분포 외 평가에서 **42.9%에서 53.6%**로 높아졌습니다. *(p. 29, Table 10)*
6. 추가 진화 없이 다른 벤치마크로 옮겼을 때 공동 성공률은 SecRepoBench→BaxBench에서 **57.1%**, 반대 방향에서 **70.0%**였습니다. *(p. 30, Table 12)*
7. CWEval 357개 인스턴스로 전이한 결과 공동 성공률은 **73.1%에서 87.4%**로 높아졌지만, 기능 성공률은 **91.9%에서 89.9%**로 낮아졌습니다. *(pp. 10–11, Table 11)*
8. 제거 실험은 다목적 선택 규칙뿐 아니라 구성요소 분리와 동적 실행도 성능에 기여한다는 결과를 제시합니다. *(pp. 24, 28, Tables 5, 7–8)*
9. 주 실험의 작은 과제 수, 3회 평균만 제시한 성능표, 일부 불완전한 보고를 고려하면, 이 연구는 하네스 일반화의 유망한 증거를 제공하지만 통계적 유의성이나 광범위한 안전성을 확정하지는 못합니다. *(pp. 18, 28–29, 37–40)*

> **용어**
>
> - **MOEA/D:** 여러 목표의 최적화를 서로 다른 선호도를 가진 작은 문제들로 분해하여 함께 탐색하는 진화 알고리즘.
> - **동일 분포(ID):** 탐색 때와 유사한 유형에서 뽑았지만 탐색에는 사용하지 않은 평가 과제.
> - **분포 외(OOD):** 탐색 때와 다른 유형이나 분포에 속하는 평가 과제.
> - **공동 성공률:** 하나의 생성 결과가 기능 검사와 보안 검사를 모두 통과한 비율.

## 2. 연구 배경, 해결하려는 문제, 목적과 필요성

### 2.1 해결하려는 문제

**[저자 보고] 첫 번째 문제는 기능 개선과 보안 개선이 자동으로 함께 일어나지 않는다는 점입니다.**  
기능 테스트를 더 잘 통과하도록 하네스를 진화시켜도 보안은 거의 개선되지 않거나, 새로운 과제에서는 오히려 악화될 수 있습니다.  
반대로 보안 검사를 통과하려고 필요한 기능을 제한하면 기능 정확도가 떨어질 수 있습니다. *(pp. 1–2)*

**두 번째 문제는 하네스 전체를 한 덩어리로 수정하면 재사용 가능한 개선과 벤치마크에만 통하는 요령이 섞인다는 점입니다.**  
예를 들어 컨테이너 안에서 코드를 빌드하고 검증하는 능력은 여러 환경에서 유용하지만, 특정 이미지 이름이나 특정 테스트 실행기의 출력 형식을 가정하는 부분은 환경에 종속됩니다.  
기존의 통합 수정 방식에서는 두 종류의 변경이 같은 보상을 받고 같은 코드에 들어갈 수 있습니다. *(p. 2)*

**세 번째 문제는 하네스의 다양성을 코드 모양만으로 판단하기 어렵다는 점입니다.**  
프롬프트 문구를 크게 바꿔도 행동은 같을 수 있고, 검증 단계 하나를 추가하는 작은 코드 변경이 행동을 크게 바꿀 수도 있습니다. *(pp. 2, 6)*

> **용어 — 단일 목적 최적화:** 하나의 점수를 최대화하는 탐색.  
> **다목적 최적화:** 여러 목표를 별도로 유지하면서 목표 사이의 관계를 탐색하는 방식.  
> **단일체적 수정(monolithic rewriting):** 여러 구성요소를 구분하지 않고 하네스 전체를 하나의 수정 대상으로 취급하는 방식.

## 5. 제안 방법과 구조: 수식 중심 설명

### 5.1 무엇을 최적화하는가?

과제 집합과 실행 경로는 다음과 같이 정의됩니다. *(p. 3)*

$$
\mathcal D=\{t_n=(x_n,p_n)\}_{n=1}^{M},
\qquad
\tau\sim P_H(\tau\mid x_n).
$$

- $H\in\mathcal H$: 하나의 하네스와 가능한 하네스들의 공간.
- $M$: 평가 과제 수.
- $n$: 과제 번호.
- $x_n$: 에이전트에게 제공되는 과제 명세.
- $p_n$: 해당 과제의 보안 정책 또는 공격 검사.
- $\tau$: 생성 코드와 도구 호출 등을 포함한 실행 경로.
- $P_H$: 하네스 $H$로 실행할 때 가능한 경로들의 확률분포.

**보안 정책 $p_n$은 과제 해결 시 에이전트에게 직접 공개되지 않고, 평가 단계에서 사용됩니다.** *(p. 3)*

#### ① 기능 성공률과 보안 성공률

원문의 식 (9), (10)은 다음과 같습니다. *(p. 16)*

```math
f_{\text{func}}(H)
=
\frac{1}{M}
\sum_{n=1}^{M}
\mathbb E_{\tau\sim P_H(\cdot\mid x_n)}
\left[F(\tau,x_n)\right].
```

```math
f_{\text{sec}}(H)
=
\frac{1}{M}
\sum_{n=1}^{M}
\mathbb E_{\tau\sim P_H(\cdot\mid x_n)}
\left[S(\tau,p_n)\right].
```

- $F(\tau,x_n)\in\{0,1\}$: 해당 실행의 결과가 기능 테스트를 통과했는지.
- $S(\tau,p_n)\in\{0,1\}$: 해당 실행의 결과가 지정된 공격을 막았는지.
- $\mathbb E$: 확률적인 실행 결과에 대한 평균.
- $f_{\text{func}},f_{\text{sec}}$: 각각 최대화할 기능성과 보안성의 평균 성공률.

**여기서 보안 성공은 시험에 포함된 공격에 대한 성공을 뜻합니다. 모든 가능한 취약점이 제거되었다는 정의는 아닙니다.**

#### ② 실제 표본으로 추정한 성공률

원문의 식 (11)입니다. *(p. 16)*

```math
\widehat f_{\text{func}}(H)
=
\frac{1}{MK}
\sum_{n=1}^{M}
\sum_{k=1}^{K}
F(\tau_{n,k},x_n),
```

```math
\widehat f_{\text{sec}}(H)
=
\frac{1}{MK}
\sum_{n=1}^{M}
\sum_{k=1}^{K}
S(\tau_{n,k},p_n).
```

- $\widehat f$: 표본 실행으로 계산한 추정치.
- $K$: 과제 하나에서 표본화한 실행 경로 수.
- $k$: 실행 표본 번호.
- $\tau_{n,k}$: 과제 $n$의 $k$번째 실행 경로.

두 값 모두 $[0,1]$ 범위이므로 별도의 척도 정규화를 하지 않습니다. **수식의 $K$와 “3회 독립 실험 평균”은 원문에서 별도로 설명되므로 자동으로 같은 것으로 간주하면 안 됩니다.**

#### ③ 최종 성능 지표: 같은 실행에서 둘 다 성공

주요 보고 지표는 원문의 식 (1)입니다. *(p. 3)*

```math
f_{\wedge}(H)
=
\frac{1}{M}
\sum_{n=1}^{M}
\mathbb E_{\tau\sim P_H(\cdot\mid x_n)}
\left[
F(\tau,x_n)S(\tau,p_n)
\right].
```

- $f_{\wedge}$: 기능과 보안을 동시에 만족하는 비율.
- 이진 값의 곱 $FS$: 두 검사에 모두 성공했을 때만 1.

논문에서는 이를 **F&S 또는 secure-pass@1**이라고 부릅니다. 두 성공률의 평균이나 단순한 주변 확률의 곱과는 다릅니다.

기능·보안 성공률과 공동 성공률 사이에는 다음 관계가 있습니다. 원문의 식 (2)입니다. *(p. 4)*

```math
\max\left\{
0,\,
f_{\text{func}}(H)+f_{\text{sec}}(H)-1
\right\}
\le
f_{\wedge}(H)
\le
\min\left\{
f_{\text{func}}(H),f_{\text{sec}}(H)
\right\}.
```

> **용어 — 주변 확률:** 다른 사건과 함께 일어나는지를 따지지 않은 개별 사건의 확률.  
> **Fréchet 경계:** 두 사건의 개별 확률만 알 때, 두 사건이 함께 일어날 확률의 가능한 최솟값과 최댓값.

**[저자 보고] 탐색은 공동 성공률 자체보다 두 개별 성공률을 최적화합니다.** 개별 점수를 유지하면 제안자에게 기능과 보안 중 무엇이 실패했는지 알려줄 수 있기 때문입니다. 동시에 저자들은 **두 주변 성공률의 개선만으로 실제 공동 성공률의 개선이 보장되지는 않는다**고 인정합니다. *(pp. 3–4)*

### 5.2 파레토 최적성과 다목적 탐색

하네스 $H$가 $H'$보다 모든 목표에서 같거나 좋고, 적어도 하나에서 더 좋으면 $H$가 $H'$를 지배한다고 정의합니다. 원문의 식 (12)은 지배되지 않는 하네스의 집합입니다. *(p. 16)*

```math
\mathcal P^*
=
\left\{
H\in\mathcal H:
\nexists H'\in\mathcal H
\text{ such that }H'\succ H
\right\}.
```

- $\succ$: 파레토 지배 관계.
- $\mathcal P^*$: 다른 후보에 의해 지배되지 않는 하네스 집합.

> **용어 — 파레토 최적:** 한 목표를 더 개선하려면 다른 목표의 손해를 감수해야 하는 상태.  
> **파레토 프런티어:** 이러한 후보들의 목적값을 모은 경계.

#### ① 여러 목표 선호도 유지

논문은 다음 가중치 집합을 사용합니다. *(p. 5)*

```math
\Lambda
=
\{\boldsymbol\lambda^1,\ldots,\boldsymbol\lambda^N\},
\qquad
\lambda_j^i\ge0,
\qquad
\sum_{j=1}^{m}\lambda_j^i=1.
```

- $N$: 하위 문제 수이자 유지하는 대표 하네스 수.
- $m=2$: 기능성과 보안성.
- $i$: 하위 문제 번호.
- $j$: 목표 번호.
- $\lambda_j^i$: 하위 문제 $i$가 목표 $j$에 부여한 가중치.
- $H_i$: 하위 문제 $i$가 현재 유지하는 하네스.

각 하위 문제는 다른 선호도를 갖습니다. 따라서 모든 후보를 하나의 전역 점수로만 경쟁시키지 않습니다.

#### ② 관측 이상점과 Tchebycheff 목적함수

지금까지 평가한 후보에서 목표별 최고값을 모아 이상점을 만듭니다.

```math
z_j^*
=
\max_{H:\,\text{evaluated}}
\widehat f_j(H).
```

원문의 식 (4)는 다음과 같습니다. *(p. 5)*

```math
g^{\text{te}}
\left(H\mid\boldsymbol\lambda^i,\mathbf z^*\right)
=
\max_{j\in\{1,\ldots,m\}}
\left\{
\lambda_j^i
\left|
z_j^*-\widehat f_j(H)
\right|
\right\}.
```

- $\mathbf z^\*=(z_1^*,\ldots,z_m^\*)$: 목표별 관측 최고값을 모은 기준점.
- $\widehat f_1=\widehat f_{\text{func}}$, $\widehat f_2=\widehat f_{\text{sec}}$.
- $g^{\text{te}}$: 목표별 **가중 부족분 중 가장 큰 값**.
- 값이 작을수록 해당 하위 문제에서 좋은 후보입니다.

> **용어 — 이상점(ideal point):** “지금까지 본 최고 기능성”과 “지금까지 본 최고 보안성”을 합친 기준점. 한 하네스가 두 값을 동시에 달성했을 필요는 없습니다.  
> **Tchebycheff 스칼라화:** 여러 목표의 부족분 가운데 가장 큰 것을 줄이는 방식. 여기서는 하위 문제마다 서로 다른 가중치를 적용합니다.

개념적인 최적 하네스는 원문의 식 (5)로 표현됩니다.

```math
H_i^*
=
\underset{H\in\mathcal H}{\text{arg\,min}}
\;
g^{\text{te}}
\left(H\mid\boldsymbol\lambda^i,\mathbf z^*\right).
```

$H_i^*$는 이론적으로 가장 좋은 해를 나타냅니다. 실제로는 유한한 탐색으로 그 근사인 $H_i$를 유지합니다.

#### ③ 이웃을 통한 후보 공유와 교체

가중치가 가까운 $T$개 하위 문제를 $B(i)$라는 이웃으로 묶습니다. 기본적으로 자신의 하네스 하나를 수정해 자식 후보를 만들고, 탐색이 정체되면 적합한 이웃을 부모로 사용할 수 있습니다. 제안자는 한 번에 부모 저장소 하나만 받습니다. *(p. 6)*

자식 $H_c$를 평가하고 이상점을 갱신한 뒤, 원문의 식 (6)으로 교체합니다.

```math
H_l\leftarrow H_c
\quad\text{if}\quad
g^{\text{te}}
\left(H_c\mid\boldsymbol\lambda^l,\mathbf z^*\right) < g^{\text{te}}
\left(H_l\mid\boldsymbol\lambda^l,\mathbf z^*\right),
\qquad l\in B(i).
```

- $H_c$: 새로 만든 자식 하네스.
- $l$: 이웃 하위 문제 번호.
- $H_l$: 해당 이웃의 기존 하네스.
- $T$: 이웃 크기.
- 한 자식이 교체할 수 있는 하네스 수는 최대 $n_r=2$입니다.

**[분석: 수학적으로 주의할 대목]** 부록 D는 다른 목표를 희생하는 후보가 받아들여지지 않는다는 취지로 설명하지만, 식 (4)와 (6)이 요구하는 조건은 **최대 가중 부족분의 감소**입니다. 모든 목표의 개별 비감소 조건은 없습니다. 따라서 이 규칙을 **보안 퇴행을 절대 금지하는 장치**로 해석하면 안 됩니다. *(p. 18과 식 (4), (6)의 대조)*

또한 동일 가중치가 항상 “현재 성공률이 더 낮은 목표”를 개선하는 것은 아닙니다. 실제 검색에서는 **관측 이상점 대비 부족분**을 비교합니다. 기준점이 두 축 모두 1인 경우에만 낮은 성공률을 우선하는 설명과 정확히 일치합니다.

#### ④ 최종 배포 하네스 선택

탐색 후에는 원문의 식 (3)으로 하나를 선택합니다. *(p. 4)*

```math
H^\dagger
=
\underset{H\in\mathcal U}{\text{arg\,max}}
\;
\min
\left\{
\widehat f_{\text{func}}(H),
\widehat f_{\text{sec}}(H)
\right\},
\qquad
\mathcal U=\bigcup_g\mathcal U_g.
```

- $\mathcal U_g$: 세대 $g$에서 평가한 자식 후보 집합.
- $\mathcal U$: 모든 세대에서 평가한 자식 후보 전체.
- $H^\dagger$: 약한 쪽의 성공률이 가장 높은, 즉 가장 균형적인 후보.

선택에는 탐색 분할만 사용하며, 동률이면 더 이른 세대의 후보를 고릅니다. 마지막 세대에 남아 있지 않은 후보도 선택될 수 있습니다. **공동 성공률이 가장 높은 후보를 직접 고르는 규칙은 아닙니다.**

### 5.3 하네스를 어떻게 분해하여 수정하는가?

이 논문의 구조는 신경망 층의 분할이 아니라 **소프트웨어 수정 대상과 적용 범위의 분할**입니다. 전체 하네스는 독립적인 Python 패키지이며, 평가기는 `AgentHarness` 진입점을 사용합니다. *(p. 19, Figure 4)*

| 구성요소 | 역할 | 수정 연산자 |
|---|---|---|
| 도구 | 파일·셸·컨테이너 실행, 검증 결과 수집과 전달 | `tool_evolve` |
| 스킬 | 발동 조건과 절차를 가진 재사용 지식·작업 지침 | `skill_evolve` |
| 제어 논리 | 실행 단계, 분기, 반복 횟수, 검증 순서, 작업 흐름 | `logic_evolve` |

*근거: p. 7, p. 21, Table 4.*

각 구성요소는 다시 **일반 범위**와 **환경 특화 범위**로 나뉩니다.

- 일반 범위에는 다른 환경에서도 사용할 수 있는 메커니즘을 둡니다.
- 환경 특화 범위에는 평가 환경이나 실행 채널에 고유한 규칙을 둡니다.
- 범위 밖 파일 수정은 도구 수준의 쓰기 허용 목록으로 차단하거나 되돌립니다. *(pp. 20–21)*

> **용어 — 귀납적 편향(inductive bias):** 탐색이 특정 종류의 해를 더 쉽게 찾도록 구조를 정하는 설계상의 가정. 여기서는 일반성과 환경 의존성을 분리하도록 유도하는 것이 이에 해당합니다.

진단과 수정 과정은 다음과 같습니다. *(p. 7, 식 (7) 및 주변 설명)*

$$
d_i=Q(\mathcal E_i),
\qquad
h_i=G(d_i,\boldsymbol\lambda^i),
\qquad
k_i=\pi_{\text{comp}}(h_i)\in\mathcal K.
$$

$$
s_i=R_{k_i}(H_i,h_i)\in\Sigma,
\qquad
H_c=\mathcal O_{k_i,s_i}(H_i;h_i).
$$

- $\mathcal E_i$: 부모 하네스의 실제 실행 피드백.
- $Q,d_i$: 실패 진단 과정과 그 결과.
- $G,h_i$: 개선 가설 생성 과정과 가설.
- $\mathcal K=\{\text{tools},\text{skills},\text{logic}\}$.
- $\pi_{\text{comp}},k_i$: 수정할 구성요소를 고르는 과정과 선택 결과.
- $\Sigma=\{\text{gen},\text{env}\}$.
- $R_{k_i},s_i$: 해당 변경의 적용 범위를 정하는 과정과 결과.
- $\mathcal O_{k_i,s_i}$: 정해진 구성요소·범위 안에서 코드를 바꾸는 연산자.

범위 선택의 실무적 질문은 **“필요한 사실을 에이전트가 실행 중 스스로 알아낼 수 있는가?”**입니다. 알아낼 수 있다면 일반 코드에서 실행 중 확인하도록 하고, 환경 자체의 고유 규칙이라면 환경 특화 영역에 둡니다. *(pp. 20–21)*

#### `generalize` 연산자의 역할

| 동작 | 문제 | 처리 |
|---|---|---|
| **Promote** | 재사용 가능한 절차가 환경 전용 영역에 묶여 있음 | 일반 영역으로 옮기고 환경 정보는 실행 중 구하도록 변경 |
| **Demote** | 일반 영역에 실행 중 알 수 없는 환경 전용 사실이 들어 있음 | 해당 사실을 환경 특화 설정이나 구성요소로 이동 |
| **Derive** | 일반 영역의 하드코딩 정보를 실행 중 알아낼 수 있음 | 일반 영역에 남기되 실행 중 도출하도록 변경 |

*근거: p. 22.*

저자는 이 연산자가 새로운 기능을 추가하기보다 **기존 기능의 잘못된 배치와 환경 의존성을 교정**한다고 설명합니다. 현재 벤치마크에서의 행동 동등성과 일반 영역만으로 실행 가능함을 요구하지만, 이것이 모든 변경에 대한 형식적 증명을 뜻하지는 않습니다.

#### 여러 연산자의 순차 적용

원문의 식 (13), (14)입니다. *(p. 22)*

$$
\Pi=(\mathcal O_1,\ldots,\mathcal O_L),
$$

$$
\mathcal O_\ell
\in
\{\mathcal O_{k,s}:k\in\mathcal K,\ s\in\Sigma\}
\cup
\{\mathcal O_{\text{generalize}}\}.
$$

```math
H_c^{(0)}=H_i,
\qquad
H_c^{(\ell)}
=
\mathcal O_\ell
\left(H_c^{(\ell-1)};h_i\right),
\quad
\ell=1,\ldots,L.
```

- $\Pi$: 제안자가 정한 수정 연산자 순서.
- $L$: 수정 단계 수.
- $\ell$: 현재 수정 단계.
- $H_c^{(\ell)}$: $\ell$번째 수정까지 반영된 후보.

후속 연산자는 앞선 수정 결과를 보고 작업하며, 마지막 결과만 전체 과제 평가에 들어갑니다. 자동 연산자 계획은 구현상 최대 8단계입니다. *(pp. 20, 22)*

### 5.4 실행 시 동적 조합

일반 구성요소와 환경 특화 구성요소의 풀은 원문의 식 (15)로 표현됩니다. *(p. 24)*

```math
\mathcal H^{\text{gen}}
=
\bigcup_{k\in\mathcal K}
\mathcal H_k^{\text{gen}},
\qquad
\mathcal H_e^{\text{env}}
=
\bigcup_{k\in\mathcal K}
\mathcal H_{k,e}^{\text{env}}.
```

- $\mathcal H_k^{\text{gen}}$: 구성요소 종류 $k$의 일반 구현 집합.
- $\mathcal H_{k,e}^{\text{env}}$: 환경 $e$에 특화된 종류 $k$의 구성요소 집합.

현재 환경과 과제에 맞는 실행 그래프를 만드는 식은 원문의 식 (8)입니다. *(p. 8)*

```math
A_{e,x}
=
\pi_\phi
\left(
e,x,\mathcal H^{\text{gen}},\mathcal H_e^{\text{env}}
\right),
\qquad
H^{(e,x)}=\mathcal C(A_{e,x}).
```

- $e$: 현재 실행 환경.
- $x$: 현재 과제.
- $\pi_\phi$: 구성 정책을 수행하는 LLM 계획자.
- $A_{e,x}$: 현재 과제에서 활성화할 단계·도구·스킬을 담은 DAG.
- $\mathcal C$: 그래프를 검사하고 실행하는 절차.
- $H^{(e,x)}$: 해당 과제에서 실제 실행되는 하네스.

> **용어 — DAG:** 방향을 따라 이동했을 때 원래 지점으로 되돌아오는 순환이 없는 작업 그래프. 병렬 검사와 조건부 실행, 순서가 있는 여러 차례의 수정 단계를 표현할 수 있습니다.  
> **오케스트레이션:** 여러 도구와 작업 단계를 어떤 순서와 조건으로 실행할지 조정하는 것.

구성 에이전트는 이미 진화한 구성요소를 다시 수정하지 않고 **어떤 구성요소를 어떤 흐름으로 사용할지 선택**합니다. 새로운 환경으로 전이할 때는 원래 벤치마크 전용 영역을 로드하지 않으며, 새로운 환경의 특화 영역도 없으므로 일반 영역만 사용합니다. *(pp. 23–24)*

### 5.5 검증, 복구, 과적합 판별

자식 후보는 전체 벤치마크 실행 전에 다음 검사를 거칩니다. *(p. 23)*

1. 모든 모듈이 불러와지고 평가 인터페이스가 유지되는지 확인.
2. 가짜 모델·환경을 이용해 기본 도구 호출과 파일 수정이 가능한지 확인.
3. 부모의 자체 검사 삭제 여부와 함수 호출·정의의 일치 여부를 정적 검사.

실패하면 한 차례 수리하고 다시 검사하며, 재실패하면 부모 상태로 되돌립니다.

> **용어 — 스모크 테스트:** 최소한의 실행 가능성을 빠르게 확인하는 검사.  
> **AST:** 코드를 문법 구조의 트리로 표현한 것. 실제 실행 없이 일부 구조적 오류를 검사하는 데 사용합니다.

별도로 LLM 판별기가 코드 변경의 과적합 위험을 평가합니다. *(p. 37, 번호 없는 정의)*

$$
\rho(\delta)\in[0,1],
\qquad
\text{reject if }\rho(\delta)>\theta.
$$

- $\delta$: 부모에서 자식으로의 코드 변경.
- $\rho(\delta)$: 판별기가 추정한 과적합 위험.
- $\theta$: 거부 임계값.

**[분석] 이 게이트의 실제 효과는 정량적으로 확정할 수 없습니다.** 원문은 보정 실험 설계를 제시하지만, 실제 임계값·검출률·오탐률·검정 결과를 제시하지 않습니다. 이 문제는 아래 통계 검토에서 다시 구분합니다.

## 7. 통계적 취약점, 비교 불가능한 수치, 보고상의 공백

### 7.1 통계적으로 취약한 부분

| 항목 | 원문에서 확인한 사실 | 해석에 미치는 영향 |
|---|---|---|
| 작은 평가 집합 | 분할당 30개 또는 28개 과제 | 몇 개 과제의 변화가 큰 %p 차이로 나타남 |
| 3회 평균 중심 보고 | 주 성능표에 실행별 값·표준편차·신뢰구간·대응 검정이 없음 | “통계적으로 유의하다”고 결론 내릴 수 없음 |
| 변동하는 유효 분모 | 인프라 실패 과제를 실행별로 제외 | 방법별로 실제 비교한 과제 집합과 분모를 확인하기 어려움 |
| 반복과 과제 수의 구분 | 같은 과제 집합에서 여러 번 실행 | 3회 반복을 독립 과제 수 3배로 간주할 수 없음 |
| `generalize` 단독 실험 | 6개 탐색 과제에서 최고값 비교 | 16.7%p 향상은 한 과제를 더 해결한 결과이며 정밀한 효과 크기 추정이 아님 |
| 다양성 분석의 선택된 표본 | 137개 변형 중 점수가 있는 것은 31개 | 성능 관련 다양성 지표는 평가까지 생존한 부분집합에 대한 결과 |

*근거: p. 18; p. 25, Table 6; pp. 35–37, Table 15.*

> **용어 — 신뢰구간:** 표본과 실행의 변동을 고려했을 때 효과 크기가 어느 범위에 있을지 나타내는 구간.  
> **대응 비교:** 같은 과제에서 두 방법의 성공·실패를 짝지어 비교하는 방식. 이 연구처럼 과제를 공유하는 실험에서는 중요한 분석 단위입니다.

특히 다양성 분석의 465쌍은 31개 후보로 만든 $\binom{31}{2}$쌍입니다. **서로 독립적인 465개의 실험 결과가 아닙니다.** 저자도 이 분석에 신뢰구간이나 영가설 모형이 없으며 기술통계라고 명시합니다. *(p. 37)*

### 7.2 서로 섞어 비교하면 안 되는 수치

| 수치 또는 비교 | 주의해야 하는 이유 | 근거 |
|---|---|---|
| Table 9–10의 평균 F&S | 탐색 분할까지 포함하므로 순수 일반화 평균이 아님 | p. 29 |
| 보안 향상 유지율 55%, 50% | OOD 보안 성공률이 아니라 **향상분의 유지 비율** | p. 9, Table 1 |
| Table 6의 100% | 6개 과제에서의 최고 성적 | p. 25 |
| 부록 K의 100/100/100 | 30개 탐색 과제에서 발견한 측정 악용 사례 | pp. 40–41 |
| Table 8의 동적 실행 64.3%와 Table 10의 HH 탐색 67.9% | 별도 실험 조건의 값이며 같은 실행의 결과라고 합칠 수 없음 | pp. 28–29 |
| Table 12 전이와 Tables 9–10 OOD | 전이는 목표의 탐색 분할, OOD는 별도 미관측 분할에서 평가 | pp. 29–30 |

**보안 향상 유지율**은 다음 비율입니다.

```math
\text{retained}
=
\frac{\Delta_{\text{OUT}}}{\Delta_{\text{evolve}}}.
```

- $\Delta_{\text{evolve}}$: 탐색 분할에서 기준 하네스 대비 보안 성공률 증가량.
- $\Delta_{\text{OUT}}$: OOD 분할에서 같은 기준 대비 증가량.

따라서 DGM의 유지율 0%는 **보안 성공률이 0%라는 뜻이 아니라, 탐색에서 얻은 추가 보안 이득이 OOD에서 남지 않았다는 뜻**입니다. 또한 작은 증가량으로 나눈 −103%, −197% 같은 값은 불안정한 비율이므로 전체 보안이 그만큼 감소했다고 해석하면 안 됩니다. *(Table 1)*

### 7.3 명확히 남아 있는 수치 불일치

**Table 13의 초기 하네스는 기능·보안이 $(56.7,56.7)$이지만, 주 결과 Table 9의 초기 하네스는 $(66.7,56.7)$입니다.** *(pp. 29, 31)*

Figure 5와 부록 설명은 Table 13의 값과 맞습니다. 그러나 주 결과표와 왜 다른지에 대한 충분한 설명은 없습니다. 별도 실행이나 유효 평가 집합 차이일 수 있지만, **원문이 설명하지 않은 원인을 임의로 확정해서는 안 됩니다.**

### 7.4 과적합 게이트의 검증 결과가 빠져 있음

부록 K는 다음 보정 설계를 설명합니다. *(pp. 37–39)*

- 실제 승인된 자식 5개.
- 원본을 포함한 16개 조건.
- 조건별 3회 판정과 다수결.
- 총 240회 판별기 호출.
- 의미적 과적합과 대조군 검증을 위한 35회 미사용 데이터 평가.
- 대응 McNemar 검정과 판정 불일치율 비교.

그러나 **실제 임계값, 검출률, 오탐률, 판정 불일치율, 보정 곡선, McNemar 검정값 또는 p값은 제시되지 않습니다.**

> **용어 — 오탐률:** 실제로는 일반적인 수정인데 과적합이라고 잘못 거부하는 비율.  
> **McNemar 검정:** 같은 대상에 대해 두 조건의 이진 결과가 달라지는 양상을 분석하는 대응 검정.

따라서 **게이트를 제안하고 보정 설계를 기술했다**고는 말할 수 있지만, **그 효과가 정량적으로 검증되었다**고 결론 내릴 수는 없습니다.

또한 게이트 보정에 사용하는 미사용 데이터와 최종 평가 데이터의 관계가 충분히 명료하지 않습니다. 이는 추가 설명이 필요한 부분이며, 이 사실만으로 데이터 누수가 발생했다고 단정할 수는 없습니다.

### 9.2 선행연구와 비교할 때 수정해서 읽어야 할 주장

**첫째, “기존 연구는 안전성을 전혀 평가하지 않았다”는 넓은 표현은 부정확합니다.** SoS는 성능과 안전을 공동 최적화하고, GEPA의 PUPA 평가는 응답 품질과 개인정보 누출을 함께 다룹니다.  
따라서 HH의 차별성은 **실행으로 판정한 코드 기능·보안을 별도 목표로 유지하면서 저장소 규모 하네스를 분리 진화·동적 조합하는 결합 설계**에 있습니다. [ACL Anthology](https://aclanthology.org/2024.emnlp-industry.76/?utm_source=chatgpt.com)

**둘째, 일반화 자체가 HH에서 처음 등장한 것은 아닙니다.** ADAS는 도메인·모델 간 전이를, Meta-Harness는 탐색에 사용하지 않은 모델로의 전이를 이미 보고합니다.  
HH의 새로운 근거는 보안 코딩 환경에서 **일반 범위만 옮겼을 때 기능·보안 공동 성과가 유지·개선되는가**에 가깝습니다. [arxiv.org](https://arxiv.org/html/2408.08435v2?utm_source=chatgpt.com)

**셋째, “미사용 데이터”의 역할을 동일하게 보아서는 안 됩니다.** Self-Harness는 미사용 과제를 후보 채택을 위한 회귀 검사에 사용합니다.  
HH는 최종 하네스 선택에 미사용 평가를 사용하지 않는다고 명시합니다.  
이처럼 선택에 쓰이는 검증 집합과 최종 평가 집합의 차이는 일반화 주장을 비교할 때 중요합니다. *(HH p. 4)* [arxiv.org](https://arxiv.org/html/2606.09498v3?utm_source=chatgpt.com)

### 9.3 더 최근의 관련 문제: 평가자료 오염

2026년 9월의 *Reflections on Trusting Trust, Revisited*는 오염된 벤치마크가 자기 수정 코딩 에이전트에 취약한 코딩 습관을 심을 수 있다는 실험을 보고합니다.  
실험 대상은 수정된 DGM, SICA, Hyperagents이며 **HH에 대한 공격 실험은 아닙니다**.  
이 결과는 HH의 실행 피드백과 일반 구성요소가 오염된 평가자료에도 견디는지 검증할 필요성을 제기하는 관련 근거입니다. [arxiv.org](https://arxiv.org/abs/2609.17817?utm_source=chatgpt.com)

## 11. 결론, 시사점, 유망한 접근과 후속 연구

### 11.1 저자가 제시한 결론과 한계

**[저자 보고]** 연구진은 기능성과 보안을 별도 축으로 유지하고, 실행 피드백으로 하네스 전체를 개선하며, 일반·환경 특화 구성요소를 분리하는 방식이 보안 코딩의 성능과 전이에 유리하다고 결론 내립니다. *(p. 11)*

저자가 명시한 주요 한계와 다음 과제는 다음과 같습니다.

- **현재 관측된 목표 충돌이 약함:** 적대적·프롬프트 주입 과제나 보안 수정이 기존 테스트와 충돌하는 환경을 조사할 필요가 있습니다. *(p. 28)*
- **탐색 점수만으로 안전성을 판단할 수 없음:** HH를 포함한 어떤 수용 규칙도 탐색 데이터에만 의존하면 측정 악용 위험이 있습니다. *(pp. 28, 40–41)*
- **외부 검증기로 행동을 차단하는 방식은 미평가:** 이른바 shielded evolution과의 비교가 없습니다. *(p. 29)*
- **도메인 범위 제한:** 보안 코드 생성 밖으로의 전이는 미해결입니다. *(p. 29)*
- **평가 비용:** 컨테이너 빌드와 공격 실행이 실제 소요시간의 큰 부분을 차지합니다. *(p. 29)*
- **다양성 측정 한계:** 코드 거리와 수정자의 자기 설명만으로 행동 다양성을 충분히 측정하기 어렵습니다. *(pp. 36–37)*

> **용어 — 프롬프트 주입:** 에이전트가 읽는 외부 내용에 지시를 넣어 의도하지 않은 행동을 유도하는 공격.  
> **측정 악용/reward hacking:** 원하는 속성을 실제로 개선하기보다 점수를 높이는 평가상의 허점을 이용하는 행동.  
> **실드(shield):** 에이전트의 행동을 외부에서 검사하고 위험한 행동을 실행 전에 거부하는 장치.

논문은 이러한 연구 방향을 제시하지만, 구체적인 수행 일정이나 후속 연구 결과를 보고하지는 않습니다.

### 11.2 빠르게 검증할 가치가 높은 접근

다음은 **[제안]**입니다. 원문의 결과를 바탕으로 우선순위를 정한 최소 검증 설계이며, 성능 향상을 예측한 결과는 아닙니다.

| 우선 검증할 접근 | 유망하다고 보는 원문 근거 | 복잡한 전체 시스템 없이 수행할 최소 실험 | 핵심 측정값 |
|---|---|---|---|
| **실행 결과를 실제 수정에 연결하는 검증 도구** | 실행 피드백을 사용하는 변형의 미사용 과제 성능 개선, Table 14 | 동일 하네스에서 실제 빌드·실행 결과를 사용하는 조건과 사용하지 않는 조건 비교 | 미사용 과제의 기능·보안·공동 성공률 |
| **일반 코드와 환경 전용 사실 분리** | 양방향 벤치마크 전이, Table 12 | 하드코딩된 환경 정보를 찾아 실행 시 확인하거나 환경 설정으로 이동한 뒤 일반 영역만 전이 | 원래 환경 성능 유지와 목표 환경 성능 |
| **작은 단계 메뉴를 이용한 과제별 실행 계획** | 동일 하네스의 동적 실행 전환 실험, Table 8 | 생성·빌드·보안 검사·수정의 소수 단계만 준비하고 고정 순서와 과제별 선택 비교 | 공동 성공률, 토큰, 지연시간 |
| **목표별 피드백과 균형적 후보 선택** | Table 2의 통제된 수용 규칙 비교 | 도구와 실행 구조를 고정한 채 가중합과 Tchebycheff 선택만 변경 | 기능·보안의 변화, 공동 성공률, OOD 유지 |

**[분석] 빠른 검증의 우선순위는 실제 실행 피드백과 범위 분리에 두는 것이 합리적입니다.** 전자는 수정의 근거를 분명하게 만들고, 후자는 전이 시 무엇을 가져가야 하는지 명시합니다. `generalize`라는 이름만으로 일반화 효과를 전제하지 말고, **일반 영역만 사용하는 목표 환경 평가**로 확인해야 합니다. *(Tables 6, 12, 14에 근거한 해석)*

### 11.3 추가 후속 연구 방향

**[제안 1: 일반화의 원인을 더 명확히 분리]**  
분리 진화 유무와 동적 실행 유무를 모두 조합한 실험을 같은 기반모델·과제·검색 예산·해결 예산에서 수행할 필요가 있습니다. 현재 누적 제거 실험보다 두 요소의 독립 효과와 상호작용을 명확히 알 수 있습니다.

**[제안 2: 평가 분할을 더 엄격하게 구분]**  
탐색, 게이트 보정, 후보 선택, 최종 평가에 사용하는 데이터를 분리하고 과제 목록을 공개하는 것이 중요합니다. 저장소와 오류 유형을 함께 분리하면 환경 고유의 요령이 전이 성능으로 나타나는지를 더 엄격하게 검사할 수 있습니다.

**[제안 3: 기반모델 간 하네스 전이]**  
한 모델에서 진화한 일반 영역을 다른 모델 계열에 그대로 적용하여, 재사용 가능한 실행 구조와 모델 특유의 프롬프트·도구 사용 습관을 구분할 수 있습니다. 이는 ADAS·Meta-Harness가 다룬 모델 간 전이와 HH를 같은 평가 틀에서 비교하는 방향입니다. [arxiv.org](https://arxiv.org/html/2408.08435v2?utm_source=chatgpt.com)

**[제안 4: 더 넓은 보안 검증]**  
기존 PoC 외에 새로운 공격, 입력 변형, 프롬프트 주입, 평가자료 오염을 포함한 별도 검사를 두어야 합니다. 평가자료 오염 연구는 이 방향의 필요성을 뒷받침하지만, HH가 해당 공격에 취약하다는 결론은 별도 실험이 필요합니다. [arxiv.org](https://arxiv.org/abs/2609.17817?utm_source=chatgpt.com)

**[제안 5: 행동과 비용을 함께 측정]**  
코드 거리보다 실제 작업 그래프, 도구 호출 경로, 과제별 성공 패턴을 비교하고, 기능·보안 성과와 함께 비용·지연시간을 보고할 필요가 있습니다. 이는 원문이 인정한 행동 다양성 측정과 실행 비용의 공백에 직접 대응합니다. *(pp. 29–37)*

### 11.4 학술적·실용적 시사점

**학술적으로**, 이 연구는 에이전트 자동 설계의 평가 대상을 단일 작업 점수에서 **기능·보안·전이의 관계**로 넓힙니다. 또한 일반화 가능한 동작이 무엇인지 코드 수준에서 분리하고, 그 부분만 다른 환경에 옮기는 실험을 제시했다는 점이 중요합니다. *(pp. 7, 10–11, 24)*

**실용적으로**, 재사용 가능한 검증 도구, 환경 정보의 실행 중 확인, 과제별 검사·수정 흐름은 직접 검토하고 개선할 수 있는 설계 단위입니다. 다만 실제 도입 판단에는 성능표뿐 아니라 총비용, 실행 안정성, 새로운 취약점에 대한 평가가 추가로 필요합니다. *(pp. 21–24, 28–29에 근거한 분석)*

**일반화 성능과 관련한 최종 결론은 다음과 같습니다.** Harmony Harness는 개선된 실행 구조가 보안 코딩 과제 사이에서 전이될 수 있다는 긍정적 근거를 제공합니다. 그 근거를 가장 강하게 뒷받침하는 것은 미사용 과제의 공동 성공률과 일반 영역만 사용하는 벤치마크 간 전이입니다. 동시에 CWEval의 기능 성능 하락은 일반화가 모든 목표의 동시 개선을 뜻하지 않음을 보여 주며, 기반모델 자체의 일반화 능력 변화와는 구분해서 평가해야 합니다. *(Tables 9–12)*
