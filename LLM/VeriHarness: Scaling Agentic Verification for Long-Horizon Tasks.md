## 1. Executive summary — 9문장

이 연구의 목적은 **더 강한 모델이나 테스트 시점의 정답·채점 기준 없이, 생성에 사용한 동일한 모델의 검증 능력을 높이는 것**입니다(pp.1–3).  
저자들은 APEX-Agents 분석에서 모든 후보가 동의한 주장도 34%가 틀렸고, 의견이 갈린 주장에서는 74%가 정답 후보를 포함하지만 최빈값이 정답인 비율은 47%에 불과하다고 보고합니다(p.2, Figure 2).  
이에 VeriHarness는 **불일치 해결자**와 **합의 도전자**를 분리하여 원본 파일·계산·메타데이터에서 증거를 수집하도록 합니다(pp.4–6, Figure 3).  
이후 동일 모델의 새로운 대화 문맥에서 두 조사 결과를 종합하여 기존 산출물을 선택하거나 증거에 따라 수정하며, 모델 가중치는 변경하지 않습니다(pp.5–6, 식 2–7). 2610.00972v1 2610.00972v1 2610.00972v1

5개 벤치마크와 2개 모델의 주된 선택 비교에서 VeriHarness는 모든 모델–벤치마크 조합의 최고 평균 점수를 기록했습니다(p.8, Table 2).  
수정까지 수행하면 단일 실행 기준 대비 벤치마크 평균이 Gemini 3.5 Flash에서 6.2점, Claude Opus 4.8에서 6.4점 향상됩니다(p.8, Table 2).  
개발 과제의 실패 피드백으로 검증 스킬을 개선하면, 사람이 작성한 스킬에서 출발한 조건은 별도로 남겨둔 평가 과제에서 APEX-Agents 6.8점, SpreadsheetBench 2 3.7점의 추가 향상을 보입니다(p.9, Figure 4).  
다만 이 자기개선 결과는 제한된 과제 분포와 단일 데이터 분할의 점추정치이며, 저자도 통계적 유의성과 분포 밖 일반화가 확립되지 않았다고 명시합니다(pp.26–27).  
따라서 가장 강하게 지지되는 결론은 **“기저 모델 자체가 더 일반적으로 학습되었다”가 아니라 “고정된 모델도 증거 수집과 재사용 가능한 검증 절차를 통해 더 좋은 결과를 낼 수 있다”**는 것입니다. 2610.00972v1 2610.00972v1 2610.00972v1

> **용어 풀이**  
> **하네스(harness):** 모델을 실제 에이전트로 작동시키는 도구, 실행 순서, 작업 공간, 메모리 등의 주변 시스템.  
> **검증 스킬(skill):** “어떤 오류를 의심하고 어떻게 확인할지”를 정리한 재사용 가능한 지침과 선택적 실행 스크립트.  
> **점추정치:** 불확실성 구간 없이 제시한 하나의 성능 추정값.  
> **분포 밖 일반화:** 개발 때와 다른 분야·문서 형식·문제 유형에서도 성능 향상이 유지되는 것.

## 3. 제안 방법과 모델 구조 — 수식 및 기호 설명

### 3.1. 작업과 후보 실행의 정의

**[저자 정의: p.3, §2]**

$$
t=(s,\mathcal E),\qquad
r_i=(d_i,w_i,\tau_i),\qquad
R=\{r_1,\ldots,r_N\}.
$$

여기서 $t$는 작업, $s$는 작업 설명, $\mathcal E$는 원본 파일·데이터·애플리케이션 상태가 있는 환경입니다. $r_i$는 $i$번째 실행 결과인 **롤아웃**, $d_i$는 제출 산출물, $w_i$는 최종 작업 공간 상태, $\tau_i$는 행동 기록입니다. $R$은 후보 롤아웃의 집합이며 $N$은 후보 수입니다. 2610.00972v1

> **용어 풀이 — 롤아웃(rollout):** 에이전트가 한 번 작업을 수행하면서 남긴 행동 과정과 최종 결과를 합친 실행 기록.

검증자는 $R$에서 하나를 선택하거나 수정하여 최종 결과 $r^\star$와 검증 기록 $C$를 반환합니다. 목표는 외부 채점기가 평가하는 품질을 높이는 것이지만, **검증 실행 중에는 그 채점기를 호출할 수 없습니다**. 검증 단위는 산출물 전체가 아니라 수치·해석·요구사항 충족 여부를 나타내는 개별 **주장(claim)**입니다(p.3). 2610.00972v1

### 3.2. 합의와 불일치: 주장 엔트로피

**[원문 식 1: p.4]**

```math
\pi_p(v)
=
\frac{1}{N}
\sum_{i=1}^{N}
\mathbf{1}[v_{i,p}=v],
\qquad
H(\pi_p)
=
-\sum_{v\in\mathcal V_p}
\pi_p(v)\log\pi_p(v).
```

$p$는 공통 질문이나 요구사항, $v_{i,p}$는 후보 $i$가 주장 $p$에 제시한 값, $\mathcal V_p$는 관찰된 후보 값의 집합입니다. $\pi_p(v)$는 값 $v$의 출현 비율이며, $\mathbf{1}[\cdot]$는 조건이 참이면 1, 거짓이면 0인 지시함수입니다. $H$는 후보들의 답이 얼마나 다양하게 갈리는지 나타냅니다. 의미가 같은 표현은 같은 값으로 묶고, **누락도 별도의 값**으로 취급합니다(pp.3–4). 2610.00972v1 2610.00972v1

> **용어 풀이 — 엔트로피(entropy):** 여기서는 답변의 분산 정도입니다. 전부 같은 답이면 0이고, 여러 답으로 갈리면 양수가 됩니다. **정답 확률을 뜻하지는 않습니다.**

저자는 $H(\pi_p)=0$을 합의, $H(\pi_p)>0$을 불일치로 정의합니다. 따라서 **“엔트로피가 낮다 → 정확하다”는 추론은 이 논문에서 성립하지 않습니다.** 모든 후보가 같은 잘못된 통화 단위를 쓰면 엔트로피는 0이어도 오류입니다(p.4, Figure 3 및 식 1). 2610.00972v1

### 3.3. 모델 구조: 새로운 신경망이 아니라 검증용 실행 구조

**[원문 식 2: p.5]**

$$
\text{Verifier}=(M,\mathcal H_V),
\qquad
\mathcal H_V=(\mathcal W,\mathcal T,\Pi,\mathcal S).
$$

$M$은 가중치가 고정된 기저 모델, $\mathcal H_V$는 검증 하네스입니다. $\mathcal W$는 작업 공간, $\mathcal T$는 증거 수집 도구, $\Pi$는 검증 프로토콜, $\mathcal S$는 스킬 라이브러리입니다. 생성자 역시 같은 $M$과 생성용 하네스 $\mathcal H_G$로 구성됩니다. 2610.00972v1

실행 구조는 다음과 같습니다.

| 단계 | 역할 | 문맥·정보 접근 |
|---|---|---|
| 불일치 해결자 | 후보마다 다른 주장과 그 출처·계산을 조사 | 독립된 문맥에서 실행 |
| 합의 도전자 | 모두가 공유한 값·해석·누락에 반례를 찾음 | 해결자의 조사 기록을 보지 않는 별도 문맥 |
| 판정 | 두 증거 기록을 종합하여 기반 후보·수정 계획·미해결 항목을 결정 | 동일 모델의 새로운 문맥 |
| 제출 | 계획을 적용하여 산출물과 검증 기록을 생성 | 판정 문맥을 이어서 사용 |

이것은 서로 다른 모델을 학습시키는 구조가 아니라 **동일 모델을 서로 다른 역할과 정보 상태로 실행하는 구조**입니다. 두 조사는 병렬로 진행되지만 판정과 제출은 같은 문맥을 공유합니다(pp.20–21, Algorithm 1). 2610.00972v1 2610.00972v1

> **용어 풀이 — 문맥(context):** 한 번의 모델 세션이 참고하는 지시문, 대화 기록, 도구 결과 등의 정보 묶음. 문맥을 분리한다고 모델의 오류 성향까지 독립적으로 바뀌는 것은 아닙니다.

사람이 작성한 라이브러리는 **증거 스킬 6개, 불일치 해결 스킬 4개, 합의 도전 스킬 3개, 수정 스킬 5개**, 총 18개입니다. 예를 들어 수식과 저장된 셀 값을 함께 읽기, 문서의 변경 내용 확인, 적용할 원본 버전 판별, 수정한 셀 이외의 부분이 손상되지 않았는지 확인하는 절차를 제공합니다(pp.24–25, Table 6). 2610.00972v1 2610.00972v1

**[해석]** 따라서 이 논문의 구조적 기여는 Transformer 층이나 새로운 학습 손실이 아니라, **검증할 대상을 찾는 지식과 증거 수집 순서를 모델 주변에 조직한 것**입니다.

### 3.4. 불일치 해결자: 정보를 많이 주는 검사를 선택

**[원문 식 3: p.5]**

```math
\text{Gain}(\chi)
=
\mathbb E
\left[
H(b_p)
-
H\!\left(b_p(\cdot\mid\mathcal E(\chi))\right)
\;\middle|\;
e_{ < k}
\right].
```

$\chi$는 검사 행동, $\mathcal E(\chi)$는 그 검사를 환경에서 실행하여 얻는 증거입니다. $b_p$는 현재 증거를 고려했을 때 주장 $p$의 정답에 대한 믿음 분포이며, $e_{<k}$는 $k$번째 검사 이전에 수집한 증거입니다. $\mathbb E$는 가능한 검사 결과에 대한 기대값입니다. **후보의 출현 빈도 $\pi_p$와 정답에 대한 믿음 $b_p$는 다릅니다.** 2610.00972v1

> **용어 풀이 — 기대 정보 이득:** 검사를 수행하면 “무엇이 맞는지 모르는 상태”가 얼마나 줄어들 것으로 예상되는지를 뜻합니다.

**중요한 구현상의 한계:** 저자는 이 값을 **수치로 계산하지 않고 모델이 정성적으로 판단한다**고 명시합니다. 따라서 식 3은 실제로 구현된 정밀한 베이지안 최적화 알고리즘이 아니라 검사 선택의 원리를 표현한 것입니다(p.5). 2610.00972v1

증거 $e$를 얻으면 모순되는 후보를 제외합니다.

**[원문 식 4: p.5]**

$$
\mathcal V_p
\leftarrow
\{v\in\mathcal V_p:
v\text{ is consistent with }e\}.
$$

$\mathcal V_p$는 남아 있는 후보 값들이고, $e$는 새로 얻은 증거입니다. 모든 후보가 반박되더라도 **증거가 새 값을 확립하는 경우에만** 새로운 정답을 기록하며, 그렇지 않으면 미해결 상태로 남깁니다. 조사 결과는 $L_{\ne}$에 기록됩니다. 2610.00972v1

**[해석]** 식 4는 형식적으로는 후보 제거 연산이지만, “증거와 일치한다”는 판정 자체를 LLM이 수행하므로 논리적 무오류가 보장되는 절차는 아닙니다.

### 3.5. 합의 도전자: 모두가 놓친 오류를 찾기

**[원문 식 5: pp.5–6]**

```math
\text{Priority}(\chi)
=
P\!\left(
\chi\text{ exposes a consensus error}
\;\middle|\;
t,R,e_{ < k}
\right).
```

$P$는 해당 검사가 합의 주장의 오류를 발견할 가능성, $t$는 작업, $R$은 후보 풀, $e_{<k}$는 이전 증거입니다. 이 역시 **확률값을 실제 추정하는 것이 아니라 정성적으로 우선순위를 판단**합니다. 2610.00972v1

도전 대상은 세 가지입니다. **공통 값**은 재계산·단위 확인으로, **공통 해석**은 원본의 정의·기간·지정 파일 확인으로, **공통 누락**은 작업 요구사항과 모든 산출물을 대조하여 검사합니다. 결과는 $L_{=}$에 저장합니다(p.6). 2610.00972v1

**[해석]** 이 부분이 단순 다수결과 가장 크게 다른 지점입니다. 특히 “아무도 쓰지 않은 필수 항목”은 후보 텍스트만 비교해서는 쉽게 발견되지 않으므로, **작업 설명에서 검증 대상을 새로 만들어내는 능력**이 필요합니다.

### 3.6. 판정과 증거 기반 수정

**[원문 식 6: p.6]**

```math
(\text{base},\text{revision\_plan},\text{unresolved})
=
A(L_{\ne},L_{=},t,R).
```

$A$는 판정 단계입니다. $\text{base}$는 수정의 출발점이 되는 후보이며 $R\cup\{\varnothing\}$에 속합니다. $\text{revision plan}$은 증거가 뒷받침하는 수정 계획, $\text{unresolved}$는 아직 결론을 내리지 못한 주장 목록입니다. 쓸 만한 후보가 없으면 $\text{base}=\varnothing$으로 설정합니다. 기반 후보는 중요한 요구사항에 대해 증거로 확인된 결함이 적은 것을 선택하지만, 그 중요도 가중치를 계산하는 별도의 수식은 제시하지 않습니다. 2610.00972v1

**[원문 식 7: p.6]**

```math
\begin{aligned}
r^\star
&=
\text{Apply}
(\text{base},\text{revision\_plan},\text{unresolved}),\\
C
&=
(L_{\ne},L_{=},\text{base},
\text{revision\_plan},\text{unresolved}).
\end{aligned}
```

$\text{Apply}$는 계획을 적용하는 제출 단계, $r^\star$는 최종 롤아웃, $C$는 전체 검증 기록입니다. 선택 전용 평가에서는 기반 후보를 바꾸지 않고 반환하며, 전체 시스템은 수정하거나 새로 구성합니다. 미해결 해석은 기록에 남기고, 산출물 형식이 허용하면 두 해석을 함께 제시합니다(pp.6, 20). 2610.00972v1 2610.00972v1

> **용어 풀이 — 증거 기록:** 주장, 수행한 검사, 얻은 증거, 판정을 연결한 기록. 수정 이유를 추적할 수 있게 하지만, 기록이 존재한다는 사실만으로 판정의 정확성이 보장되지는 않습니다.

### 3.7. 스킬 자기개선: 무엇을 학습하는가?

**[저자 보고]** 모델과 프로토콜은 고정하고 스킬 라이브러리만 바꿉니다. 개발 실패 패키지에는 작업·후보·증거 기록·수정 계획·제출 결과와 **항목별 채점 피드백**이 포함됩니다. 매 라운드 초기에는 3개, 이후에는 5개 후보 라이브러리를 만들고, 같은 개발 과제에서 현재 라이브러리보다 나쁘지 않은 최선의 후보를 채택합니다(p.26). 2610.00972v1

이 선택 규칙을 설명용으로 다시 쓰면 다음과 같습니다. **아래는 원문의 번호 수식이 아니라 본 답변의 재표기입니다.**

$$
\mathcal S_{\ell+1}
\in
\arg\max_{\mathcal S\in
\{\mathcal S_\ell,\mathcal S_\ell^{(1)},\ldots,
\mathcal S_\ell^{(K_\ell)}\}}
\widehat Q_{\text{dev}}(\mathcal S).
$$

$\ell$은 진화 라운드, $\mathcal S_\ell$은 현재 라이브러리, $\mathcal S_\ell^{(j)}$는 $j$번째 후보, $K_\ell$은 후보 수, $\widehat Q_{\text{dev}}$는 해당 라이브러리를 사용한 전체 시스템의 개발 점수입니다. 동점이면 교체가 허용됩니다.

**“Training-free”를 “피드백 없이 학습”으로 읽어서는 안 됩니다.** 여기서는 신경망 가중치를 훈련하지 않는다는 뜻이며, 스킬 진화는 개발 채점기의 감독 신호를 사용합니다. 테스트 과제에서 정답·루브릭을 보지 않는 것과 개발 과정에서 피드백을 받는 것은 서로 다른 조건입니다(pp.9, 26). 2610.00972v1 2610.00972v1

## 7. 모델의 일반화 성능 향상 가능성: 어디까지 입증됐는가?

### 7.1. 현재 증거가 지지하는 일반화 수준

**첫째, 프로토콜의 폭넓은 적용 가능성은 관찰됩니다.** 같은 기본 검증 구성을 두 모델과 다섯 작업 벤치마크에 적용했습니다. 그러나 이것은 한 벤치마크에서 개발한 스킬을 완전히 새로운 벤치마크에 그대로 옮기는 **벤치마크 간 전이 실험**과는 다릅니다(pp.7–8, 24–26). 2610.00972v1 2610.00972v1 2610.00972v1

**둘째, 스킬의 동일 분포 내 미관측 과제 전이는 관찰됩니다.** 개발·평가 과제를 원본 자료 단위로 분리했다는 점은 강점입니다. 그러나 저자가 직접 밝히듯, 평가한 과제 분포를 넘어선 일반화와 개발 채점 피드백 없는 개선은 아직 확인되지 않았습니다(pp.26–27). 2610.00972v1 2610.00972v1

**셋째, 실행 시스템 간 이식은 불완전합니다.** 예를 들어 Opus의 JobBench 선택 점수는 전용 구현 46.1에 비해 Claude Code에서 42.4이며, 단일 실행 기준은 42.8입니다. 따라서 “텍스트로 프로토콜과 스킬을 전달하면 어느 에이전트에서도 동일하게 작동한다”는 주장은 지지되지 않습니다(p.8, Table 2; p.23). 2610.00972v1 2610.00972v1

**넷째, 모델 가중치에 내재화된 일반화 개선은 측정하지 않았습니다.** 이 논문은 가중치가 고정된 모델에 더 좋은 정보·절차를 제공한 실험입니다. 하네스를 제거한 뒤에도 모델 자체가 이전보다 더 잘하는지는 평가하지 않았으며, 검증 기록으로 생성자를 훈련하는 것은 후속 방향으로 남겨두었습니다(pp.5, 12). 2610.00972v1 2610.00972v1

### 7.2. 일반화가 가능할 것으로 보는 이유 — 본 답변의 해석

**[해석]** 가장 유망한 요소는 답 자체가 아니라 **오류를 찾는 절차의 재사용**입니다. “성장률 수식의 시작·종료 열이 라벨의 기간과 맞는가”, “차감 항목의 부호가 통합문서 규칙과 맞는가”, “모든 요구 항목이 결과에 포함되었는가”는 특정 정답 수치보다 다른 과제로 옮기기 쉽습니다. 실제 학습된 스킬 예시가 이런 절차를 포함합니다(pp.10, 26–27). 2610.00972v1 2610.00972v1

하지만 전이에는 조건이 있습니다. 새로운 과제에서 원본 증거를 읽을 수 있어야 하고, 스킬의 적용 조건이 맞아야 하며, 모델이 **올바른 중간값을 확인하는 것과 최종 요구사항을 확인하는 것**을 구분해야 합니다. 저자 분석에서 살아남은 합의 오류의 70%는 검증한 값이 입력·중간값이고 실제 오답은 더 아래 단계에 있는 경우였습니다(p.27, Table 7). 2610.00972v1

> **용어 풀이 — 적용 조건:** 특정 검사 규칙을 사용해도 되는 상황. 예를 들어 한 통합문서의 부호 규칙이 다른 문서에도 그대로 맞는다고 가정해서는 안 됩니다.

## 10. 결론과 후속 연구 방향

### 10.1. 저자가 제시한 시사점과 후속 방향

**[저자 결론]** 검증 능력의 향상은 더 강한 모델의 등장을 기다릴 필요가 없으며, 기존 모델의 후보 실행, 환경 증거, 축적된 검증 경험을 조직하는 방식으로도 가능하다는 것이 핵심입니다. 검증 기록을 생성자 훈련 데이터로 바꾸는 것을 자연스러운 다음 단계로 제안합니다(pp.11–12). 2610.00972v1

또한 개별 롤아웃에 **보정된 단일 점수**를 부여하는 방법은 후속 연구로 남겨두며, 더 강한 검증 모델을 사용하는 경우는 하네스 효과와 모델 능력 차이를 분리하기 어렵기 때문에 본 연구 범위에서 제외합니다(p.12). 2610.00972v1

> **용어 풀이 — 보정된 점수(calibrated score):** 예를 들어 신뢰도 80%를 부여한 결과들이 실제로도 대략 80% 맞도록, 점수와 현실의 정확성이 일치하는 상태.

### 10.2. 추가로 권하는 연구 방향 — 본 답변의 제안

**① 일반화를 “새 과제·새 분야·새 모델”로 분리하여 측정해야 합니다.**  
같은 원본을 공유하지 않는 과제 분할을 유지하면서, 한 벤치마크 전체를 개발에서 제외하는 시험, 새로운 문서 형식·기간·단위 규칙을 사용하는 시험, 한 모델에서 만든 스킬을 다른 모델에 전달하는 시험을 각각 수행하는 것이 우선입니다. CoEvoSkills의 모델 간 전이 실험은 설계상 참고할 만하지만, 그 결과를 VeriHarness의 전이 성능으로 대체할 수는 없습니다. [arXiv](https://arxiv.org/pdf/2604.01687v3)

**② 스킬 진화의 총비용을 포함한 비교가 필요합니다.**  
후보 생성, 검증, 수정, 개발 후보 라이브러리 평가까지 포함한 예산을 맞춘 뒤, 추가 생성·반복 검증·스킬 진화 중 어디에 계산을 쓰는 것이 유리한지 비교해야 합니다. 개발 비용을 여러 미래 과제에 나누어 부담하는 상황도 별도로 보고해야 실제 배포 가치를 판단할 수 있습니다. 이는 기존 하네스 진화 평가 연구가 지적한 공정한 비교 문제와 연결됩니다. [arXiv](https://arxiv.org/pdf/2408.03314)

**③ 주장 간 의존관계를 검증 대상으로 삼아야 합니다.**  
현재 분석의 70% 잔존 오류는 올바른 중간값을 확인하고도 잘못된 최종 결론을 놓친 경우입니다. 따라서 단일 셀이나 단일 문장 확인을 넘어 **원본 입력 → 중간 계산 → 최종 수치 → 요구사항 충족**의 연결 전체를 검사하는 구조가 유망합니다. 한 단계의 재계산 일치가 최종 답의 정확성을 뜻하지 않도록 스킬을 설계해야 합니다(p.27, Table 7). 2610.00972v1

**④ “잘 고쳤는가”와 “잘못 고치지 않았는가”를 분리해서 평가해야 합니다.**  
평균 점수 외에 정확한 주장을 망가뜨린 비율, 오류를 남겨둔 비율, 미해결 표시의 적절성, 과제별 최악의 악화 폭을 보고할 필요가 있습니다. 특히 합의 도전자는 공격적인 반례 탐색이 중요한 만큼, 근거가 부족할 때 수정하지 않는 판단도 별도의 평가 대상이 되어야 합니다. 이는 논문의 미해결 기록 설계를 실제 안전성 지표로 발전시키는 방향입니다(pp.6, 20, 27). 2610.00972v1 2610.00972v1 2610.00972v1

**⑤ 기저 모델 자체의 일반화를 높이려면 검증 기록을 학습에 내재화해야 합니다.**  
저자가 제안한 후속 방향을 실제로 검증하려면, 증거가 충분한 수정 사례와 불충분한 사례를 구분하여 생성자를 훈련한 뒤, **하네스 없이도 새로운 과제에서 성능이 유지되는지** 측정해야 합니다. 이때 자동 검증 기록을 무조건 정답 라벨로 사용하면 검증기의 공통 오류까지 학습할 수 있으므로, 독립적 재검사와 사람 표본 감사를 거친 데이터가 필요합니다. 과정 감독 연구는 이런 세분화된 학습 신호의 가능성을 뒷받침하지만, VeriHarness 기록의 학습 효과는 아직 실험되지 않았습니다. 2610.00972v1 [arXiv](https://arxiv.org/pdf/2305.20050)

### 최종 평가

**VeriHarness는 “고정된 모델의 검증 행동을 더 잘 조직하면 장기 작업의 결과가 개선된다”는 설득력 있는 실증 연구입니다.** 특히 합의된 오류까지 검사하고 그 증거를 실제 수정으로 연결한 점이 중요합니다. 다만 **일관된 평균 개선, 동일 분포의 홀드아웃 전이, 다른 실행 시스템으로의 이식, 기저 모델의 분포 밖 일반화는 서로 다른 주장**이며, 현재 결과가 가장 직접적으로 지지하는 것은 앞의 두 가지입니다. 후속 연구의 핵심은 개선 폭을 더 키우는 것만이 아니라, **어떤 스킬이 어떤 분포로 전이되는지, 그 이득이 얼마의 비용과 수정 위험을 수반하는지, 공개 실험 자료로 동일하게 재현되는지**를 확립하는 데 있습니다. 2610.00972v1 2610.00972v1

**주요 자료 출처:** 첨부 논문 *VeriHarness: Scaling Agentic Verification for Long-Horizon Tasks*; 공식 구현 *google-research/veriharness — README*; 저자 데이터 카드 *VeriHarness rollouts*입니다. 비교에 사용한 선행 논문의 전체 제목과 원문 출처는 8절 표에 각각 표시했습니다. [arXiv](https://arxiv.org/abs/2610.00972)
