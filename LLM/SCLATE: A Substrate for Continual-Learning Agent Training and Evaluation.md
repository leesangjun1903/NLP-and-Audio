## 2. 연구 목적과 필요성, 핵심 주장

### 2.1 무엇이 기존 방식으로는 어려웠는가?

**[저자 보고]** 논문은 지속학습 에이전트를 단순한 언어모델이 아니라 **모델의 행동, 하네스의 실행 규칙, 세션을 넘어 유지되는 메모리가 결합된 시스템**으로 정의합니다. 그런데 기존 평가 방식은 대체로 정적인 대화 기록을 읽고 답하게 하거나, 평가 프레임워크에 내장된 에이전트를 실행하거나, 외부 에이전트를 받아도 벤치마크만 사건을 예약하도록 구성되어 있다고 분류합니다. **[pp. 1–3, Figure 1]** 2609.32391v2 2609.32391v2

이러한 환경에서는 “어제의 작업을 기억했는가?”뿐 아니라 “세션 종료 때 무엇을 저장했고, 밤중에 어떻게 정리했으며, 다음 날 재시작할 때 무엇을 복구했는가?”를 함께 평가하기 어렵습니다. SCLATE는 이 전체 생애주기를 하나의 시간축에서 실행하는 것을 목표로 합니다. **[저자 보고: pp. 2–5]** 2609.32391v2 2609.32391v2

> **용어 풀이 — 지속학습:** 이 논문에서는 세션 사이의 기억 축적과 모델 후속 학습을 포함하는 넓은 의미입니다. 새 과제를 배워도 과거 능력을 잃지 않는다는 의미의 지속학습까지 자동으로 입증한 것은 아닙니다.

**[해석]** 연구의 필요성은 분명합니다. 모델을 실제 배포와 다른 도구·문맥·메모리 환경에서 학습시키면, 학습 중 얻은 행동이 배포 환경에 맞지 않을 수 있습니다. SCLATE의 기여는 이 불일치를 줄일 실험 기반을 제공한다는 데 있습니다. 다만 **같은 실행 기반을 쓰는 것과 모든 비교 조건을 동일하게 만드는 것은 다릅니다**. 모델별 응답 지연, 하네스의 문맥 정책, 메모리 용량 제한 등은 여전히 결과에 영향을 줍니다. **[근거: pp. 7–8, Figure 4]** 2609.32391v2

**외부 계층**에는 벤치마크, Claude Code·Hermes·Codex 같은 하네스, 메모리 시스템, 추론 서버, 학습 프레임워크가 있습니다. **호스트 제어 계층**에는 컨테이너 생성·종료를 관리하는 Orchestrator와 학습용 실행 결과를 수집하는 Rollout Engine이 있습니다. **컨테이너 내부 계층**에는 스케줄러, 시뮬레이션 시계, 에이전트, 환경, 채점기, 모델 호출 프록시가 있습니다. 2609.32391v2

### 3.2 개방형 사건 스케줄러와 하이브리드 시계

**[저자 보고]** 스케줄러는 현재 시간, 환경 상태, 에이전트 행동, 채점 결과, 이미 완료된 사건을 읽어 실행 가능한 다음 사건을 고릅니다. 에이전트나 백그라운드 작업이 동작 중이면 시간이 실제 속도로 흐르고, 모두 유휴 상태일 때만 다음 사건 시각으로 이동합니다. **[p. 4, p. 14 Algorithm 1]** 2609.32391v2 2609.32391v2

다음은 **Algorithm 1을 설명하기 위해 다시 쓴 수식**이며, 별도의 새로운 이론식은 아닙니다.

$$
c_{k+1}=
\begin{cases}
c_k+\Delta t_{\text{wall}}, & b_k=1,\\[4pt]
\max\!\left(c_k,\min_{f\in\mathcal F_k}t_f\right),
& b_k=0,\ \mathcal F_k\neq\varnothing.
\end{cases}
$$

여기서 $c_k$는 현재 시뮬레이션 시간, $\Delta t_{\text{wall}}$은 실제로 경과한 시간, $b_k$는 실행 중인 작업이 있으면 1인 표시값, $\mathcal F_k$는 현재 사건 후보 집합, $t_f$는 사건 $f$의 예정 시각입니다. 유휴 상태이고 후보도 없으면 실행을 종료합니다.

실행할 사건은 준비된 후보 중 가장 이른 사건으로 정하며, 같은 시각이면 식별자로 순서를 정합니다.

$$
e^\star=
\underset{f\in\mathcal F_{\text{ready}}}{\text{arg min}}
\left(t_f,\text{id}_f\right).
$$

여기서 $\mathcal F_{\text{ready}}$는 현재 시각까지 실행 조건이 충족된 후보, $\text{id}_f$는 사건의 식별자, $e^\star$는 선택된 사건입니다. 이 순서 규칙은 Algorithm 1에 직접 제시됩니다. **[p. 14]** 2609.32391v2

> **용어 풀이 — 하이브리드 시계:** 실제 시간 진행과 사건 시각으로의 점프를 결합한 시계입니다. **cron**은 정해진 시각에 반복 실행되는 예약 작업입니다. **메모리 통합·정리**는 여러 기록을 요약하거나 중복을 줄여 이후에 사용하기 쉬운 기억으로 바꾸는 작업입니다.

**[해석]** 핵심은 시간을 무조건 빠르게 돌리는 것이 아니라, **작업이 진행 중인 시간과 아무 일도 없는 시간을 구분하는 것**입니다. 따라서 모델 응답과 도구 실행에 걸리는 시간은 그대로 성능에 영향을 줍니다. 반면 야간·주말의 대기 시간은 크게 줄일 수 있습니다. Figure 9가 이 차이를 가장 직관적으로 보여줍니다. **[pp. 16–17]** 2609.32391v2

### 3.3 세션 사이의 상태 유지와 ‘무수정’의 의미

> **용어 풀이 — 로그확률·손실 마스크:** 로그확률은 모델이 어떤 토큰을 선택할 확률에 로그를 취한 값입니다. 손실 마스크는 모델이 생성하지 않은 도구 응답 등을 학습 대상에서 제외하는 표시입니다.

**[해석]** 이 기능은 “성공한 작업의 문장을 나중에 복사해 학습하는 것”과 다릅니다. 실제 실행 시점의 토큰과 확률을 보존해, 모델이 어떤 행동을 선택했는지에 맞는 학습 신호를 전달하는 것이 중요합니다.

### 3.5 MetaClaw 학습: 교사의 추가 정보를 활용하는 on-policy distillation

**[저자 보고]** 학생 모델이 기존 하네스를 통해 직접 실행 기록을 생성하고, 교사는 학생이 보지 못하는 해당 라운드의 교정 피드백을 받아 학생 토큰에 대한 확률을 계산합니다. Hindsight 구성에서는 사실 추출 호출도 학생 모델을 사용하므로, 에이전트 행동과 메모리 기록 생성이 함께 학습됩니다. **[p. 9, Appendix E.2]** 2609.32391v2 2609.32391v2

> **용어 풀이 — on-policy distillation:** 학생이 스스로 생성한 응답에 대해 교사의 평가 신호를 받아 배우는 증류 방식입니다. **특권 정보**는 학습 중 교사에게만 제공되고 실제 학생에게는 주어지지 않는 추가 정보입니다.

논문에 직접 제시된 핵심식은 다음과 같습니다.

```math
\widehat A_i
=
A_i-\beta
\left[
\log \pi_{\text{student}}(y_i)
-
\log \pi_{\text{teacher}}(y_i)
\right].
```

$\widehat A_i$는 수정된 학습 이득 신호, $A_i$는 원래 과제 보상에서 얻는 이득 신호, $y_i$는 학생이 생성한 토큰, $\pi_{\text{student}}$와 $\pi_{\text{teacher}}$는 각각 학생·교사의 토큰 확률, $\beta$는 증류 신호의 세기입니다. **이 실험에서는 과제 보상을 붙이지 않아 $A_i=0$이고, $\beta=1.0$입니다.** 따라서 학습 신호는 학생과 교사의 로그확률 차이에서 나옵니다. **[p. 20, Appendix E.2]** 2609.32391v2

> **용어 풀이 — 이득 신호, advantage:** 어떤 선택을 더 자주 하도록 강화할지, 덜 하도록 억제할지를 정하는 학습 값입니다.

조건을 명시하면, 이 로그확률 차이의 학생 분포에 대한 기댓값은 다음 역방향 KL 발산에 해당합니다. 아래는 논문의 설명을 풀어 쓴 식입니다.

```math
\text{KL}
\left(
\pi_\theta(\cdot\mid h_i)
\,\Vert\,
\pi_T(\cdot\mid h_i,z_i)
\right)
=
\sum_{v\in\mathcal V}
\pi_\theta(v\mid h_i)
\log
\frac{\pi_\theta(v\mid h_i)}
{\pi_T(v\mid h_i,z_i)}.
```

$h_i$는 토큰 생성 전 문맥, $z_i$는 교사만 받는 교정 정보, $\theta$는 학생 모델의 파라미터, $T$는 교사, $\mathcal V$는 토큰 집합, $v$는 개별 토큰입니다.

> **용어 풀이 — KL 발산:** 두 확률분포가 얼마나 다른지를 측정합니다. 여기서는 학생이 실제로 선택하는 응답 영역에서 학생과 교사의 차이를 줄이는 방향의 신호를 사용합니다.

학습은 1–20일의 227개 라운드에 대해 5에포크 수행하며, 학습률은 $10^{-6}$입니다. 교사는 Qwen3.5-35B-A3B, 학생은 Qwen3.5-4B이고, 별도의 기준 모델 KL 항 계수는 0.001로 보고됩니다. **[p. 29, Table 14]** 2609.32391v2

### 3.6 SWE-Gym 학습: GRPO의 활용

**[저자 보고]** SWE-Gym에서는 채점 결과를 보상으로 삼아 GRPO를 사용합니다. 293개 학습 과제, 프롬프트당 16개 실행, 배치당 4개 프롬프트, 73회 학습 반복, 50,000토큰 문맥 창을 사용합니다. **[p. 10, p. 27 Table 13]** 2609.32391v2 2609.32391v2

SCLATE는 GRPO를 새로 제안하지 않았습니다. 다음은 인용된 **DeepSeekMath의 GRPO 일반형**을 간략히 표현한 것입니다. **[외부 원논문 pp. 13–14, Eq. 3]** [arXiv](https://arxiv.org/pdf/2402.03300)

```math
\widehat A_j
=
\frac{R_j-\bar R}{\sigma_R},
\qquad
\rho_{j,t}(\theta)
=
\frac{\pi_\theta(y_{j,t}\mid h_{j,t})}
{\pi_{\text{old}}(y_{j,t}\mid h_{j,t})}.
```

$R_j$는 같은 과제에 대한 $j$번째 실행의 보상, $\bar R$와 $\sigma_R$는 실행 집단의 보상 평균과 표준편차, $\widehat A_j$는 상대적 이득 신호입니다. $y_{j,t}$는 해당 출력의 $t$번째 토큰, $h_{j,t}$는 그 토큰의 입력 문맥, $\pi_{\text{old}}$는 실행을 생성한 이전 정책, $\rho_{j,t}$는 현재 정책과 이전 정책의 확률비입니다.

```math
J_{\text{GRPO}}(\theta)
=
\mathbb E
\left[
\frac{1}{G}
\sum_{j=1}^{G}
\frac{1}{L_j}
\sum_{t=1}^{L_j}
\left\{
\min
\left[
\rho_{j,t}\widehat A_j,\,
\text{clip}(\rho_{j,t},1-\epsilon,1+\epsilon)\widehat A_j
\right]
-\lambda D_{j,t}
\right\}
\right].
```

$G$는 실행 집단 크기, $L_j$는 출력 길이, $\epsilon$은 정책 변화 제한 폭, $\lambda$는 기준 정책과의 KL 벌점 가중치, $D_{j,t}$는 해당 문맥에서 현재 정책과 기준 정책 사이의 KL 항입니다. $\mathbb E$는 과제와 생성 출력에 대한 평균을 뜻합니다.

> **용어 풀이 — GRPO·clipping:** GRPO는 같은 문제에 대한 여러 실행을 서로 비교해 상대적으로 좋은 행동을 강화합니다. Clipping은 한 번의 학습에서 정책이 지나치게 바뀌지 않도록 확률비를 제한합니다.

**주의:** 위 식은 GRPO의 배경 설명입니다. SCLATE 논문이 실제 코드의 모든 clipping 값, 보상 분산이 0일 때의 처리, 세부 손실 정규화까지 보고한 것은 아닙니다. 또한 **MetaClaw의 보상 없는 증류 실험과 SWE-Gym의 보상 기반 GRPO 실험을 같은 학습 조건으로 취급하면 안 됩니다.**

## 9. 결론과 후속 연구: 일반화 성능 향상을 중심으로

### 9.1 연구자들이 제시한 시사점과 후속 계획

**[저자 보고]** 결론의 핵심은 다음과 같습니다. 벤치마크와 에이전트는 각각의 어댑터로 공유 스케줄러에 연결할 수 있고, 장기 시나리오는 유휴 시간을 압축해 실행할 수 있으며, 모델·하네스·메모리는 함께 평가해야 합니다. 또한 기존 실행 환경을 유지한 후속 학습으로 문맥 사용과 메모리 기록 행동을 바꿀 수 있다고 정리합니다. **[p. 10, Conclusion]** 2609.32391v2

**구체적인 후속 실험 일정이나 명시적인 연구 로드맵은 결론에 제시되지 않습니다.** 따라서 아래 방향은 저자 계획이 아니라, 이 논문의 결과와 공백에 근거한 추가 제안입니다.

### 9.2 추가 후속 연구 방향

#### A. 하나의 모델을 여러 하네스·메모리 조합에서 학습시키고, 보지 못한 조합으로 평가해야 한다

현재 결과는 특정 하네스에 적응한 것과 일반적인 도구 사용 능력을 얻은 것을 충분히 분리하지 못합니다. 같은 초기 모델을 단일 하네스 학습과 혼합 하네스 학습으로 나누고, 학습에서 제외한 하네스·메모리 조합에 평가하는 것이 우선입니다.

예를 들어 Claude Code와 Hermes를 섞어 학습한 모델을 Codex에서 평가하거나, Mem0 없이 학습한 모델이 Mem0를 처음 접했을 때도 개선되는지 볼 수 있습니다. **예상되는 이점은 특정 도구 이름·문맥 형식에만 적응하는 현상을 줄이는 것이지만, 실제 이득은 검증 대상입니다.** 이는 Table 1의 강한 구성 의존성을 직접 다루는 설계입니다. 2609.32391v2

#### B. 행동 능력과 기억 생성 능력을 분리해야 한다

행동 모델과 사실 추출 모델에 대해 ‘기본/학습’의 $2\times2$ 비교를 수행해야 합니다. 여기에 동일 대화를 입력하는 추출 실험과, 저장된 기억을 서로 바꾸는 평가를 추가하면 기록 변화가 실제 문제 해결에 기여했는지 확인할 수 있습니다.

기록 길이뿐 아니라 **정확성, 중복률, 나중에 검색된 비율, 검색 후 성공률, 오래된 정보의 수정 성공률**을 측정하는 것이 좋습니다. Figure 5와 Figure 18은 이런 실험의 출발점이지 최종 인과 증거는 아닙니다. 2609.32391v2

> **용어 풀이 — 인과 분리 실험:** 여러 요소를 동시에 바꾸지 않고 한 요소씩 바꾸어, 무엇이 성능 변화의 원인인지 확인하는 실험입니다.

#### C. 시간 일반화를 새로운 사용자·저장소·규칙 일반화로 확장해야 한다

동일한 30일 시나리오의 뒤쪽만 남겨두는 평가에 더해, 사용자·프로젝트·코드 저장소·업무 규칙 자체가 다른 평가가 필요합니다. 규칙이 중간에 바뀌는 상황도 포함해야 합니다. 그래야 “예전 규칙을 더 잘 기억한다”와 “새 상황에 맞게 기억을 갱신한다”를 구분할 수 있습니다.

특히 학습용 교사 정보는 학습 분할별로 물리적으로 나누고, 평가 로그에는 교사 접근이 없음을 남기는 방식이 재현성과 일반화 주장에 도움이 됩니다. **[설계 동기: Appendix E.2의 전체 라운드 교사 문맥]** 2609.32391v2

#### D. 일반화 향상과 기존 능력 보존을 함께 측정해야 한다

다음 두 지표를 함께 보고하는 평가를 제안합니다. **아래 식은 SCLATE의 원문 수식이 아니라 후속 평가용 정의입니다.**

```math
\Delta_{\text{unseen}}
=
\frac{1}{K}
\sum_{k=1}^{K}
\left[
\text{Acc}_{\text{trained}}(U_k)
-
\text{Acc}_{\text{base}}(U_k)
\right],
```

```math
\Delta_{\text{retain}}
=
\frac{1}{J}
\sum_{j=1}^{J}
\left[
\text{Acc}_{\text{after}}(D_j)
-
\text{Acc}_{\text{before}}(D_j)
\right].
```

$U_k$는 학습에서 제외한 사용자·도메인·하네스 평가 집합이고 $K$는 그 집합 수입니다. $D_j$는 새 학습 이전의 능력을 측정하는 평가 집합이며 $J$는 그 수입니다. $\text{Acc}$는 동일한 평가 조건에서의 정확도입니다.

첫 번째 값이 양수여도 두 번째 값이 크게 음수라면, 새로운 환경에서는 좋아졌지만 기존 능력을 잃은 것입니다. **일반화 향상과 지속학습 성공을 함께 주장하려면 두 축을 모두 확인해야 합니다.** SDFT는 기존 능력 보존을 명시적으로 시험하는 비교 대상으로 적합합니다. [arXiv](https://arxiv.org/abs/2601.19897)

#### E. 시간 압축의 이점과 실제 배포 성능을 분리해 검증해야 한다

에이전트의 논리적 능력을 보는 평가와 실제 지연까지 포함하는 평가를 병행해야 합니다. 서버 응답 지연, 사건 도착 간격, 알림 폭주, 메모리 정리 시간 등을 바꾸어도 성능이 유지되는지 시험하면, 시뮬레이션에서 실제 배포로의 전이를 더 잘 판단할 수 있습니다.

현재 GAIA-2 점수에 하네스와 모델 제공 서버의 지연이 영향을 준다는 저자의 설명이 이 필요성을 뒷받침합니다. **[p. 8]** 2609.32391v2

#### F. 수집한 실행 기록의 학습 단위와 비용을 명시해야 한다

같은 과제라도 하네스에 따라 모델 호출 수와 기록 분할 수가 달라집니다. 따라서 호출 단위가 많은 실행이 의도치 않게 더 큰 학습 가중치를 받지 않는지 확인해야 합니다. Agent Lightning v1.0의 실행 단위 이득 계산·손실 정규화 분석은 이 문제를 직접 다룹니다. SCLATE에 이러한 검증을 결합하면, 학습 효과가 기록 형식의 차이에서 발생한 것인지 행동 개선에서 발생한 것인지 더 명확해집니다. [arXiv](https://arxiv.org/html/2608.17528)

### 최종 평가

**SCLATE의 가장 큰 가치는 ‘일반화를 달성한 완성된 에이전트’보다, 일반화와 지속학습을 실제 시스템 수준에서 검증할 수 있는 실행 기반을 제시했다는 데 있습니다.** 시간적 전이와 소프트웨어 공학 과제 전이에 대한 긍정적인 결과는 있지만, 구성별 편차, 제한된 반복, 메모리의 인과 기여 미분리, 기존 능력 보존 평가 부재 때문에 그 범위를 넓혀 해석해서는 안 됩니다.

앞으로 가장 결정적인 실험은 **미관측 사용자·도메인·하네스로의 전이와 기존 능력 보존을, 동일 비용·반복 실행·엄격한 정보 분리 아래 동시에 보여주는 것**입니다. 그 결과가 확보된다면 SCLATE는 단순한 평가 편의 도구를 넘어, 모델과 실행 환경의 공동 학습을 연구하는 중요한 기반이 될 수 있습니다.
