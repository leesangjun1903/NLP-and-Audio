## 2. 연구의 목적과 필요성

### 2.1 해결하려는 문제는 “문제 생성”보다 “유효한 훈련장 생성”이다

**[저자 보고]** 기존 에이전트 훈련장은 과제뿐 아니라 도구, 데이터, 접근 권한, 실행 상태, 성공 판정까지 사람이 맞춰 만들어야 합니다. 이렇게 만든 과제 분포는 모델이 발전해도 자동으로 바뀌지 않으며, 공개 과제가 반복적으로 사용되면 평가 데이터 오염에 노출될 수 있습니다. 반대로 LLM으로 문제 문장만 대량 생성하면, 문장은 복잡해도 실제 추론 구조는 단순하거나 정답이 제대로 정의되지 않을 수 있다는 것이 저자들의 문제의식입니다. **[pp. 1–2]** 2609.22592v1

> **용어 설명:** *평가 데이터 오염*은 테스트 문제가 사전학습이나 후속 학습에 이미 포함되어, 새로운 문제를 푸는 능력과 암기 효과를 구분하기 어려워지는 현상입니다.

**[해석]** 여기서 중요한 구분은 **“어려워서 실패한 과제”와 “잘못 만들어져서 실패한 과제”**입니다. 예를 들어 필요한 정책 문서가 환경에 없는데 정책 준수 여부를 답하라고 하면, 낮은 점수는 모델의 추론 한계가 아니라 과제 결함을 반영합니다. AutoGym은 이 둘을 분리하기 위해 해법과 필요한 정보의 존재를 먼저 점검하도록 설계되었습니다. 실제로 저자들도 낮은 점수만으로 좋은 과제임을 입증할 수 없다고 명시합니다. **[p. 8]** 2609.22592v1

### 2.2 일반화 연구에서 왜 중요한가

**[해석]** 일반화를 연구하려면 단순히 문제 수를 늘리는 것보다, **어떤 추론 구조·도구 조건·방해 요소를 학습했고 무엇을 보지 못했는지 통제할 수 있어야 합니다.** AutoGym의 명시적 생성 매개변수는 이러한 실험 설계를 가능하게 할 잠재력이 있습니다. 다만 논문이 보여주는 “다른 도메인에도 생성 파이프라인을 적용할 수 있다”는 결과와, “그 환경으로 학습한 모델이 다른 도메인에서 잘한다”는 결과는 서로 다릅니다. 논문은 전자에 대한 사례를 제시하지만 후자를 직접 검증하지는 않습니다. **[p. 4; pp. 19–22]** 2609.22592v1 2609.22592v1 2609.22592v1

> **용어 설명:** *일반화*는 학습 중 보지 못한 문제에서도 능력을 유지하는 것입니다. *도메인*은 조달, 교육, 클라우드 운영처럼 과제가 속한 업무 영역입니다.

## 4. 제안 방법과 시스템 구조 — 수식 포함

### 4.1 새로운 신경망 구조가 아니라 환경 생성 시스템이다

**[저자 보고]** AutoGym은 새로운 Transformer 구조나 독자적인 학습 손실함수를 핵심 기여로 제안하지 않습니다. 중심은 **설계도 생성 → 환경 구현 → 정답·검증기 조립 → 평가 → 실패 분석**의 파이프라인입니다. 주 실험에서 생성에는 Claude Sonnet 4.6을 사용하고, 평가 대상은 Claude Opus 4.6과 gpt-oss-120b입니다. 평가 에이전트에게는 문제와 환경 접근만 제공하며, blueprint·정답·검증 기준은 숨깁니다. **[p. 3, Figure 1; p. 7]** 2609.22592v1 2609.22592v1

| 구성 요소 | 역할 |
|---|---|
| 생성기 | 도메인, 도구 명세, 시나리오, 사용자 역할을 바탕으로 blueprint 생성 |
| 환경 구현부 | 데이터, 관계, 권한, 방해 요소를 실제 도구로 접근 가능한 환경에 배치 |
| 정답 계산부 | blueprint의 해법을 구현된 환경에 실행하여 기준 정답 계산 |
| 검증부 | 결과·과정·방해 요소 대응·필요시 사용자 선호 준수 평가 |
| 평가 에이전트 | 숨겨진 정답을 보지 않고 문제 해결 |
| 실패 분석·커리큘럼 조정부 | 반복 실패를 찾아 다음 생성 매개변수의 분포 조정 |

위 구분은 Figure 1과 방법론을 정리한 것입니다. 검증에 쓰이는 모든 LLM의 구체적인 모델명이나, 부록의 8B 학습 모델의 정확한 체크포인트 이름은 명시되어 있지 않습니다. **[Figure 1; Appendix C, G]** 2609.22592v1 2609.22592v1 2609.22592v1

> **용어 설명:** *파이프라인*은 여러 처리 단계를 순서대로 연결한 시스템입니다. *체크포인트*는 특정 학습 시점의 모델 매개변수를 저장한 것입니다.

### 4.2 Blueprint-first 생성

**[저자 보고]** Blueprint에는 문제의 운영 맥락, 정답에 필요한 개체와 속성, 정보 간 의존 관계, 올바른 결과의 조건이 포함됩니다. 이때 특정 도구 호출 순서 하나를 반드시 정답 경로로 강제하기보다, 해결에 필요한 정보와 중간 조건을 정의하려고 합니다. 이후 질문에서 일부 정보를 지우고, 그 정보를 환경에서 찾아낼 수 있도록 배치합니다. **[pp. 4–5]** 2609.22592v1

**[설명용 수식 재구성 — 논문에 그대로 제시된 원식은 아님]**

주 실험의 생성 과정을 다음처럼 표현할 수 있습니다.

$$
B=\text{Blueprint}(x,z),
\qquad
E=\text{Materialize}(B),
$$

$$
y^\star=\text{Execute}(D_B,E),
\qquad
V=\text{AssembleVerifier}(B,y^\star).
$$

여기서 $x$는 도메인·도구 명세 등의 입력, $z$는 난도와 구조를 조절하는 생성 매개변수, $B$는 blueprint, $E$는 구현된 환경입니다. $D_B$는 blueprint에 정의된 정답 도출 절차, $y^\star$는 환경에서 계산한 기준 정답, $V$는 검증기입니다. 핵심은 **생성 모델이 처음 제안한 숫자를 정답으로 믿지 않고, 만들어진 환경에서 다시 계산한다**는 점입니다. **[pp. 5–6]** 2609.22592v1

**[해석]** 이는 소프트웨어 개발에서 명세와 테스트를 먼저 정하고 구현을 맞추는 방식과 유사합니다. 다만 설계도 자체가 잘못된 업무 가정을 포함할 가능성까지 제거하지는 않습니다. **“정해진 명세를 만족한다”와 “그 명세가 사용자의 실제 의도에 맞다”는 별개의 문제**입니다.

### 4.3 해결 가능성 불변조건

**[저자 보고]** 질문과 에이전트가 접근 가능한 환경에는 검증 조건을 만족하는 데 필요한 정보가 충분히 있어야 합니다. 방해 요소는 탐색을 어렵게 만들 수 있지만, 모든 올바른 해결 경로를 막아서는 안 됩니다. 숨긴 값은 어디서 발견할 수 있는지 기록하고, 실제로 해당 자원이 존재하는지 검사합니다. **[p. 5; pp. 15, 24–25]** 2609.22592v1 2609.22592v1 2609.22592v1

**[설명용 수식 재구성]**

$$
\mathcal I_{\text{required}}(B)
\subseteq
\mathcal I(q)
\cup
\mathcal I_{\text{reachable}}(E,\mathcal T,p).
$$

$q$는 사용자에게 제시되는 질문, $\mathcal T$는 사용 가능한 도구, $p$는 사용자 역할과 접근 권한입니다. $\mathcal I_{\text{required}}(B)$는 해법에 필요한 정보 집합, $\mathcal I(q)$는 질문에 이미 주어진 정보, $\mathcal I_{\text{reachable}}$은 도구와 권한을 통해 발견할 수 있는 정보입니다.

이를 해결 경로 관점에서 표현하면 다음과 같습니다.

$$
\exists \tau \in \mathcal A(q,E,\mathcal T,p)
\quad \text{such that} \quad
C_B(\tau,E)=1.
$$

$\tau$는 도구 사용과 응답으로 이루어진 실행 경로, $\mathcal A$는 허용된 실행 경로 집합, $C_B$는 blueprint가 요구하는 성공 조건입니다.

> **용어 설명:** *불변조건*은 과정이 어떻게 진행되든 유지되어야 하는 조건입니다. 여기서는 “필요한 정보를 실제로 찾아 정답에 도달할 수 있어야 한다”는 뜻입니다.

**[해석]** 이 수식은 저자들의 설계 의도를 명확히 한 것이지, 논문이 정리와 증명으로 보장한 결과가 아닙니다. 정보가 존재해도 질문이 모호하거나, 어느 자료가 권위 있는지 판단할 근거가 부족하거나, 허용된 도구 호출 예산 안에서 찾을 수 없다면 실질적인 해결 가능성은 여전히 문제가 됩니다.

또한 **클라우드 부록에는 중요한 구현 차이**가 있습니다. 주 실험은 구현된 환경에서 정답을 계산하지만, Appendix E는 선언적 상태 정의의 `_ground_truth` 주석에서 정답을 계산하며 실제 실행 환경을 통한 재확인은 선택적입니다. 따라서 두 구현의 검증 강도를 동일하게 간주하면 안 됩니다. **[pp. 19–21]** 2609.22592v1 2609.22592v1

### 4.5 실제 예시: 납기 준수율 계산

**[저자 보고]** 조달 예시에서는 에이전트가 관련 지역·품목·분기를 찾아 배송 기록을 필터링하고, 정책 테이블에서 기준치를 확인해야 합니다. 다른 지표의 85% 기준, 지역이 재분류된 기록, 폐기된 품목 이름, 페이지당 50개 제한 등이 방해 요소입니다. 올바른 결과는 96건 중 78건이 정시 배송되어 81.25%이며, 적용 기준 90%를 만족하지 못합니다. **[pp. 5–6]** 2609.22592v1 2609.22592v1

**[원문의 수치 관계를 수식으로 표현]**

```math
\text{OTD}
=
100\cdot
\frac{N_{\text{on-time}}}{N_{\text{eligible}}}
=
100\cdot\frac{78}{96}
=
81.25\%.
```

```math
\text{Compliance}
=
\mathbf 1[\text{OTD}\geq T]
=
\mathbf 1[81.25\geq90]
=
0.
```

$N_{\text{on-time}}$은 정시 배송 건수, $N_{\text{eligible}}$은 올바른 조건으로 걸러낸 전체 배송 건수, $T$는 정책 기준치입니다. $\mathbf 1[\cdot]$은 조건이 참이면 1, 거짓이면 0을 반환합니다.

**[해석]** 어려움은 나눗셈 자체보다 **정확한 분모를 만들고 올바른 정책을 고르는 과정**에 있습니다. 이것이 저자들이 말하는 “겉보기 문장 난도”와 “실제 에이전트 과제 난도”의 차이입니다.

### 4.7 적응형 커리큘럼

**[저자 보고]** 여러 실행 결과를 능력별로 집계하여 성공 수준이 0.30보다 낮으면 해당 차원을 완화하고, 0.80보다 높으면 강화합니다. 조정 폭을 제한하여 과도한 진동을 줄이며, 성능이 안정되거나 반복 한도에 도달할 때까지 진행하도록 설계합니다. **[p. 6, §3.6]** 2609.22592v1

**[설명용 수식 재구성]**

$$
\widehat s_{k,t}<0.30
\Rightarrow
\text{Relax}(k),
\qquad
\widehat s_{k,t}>0.80
\Rightarrow
\text{Strengthen}(k).
$$

$\widehat s_{k,t}$는 생성 라운드 $t$에서 능력 축 $k$에 대해 집계한 성공 수준입니다. $\text{Relax}$와 $\text{Strengthen}$은 해당 축을 겨냥한 과제를 더 쉽게 또는 더 어렵게 만드는 조정을 뜻합니다.

**[검토]** 논문은 정확한 가중치 갱신식, 조정 폭, 안정화 판정 기준을 충분히 명세하지 않습니다. 또한 시간 추론 실험은 실패에서 출발한 **표적 과제 생성**을 보여주지만, “생성 → 모델 학습 → 재평가 → 재생성”을 여러 차례 반복했을 때의 추가 이익을 정량적으로 제시하지는 않습니다. **[pp. 6, 8–9]** 2609.22592v1 2609.22592v1

## 5. 실험 결과: 무엇이 개선되었고, 무엇은 아직 모르는가

### 5.1 평균 검증 점수와 성공률을 먼저 구분해야 한다

**[저자 정의]** 과제마다 8회 실행하고, 개별 실행의 검증 점수가 정확히 1일 때 성공으로 봅니다. 반면 hard/medium/easy 구분은 8회 실행의 **평균 검증 점수**로 정합니다. **[p. 7]** 2609.22592v1

**[정의의 수식화]**

```math
\overline r_i
=
\frac{1}{8}\sum_{j=1}^{8}r_{ij},
\qquad
\widehat p_i
=
\frac{1}{8}\sum_{j=1}^{8}\mathbf 1[r_{ij}=1].
```

$r_{ij}\in[0,1]$은 과제 $i$의 $j$번째 실행 점수, $\overline r_i$는 평균 점수, $\widehat p_i$는 논문 정의에 따른 실행 성공률입니다.

$$
\text{Band}(i)=
\begin{cases}
\text{hard}, & \overline r_i<0.30,\\
\text{medium}, & 0.30\leq\overline r_i<0.80,\\
\text{easy}, & \overline r_i\geq0.80.
\end{cases}
$$

경계값 0.80은 원문의 easy 정의에 따라 easy에 포함했습니다.

**[중요한 해석]** 평균 점수와 성공률은 같지 않습니다. 예를 들어 8회 모두 0.9점이면 평균은 0.9여서 easy이지만, 점수 1만 성공으로 세는 정의에서는 성공률이 0입니다. 이는 설명용 예시이며, 실제 실험에서 이런 과제가 몇 개였는지는 보고되지 않았습니다. 따라서 **“easy 과제가 89%”를 “성공률 89%”로 바꾸어 쓰면 안 됩니다.**

### 5.6 강화학습: 훈련 보상 상승과 일반화는 다르다

**[저자 보고]** 지시 준수 실패에서 생성한 600개 과제를 사용하여 8B 모델에 500단계 GRPO를 적용했고, 훈련 보상이 증가했습니다. 이 600개는 생성 비용·확장성 설명에 등장하는 **6개 도메인 600개 과제와 별도의 실험**입니다. **[p. 7; p. 22, Figure 2]** 2609.22592v1 2609.22592v1

> **용어 설명:** *GRPO*는 같은 문제에 대한 여러 응답의 보상을 서로 비교하여, 상대적으로 좋은 응답을 더 자주 만들도록 학습하는 강화학습 방법입니다. 별도 가치 모델 대신 그룹 내 보상을 활용하는 방법으로 DeepSeekMath에서 제안되었습니다. [arXiv](https://arxiv.org/html/2402.03300v3)

GRPO의 기본 상대 보상 개념은 다음과 같습니다. **이 식은 AutoGym의 독자적 제안이 아니라 GRPO 원 연구의 설명입니다.**

```math
\widehat A_j
=
\frac{r_j-\text{mean}(\mathbf r)}
{\text{std}(\mathbf r)}.
```

$\mathbf r$은 같은 문제에서 생성한 응답들의 보상 집합, $r_j$는 응답 $j$의 보상, $\widehat A_j$는 그룹 평균보다 얼마나 좋은지를 나타내는 상대적 이점입니다. 이 표현은 보상 표준편차가 0이 아닌 경우에 해당하며, AutoGym은 이러한 세부 구현과 예외 처리까지 보고하지 않습니다. [arXiv](https://arxiv.org/html/2402.03300v3)

**[해석]** Figure 2는 유효한 최적화 신호가 있다는 초기 증거입니다. 그러나 훈련 보상 증가는 과제 암기, 특정 판정기에 대한 적응, 일반적인 능력 향상을 구분하지 못합니다. 외부 평가와 대조군이 있어야 이 차이를 판별할 수 있습니다.

### 6.2 원문 내부에서 확인되는 불일치

**① 시간 추론 비율의 본문–표 불일치**

본문은 Opus easy 비중을 89.1%라고 쓰지만 Table 4는 89.2%라고 표시합니다. 또한 본문의 gpt-oss hard+medium 41.4%와 표의 합 41.3%도 다릅니다. 원시 과제별 데이터와 반올림 규칙이 없어 이를 임의로 통일해서는 안 됩니다. **[pp. 8–9]** 2609.22592v1

**② 교육 예시의 산술적 불일치 가능성**

Appendix D의 Lincoln Heights 행에는 `due=24`, `on_time=20`, `pct=84.6`이 기록되어 있고, 정답표도 84.6%와 기준 대비 0.4퍼센트포인트 부족을 사용합니다. **[pp. 18–19]** 2609.22592v1 2609.22592v1

그러나 `pct`가 해당 행의 `on_time / due`를 뜻한다면,

$$
100\cdot\frac{20}{24}\approx83.33\%,
\qquad
85-83.33\approx1.67
$$

이므로 표의 84.6%, 부족분 0.4와 일치하지 않습니다. **다른 분모나 별도 정의를 사용했는지는 문서가 설명하지 않습니다.** 따라서 이를 임의로 고쳐 정답이라고 제시할 수는 없지만, 정답 계산과 환경 일관성 검사에 대한 추가 감사가 필요한 구체적인 사례입니다.

**③ “약 100배 빠름”의 해석 범위**

Table 8의 과제당 시간은 전문가 60–90분 대 AutoGym 15.6분이므로, 이 값만 비교하면 약 **3.85–5.77배**입니다. Table 9의 50개 배치 비교는 AutoGym의 20개 병렬 실행을 포함하며, 사람 측 시간은 2–4주로 제시됩니다. 따라서 본문의 “약 100배”를 **단일 과제의 동일 자원 조건 지연시간 개선**으로 읽으면 안 됩니다. **[p. 22, Tables 8–9; 배율은 직접 계산]** 2609.22592v1

### 6.3 특히 직접 비교하면 안 되는 수치

### 8.2 검증 방식의 중요한 비교: EnvScaler

EnvScaler는 최종 상태에 대해 여러 검사 함수를 실행한 뒤 통과 비율을 보상으로 사용합니다. 원 논문 §4.2의 식 (10)을 간단히 쓰면 다음과 같습니다.

```math
R_{\text{state}}
=
\frac{1}{K}
\sum_{k=1}^{K}
\mathbf 1[f_k(s_{\text{final}})=\text{True}].
```

$K$는 검사 조건 수, $f_k$는 조건 $k$의 검사 함수, $s_{\text{final}}$은 실행 종료 후 환경 상태입니다. 이 방식은 최종 상태를 중심으로 검사하므로 여러 합법적 해결 경로를 허용할 수 있습니다. [arXiv](https://arxiv.org/html/2601.05808v1)

**[해석]** AutoGym의 과정 평가는 실패 원인 분석과 부분 보상에 유용할 수 있지만, 참조 경로에 대한 편향을 추가할 수 있습니다. 따라서 **상태 기반 결과 검증만 사용하는 경우와 과정 점수를 함께 사용하는 경우의 일반화·보상 악용·대체 해법 수용성을 비교**하는 것이 중요합니다.

> **용어 설명:** *보상 악용*은 실제 목적을 달성하기보다 채점기의 허점을 이용해 높은 점수를 얻는 현상입니다.

### 8.3 최신 연구를 고려한 독창성 평가

**[해석]** AutoGym을 “자동 환경 생성, 난도 조절, 실행 기반 검증, 적응형 커리큘럼을 처음 제안한 연구”로 평가하는 것은 부정확합니다. 위 선행 연구들에 각각의 요소가 존재합니다. 보다 좁고 설득력 있는 독창성은 다음의 **통합 방식**입니다.

**해법과 검증 조건을 먼저 구조화하고, 그 구조를 보존하면서 질문의 구체성과 환경 방해 요소를 조절하며, 결함 수리와 능력 부족에 대한 커리큘럼 조정을 분리한다**는 것입니다. 이 통합이 실제 학습 효율과 일반화를 높이는지는 추가 실험이 필요합니다. 2609.22592v1 2609.22592v1

서지상 주의점도 있습니다. AutoGym 참고문헌은 EnvScaler를 2025년으로 표기하지만, 확인된 arXiv 최초 공개일은 **2026년 1월 9일**입니다. 위 비교에서는 외부 원문의 공개 연도를 사용했습니다. 2609.22592v1 [arXiv](https://arxiv.org/abs/2601.05808)

## 9. 모델의 일반화 성능을 높일 가능성과 검증 방법

### 9.1 가능성이 있는 이유 — 아직은 가설이다

**[해석 1: 추론 요소의 새로운 조합]** 과제 구조와 능력 축을 분리하면, 예를 들어 학습에서는 시간 추론과 단일 출처 계산을 각각 익히고, 테스트에서는 시간 추론·다중 출처·페이지 넘김을 함께 요구할 수 있습니다. 이것은 단순한 이름 변경보다 강한 **조합적 일반화** 실험을 가능하게 합니다. 다만 논문의 “구조적으로 독립적인 축”이 실제 생성 데이터에서도 통계적으로 독립적이라는 보장은 없습니다. **[근거: Appendix A.1–A.2]** 2609.22592v1 2609.22592v1

> **용어 설명:** *조합적 일반화*는 이미 배운 능력들을 학습 때 보지 못한 조합으로 사용할 수 있는 능력입니다.

**[해석 2: 답을 추측하기보다 환경에서 기준을 찾는 습관]** 질문에서 정책 기준을 빼고 환경에서 검색하게 하면, 에이전트가 익숙한 숫자를 추측하기보다 근거를 확인하도록 학습할 가능성이 있습니다. 그러나 질문을 지나치게 모호하게 만들면, 정보 탐색보다 사용자 의도 추측을 강요할 수 있으므로 **명확화 질문을 해야 하는 과제**도 함께 설계해야 합니다. **[근거: Appendix A.3]** 2609.22592v1

**[해석 3: 방해 정보에 대한 강건성]** 오래된 정책, 잘못된 버전, 유사 이름의 자료를 구분하는 학습은 실무형 오류를 줄일 잠재력이 있습니다. 다만 C1/C2는 도구 방해 채널을 활성화하지 않았으므로, 도구 장애나 실제 API의 비정상 동작에 대한 강건성 향상까지 주장할 수는 없습니다. **[근거: Appendix A.4–A.5]** 2609.22592v1 2609.22592v1

> **용어 설명:** *강건성*은 잡음, 잘못된 자료, 예외 상황이 있어도 성능이 크게 무너지지 않는 성질입니다.

**[해석 4: 약점에 집중하는 표본 효율]** 이미 잘 푸는 과제를 반복하기보다 학습 가능한 약점을 겨냥하면 상호작용 예산을 효율적으로 사용할 가능성이 있습니다. 하지만 한 약점만 반복하면 다른 능력이 약화되거나 생성기의 스타일에 과적합될 수 있습니다. AutoEnv의 결과도 다양한 환경에서 단일 학습 전략의 효과가 계속 유지되지 않을 수 있음을 보여줍니다. [arXiv](https://arxiv.org/abs/2511.19304)

### 9.2 일반화를 입증할 핵심 평가식

**[후속 연구 제안 — AutoGym 원문의 식이 아님]**

```math
\Delta_{\text{OOD}}
=
\mathbb E_{g\sim P_{\text{test}}}
\left[
S(\pi_{\text{AutoGym}},g)
-
S(\pi_{\text{control}},g)
\right].
```

$g$는 테스트 과제와 환경, $P_{\text{test}}$는 학습 때 보지 않은 환경의 분포입니다. $\pi_{\text{AutoGym}}$은 AutoGym으로 학습한 모델, $\pi_{\text{control}}$은 같은 초기 모델과 학습 예산을 사용한 대조 모델입니다. $S$는 **동일하고 독립적으로 검증된 평가 기준**에 따른 성공 지표이며, $\Delta_{\text{OOD}}$는 외부 환경에서 얻는 순수한 성능 차이입니다.

> **용어 설명:** *OOD, out-of-distribution*은 학습 데이터의 분포에서 벗어난 경우입니다. 새로운 업무 분야, 도구 형식, 추론 조합 등이 해당할 수 있습니다.

이 값을 신뢰할 수 있게 추정하려면 다음 분리를 권합니다.

| 일반화 종류 | 학습·테스트를 어떻게 나눌 것인가 |
|---|---|
| 도메인 일반화 | 조달·교육 등 일부 도메인 전체를 테스트용으로 남김 |
| 구조 일반화 | 특정 의존 구조나 능력 조합 전체를 학습에서 제외 |
| 도구 일반화 | 같은 목적을 다른 API·스키마·권한 체계로 수행하게 함 |
| 길이 일반화 | 학습보다 더 긴 정보 의존 관계와 상호작용을 요구 |
| 현실 환경 전이 | 모의 데이터베이스가 아니라 실제와 가까운 API 또는 별도 샌드박스에서 평가 |
| 판정기 일반화 | 학습 보상에 사용한 LLM과 독립적인 실행 검사·사람 평가로 테스트 |

**단순 무작위 과제 분할만으로는 부족합니다.** 같은 blueprint에서 이름과 숫자만 바뀐 과제가 학습과 테스트에 나뉘면, 실제보다 일반화가 좋아 보일 수 있습니다.

### 9.3 우선순위가 높은 후속 실험

**첫째, blueprint-first의 인과적 효과를 분리해야 합니다.** 같은 도메인, 도구, 생성 모델, 토큰 예산에서 과제 우선 생성과 blueprint 우선 생성을 비교하고, 해결 불가능 과제 비중·검증 오류·외부 학습 성과를 함께 측정해야 합니다. 난도 상승만으로 blueprint-first의 학습상 이점을 입증할 수는 없습니다.

**둘째, 커리큘럼은 정적 분포와 비교해야 합니다.** 같은 총 과제 수와 학습량을 사용해 고정 분포, 무작위 난도 조절, 실패 기반 조절을 비교해야 합니다. 평가용 고정 과제 집합도 유지해야, 생성 분포가 바뀌어서 점수가 달라진 것과 모델이 좋아진 것을 구분할 수 있습니다.

**셋째, 검증기를 독립적으로 시험해야 합니다.** 정답은 맞지만 도구 경로가 다른 실행, 계산은 틀렸지만 설명이 그럴듯한 실행, 권한을 위반해 답을 얻은 실행 등을 의도적으로 만들어 오판율을 측정해야 합니다. 데이터 순서를 바꾸거나 무관한 자료를 추가해도 정답이 유지되는지 검사하는 방법도 유용합니다.

**넷째, 폭넓은 과제와 표적 과제를 혼합하는 설계를 검증할 필요가 있습니다.** 예를 들어 다음은 가능한 후속 설계입니다.

```math
p_t(z)
=
(1-\lambda)p_{\text{coverage}}(z)
+
\lambda p_{\text{target},t}(z),
\qquad
0\leq\lambda\leq1.
```

$z$는 생성 설정, $p_{\text{coverage}}$는 다양한 능력을 유지하는 기본 분포, $p_{\text{target},t}$는 현재 약점을 겨냥한 분포, $\lambda$는 표적 학습 비중입니다. **이 혼합식은 제 제안이며 AutoGym의 구현식이 아닙니다.** 목표는 약점 개선과 기존 능력 유지의 균형을 시험하는 것입니다.

## 11. 결론: 연구적 시사점과 후속 방향

### 저자들이 제시한 시사점과 계획

**[저자 보고]** 에이전트 훈련장 구축은 수작업으로 고정된 벤치마크를 만드는 활동에 머무르지 않고, 자동 생성·난도 제어·성능 기반 갱신이 가능한 대상으로 바뀔 수 있다는 것이 결론입니다. 명시적인 후속 과제는 더 다양한 모델 규모와 긴 학습, 여러 도메인의 강화학습, 실제 API와 더 가까운 환경, 개방형 검증의 개선, 클라우드 실행 환경에서의 난도·구별력 평가입니다. **[p. 9, §§5–6]** 2609.22592v1

### 종합 판단

**[해석]** AutoGym의 중요한 전환은 **“문제를 많이 만들자”에서 “해결 조건과 검증 근거를 함께 설계하자”로 초점을 옮긴 것**입니다. 이 방식은 평가 실패의 원인을 분리하고, 추론 구조를 통제하며, 새로운 능력 조합을 시험하는 데 유용할 가능성이 있습니다.

하지만 현재 결과로 확인되는 것은 **난도 조절, 두 모델 간 구별, 수리·감사 후 과제 유지, 훈련 보상 상승**입니다. **일반화 향상, 최적의 커리큘럼, 완전한 검증 신뢰성, 공정한 총비용 우위는 아직 확인되지 않았습니다.**

**[후속 연구 제안]** 가장 우선할 연구는 더 많은 과제를 생성하는 실험보다, **같은 초기 모델·같은 총예산·독립 검증기·blueprint 단위로 분리된 외부 테스트를 사용하는 비교 실험**입니다. 그 실험에서 외부 성능 향상이 반복적으로 확인된다면, AutoGym은 단순한 벤치마크 생성기를 넘어 **일반화 능력을 체계적으로 훈련하는 환경 설계 방법**으로 평가받을 수 있습니다.
